## Overview

Co-moderated by [SFC](../../people/SFC.md). The main outcomes: TG2 settled the open design issues of NumberFormat v3 (`roundingIncrement` rules, a longer list of accepted increments, `roundingPriority: "auto"`) and then gave TG2 approval for NumberFormat v3 to go to Stage 3, and also agreed that Intl Enumeration API should proceed to Stage 3 at TC39. A debate on specifying the sort order of `pluralCategories` ended without a conclusion, and a side discussion on cross-browser data inconsistency led to talk of a consistency handbook. [RCA](../../people/RCA.md) gave the MessageFormat Working Group and MDN updates but is not in the attendee list. [USA](../../people/USA.md)'s comment on PR #581 was relayed from the issue thread rather than spoken on the call.

## MessageFormat Working Group

[RCA](../../people/RCA.md) reported a Q&A session held to help the group understand the data model options and unblock progress; there is no conclusive answer yet, and work continues at the next Extended and Plenary meetings. [EAO](../../people/EAO.md) added that two data model proposals still exist (one by Mihai Niță, one by [EAO](../../people/EAO.md)), but the group's understanding of the differences between them is improving; the two shared documents describe the same thing from each side.

## MDN

## Editorial: mention "cf" in Note 1 of #sec-intl.numberformat-internal-slots #581

- proposal: [ecma402#581](https://github.com/tc39/ecma402/pull/581)

[FYT](../../people/FYT.md)'s PR adds a note that the `cf` extension is not supported by `NumberFormat`, matching other notes about unsupported extension keys. [USA](../../people/USA.md) (via the issue thread) asked how to handle the list of extension keywords growing as BCP 47 evolves. [RGN](../../people/RGN.md) saw nothing actionable now; [SFC](../../people/SFC.md) suggested a systematic approach to keeping ECMA-402 in sync with UTS 35 (as discussed earlier for numbering systems), and [FYT](../../people/FYT.md) agreed a stance is needed. **Conclusion: Editors to make an action plan.**

## Potentially confusing behavior of RoundingIncrement with significant digits

- proposal: [proposal-intl-numberformat-v3#46](https://github.com/tc39/proposal-intl-numberformat-v3/issues/46)

[SFC](../../people/SFC.md) proposed throwing in the constructor whenever significant-digits rounding could be in effect (significant-digit options present, or rounding priority used) together with `roundingIncrement`, e.g. `maximumFractionDigits: 0` with an increment of 50 or 500. [ZB](../../people/ZB.md) worried about per-number surprises; [SFC](../../people/SFC.md) clarified the check depends only on the options bag. [EAO](../../people/EAO.md) found it surprising for `roundingIncrement` to throw instead of taking part in the priority fallback; [SFC](../../people/SFC.md) answered that the option is new, so no existing code gains an exception. **Conclusion: Accepted.**

## Limit for maximumFractionDigits option for decimal strings formatting

- proposal: [proposal-intl-numberformat-v3#34](https://github.com/tc39/proposal-intl-numberformat-v3/issues/34)

The current limit of 20 fraction digits was chosen to suffice for IEEE doubles, but arbitrary-precision input might justify raising it. [RGN](../../people/RGN.md) argued ECMA-402 should be as capable as ECMA-262 but need not go beyond, and `Number.prototype.toFixed` allows 100; [JSW](../../people/JSW.md) supported 100 for consistency. [FYT](../../people/FYT.md), [SFC](../../people/SFC.md), [JSW](../../people/JSW.md) and [RGN](../../people/RGN.md) agreed that it should be handled as a separate change rather than folded into NumberFormat v3. **Conclusion: Migrate the issue to 402.**

## Type of roundingIncrement #33

- proposal: [proposal-intl-numberformat-v3#33](https://github.com/tc39/proposal-intl-numberformat-v3/issues/33)

[FYT](../../people/FYT.md) preferred supporting only increments with known use cases; [SFC](../../people/SFC.md) wanted at least rounding to 500 (e.g. "turn left in 500 meters") and favoured increments that divide powers of 10, since arbitrary values like 7 have an unclear reference point. [EAO](../../people/EAO.md) cited a real need to round to 20 (anonymizing salary data) and the value of a final zero digit to communicate precision, which led to adding 2 and 20 variants. **Conclusion: Use [SFC](../../people/SFC.md)'s recommendation: accept `roundingIncrement` as a Number from « 1, 2, 5, 10, 20, 25, 50, 100, 200, 250, 500, 1000, 2000, 2500, 5000 ».**

## Define sort order of "pluralCategories" array #578

- proposal: [ecma402#578](https://github.com/tc39/ecma402/issues/578)

[RGN](../../people/RGN.md) and [JSW](../../people/JSW.md) favoured specifying the order to remove implementation dependence; [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md) objected that the categories are an unordered set, sorting costs CPU, and a specified order sets a precedent (and may mislead, since "one" need not contain 1). [SFC](../../people/SFC.md) raised lexicographic ordering, romanized identifiers, and userland code possibly relying on web-reality order; [FYT](../../people/FYT.md) countered that web-reality order is neither UTS 35 nor lexicographic, so specifying a different order is unproductive. [EAO](../../people/EAO.md) would prefer implementation-defined, but if an order is picked, the UTS 35 order (the one the `Intl.PluralRules` polyfill returns, drawn from CLDR). **Conclusion: No conclusion; share the notes and let the issue champion work them out.**

## Discussion on data consistency and adoption challenges

CJR raised inconsistencies between browsers (e.g. `weekday: "short"` output in Safari versus Chrome, and default numbering system for `ar`) as an adoption blocker versus third-party libraries such as Globalize. [ZB](../../people/ZB.md) and [SFC](../../people/SFC.md) replied that output strings must not be relied on and that data differences are CLDR matters ([SFC](../../people/SFC.md) explained that using Latin digits for `ar` is a Google decision, while [FYT](../../people/FYT.md) noted `ar-EG` yields Arabic digits). [SFC](../../people/SFC.md) supported a developer handbook on consistency (in section 2 of the spec or a separate markdown file) and pointed to #210 (data overlays) and ICU4X as the longer-term direction; [JSW](../../people/JSW.md) noted Annex A already lists implementation-dependent behaviour; [ZB](../../people/ZB.md) felt UX should be designed to be flexible. CJR offered to help with a consistency handbook.

## Intl Enumeration API for Stage 3

[FYT](../../people/FYT.md) addressed the two concerns from the previous meeting (use cases; iterator versus array) by switching to an array and updating the slides, and asked for Stage 3. [SFC](../../people/SFC.md) supported; [LEO](../../people/LEO.md) advised syncing offline with Jordan Harband. [ZB](../../people/ZB.md) said the group had reached a conclusion not to block, though "We do not believe this proposal is useful"; [YSZ](../../people/YSZ.md) said Apple was fine with Stage 3, preferring stronger motivation, with the fingerprinting concern resolved since Apple already ships the entire payload. **Conclusion: Proceed with Stage 3 at TC39.**
