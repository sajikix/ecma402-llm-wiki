## Overview

[SFC](../../people/SFC.md) was co-moderator. TG2 agreed to ask plenary for Stage 4 for `Intl.DisplayNames` v2 (ecma402#622) and the extend-timezonename proposal for `Intl.DateTimeFormat` (ecma402#621). `Intl.Segmenter` v2 got only partial support for Stage 1, with [MCM](../../people/MCM.md) stating Apple does not support it; it is to be presented at plenary anyway. [FYT](../../people/FYT.md) also raised concerns from the V8 [Temporal](../../proposals/temporal.md) implementation about the `Intl.DateTimeFormat` internal slots, which led to a procedural conclusion about how implementers should raise such issues. All abbreviations in the notes already match delegates.txt.

[FYT](../../people/FYT.md) asked for support to request Stage 1, citing demand and that it is already available in Safari. ## Temporal requirement to Intl.DateTimeFormat internal slots & review/Feedback - Ch15 Temporal proposal

- wiki: [Temporal](../../proposals/temporal.md)

[FYT](../../people/FYT.md), implementing [Temporal](../../proposals/temporal.md) in V8, asked for review of the [Temporal](../../proposals/temporal.md) spec's chapter 15 because the `Intl.DateTimeFormat` internal slots load multiple patterns instead of one, with high potential to slow performance and increase memory. [ZB](../../people/ZB.md) shared the concern, relayed [SFC](../../people/SFC.md)'s view that this is an architectural limitation of ICU4C to be solved in ICU4X (about six months from release), and called an architectural memory cost in all browsers unacceptable for a new feature. [FYT](../../people/FYT.md) replied that it is not only an ICU issue: the returned pattern's complexity can give different results, and exposing only one makes implementation difficult. [YSZ](../../people/YSZ.md) (Apple, also implementing [Temporal](../../proposals/temporal.md)) shared the performance and memory concern, and [MCM](../../people/MCM.md) and [YSZ](../../people/YSZ.md) asked for more description on the agenda next time. [FYT](../../people/FYT.md) also raised a procedural question, whether implementation issues like this should be brought by the [Temporal](../../proposals/temporal.md) group or discussed proactively in TG2. [ZB](../../people/ZB.md) said implementers should give feedback at Stage 3, and that the [Temporal](../../proposals/temporal.md) group should bring concerns to TG2 rather than the reverse; [SFC](../../people/SFC.md) agreed ECMA-402 is the place, but [USA](../../people/USA.md) was absent. **Conclusion: review chapter 15 to help find a possible solution; implementers can raise concerns directly with the proposal champions, and further discussion can take place in TG2.** The notes give the issue link as `tc39/proposal/issues/622`, which looks malformed (not a valid proposal repo), so no URL is recorded here.

## Strings Meta - Localizable Strings - APP

- proposal: [string-meta](https://w3c.github.io/string-meta/)

APP presented W3C string metadata for localizable strings; [ZB](../../people/ZB.md) saw a relation to localizable metadata and localization bindings in MessageFormat 2.0, and APP said the name "Localizable" may be misleading and the focus is metadata for the string. [MCM](../../people/MCM.md) gave immediate feedback that a new string type holding metadata seems reasonable, but asked for use cases and noted every API would need to decide which metadata applies. **Conclusion: follow up offline by raising GitHub issues.**
