## Overview

Moderated by [SFC](../../people/SFC.md) (co-moderator). TG2 approved two PRs to the [Intl Locale Info](../../proposals/intl-locale-info.md) proposal (#43 Annex A changes, #44 non-contiguous weekend), sent the question of defining sort order for returned lists to TG1, and agreed that the whole locale, including extension subtags, should influence week info. TOM presented a JS Input Masking idea, and the discussion pointed toward a library or Unicode working group before ECMA-402. Several ECMA-402 issues were settled with short conclusions (#608, #588, #590, #583, #564).

## Status Updates

- Editor's Update: [RGN](../../people/RGN.md) had no updates.
- MessageFormat Working Group: [RCA](../../people/RCA.md) is working on a middle-ground data model aimed at unblocking the situation; [EAO](../../people/EAO.md) put together a spec outline (not a specific proposal) expected to be merged that week.
- Proposal Status Changes: [FYT](../../people/FYT.md) reported more Test262 coverage but still needs help; [RCA](../../people/RCA.md) updated MDN browser compat for Locale Info and documentation for hour cycle.

## Change weekInfo to express non-continouse [sic] weekend

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#44](https://github.com/tc39/proposal-intl-locale-info/pull/44)

[FYT](../../people/FYT.md) explained that some regions have a non-contiguous weekend, so the data model changes. [LAF](../../people/LAF.md) wondered whether "weekend" is the right term versus "business day"; [EAO](../../people/EAO.md) found that Brunei calls these days "weekend", and [SFC](../../people/SFC.md) asked [LAF](../../people/LAF.md) to open an issue on the option name. **Conclusion: Approved.**

## CollationsOfLocale() order

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#33](https://github.com/tc39/proposal-intl-locale-info/issues/33)

[SFC](../../people/SFC.md) felt that lists should define their sort order (as in the earlier plural rule strings discussion), while [ZB](../../people/ZB.md) argued developers should not depend on the order. [RGN](../../people/RGN.md) noted that an observable order always exists; the question is whether it is enforced across implementations and what it should be. [FYT](../../people/FYT.md)'s Set suggestion did not help, since Sets are ordered too. **Conclusion: [SFC](../../people/SFC.md) to make a presentation to TC39-TG1 to establish a best practice in the style guide.**

## Define if "ca" Unicode extensions have an effect on Intl.Locale.prototype.weekInfo

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#30](https://github.com/tc39/proposal-intl-locale-info/issues/30)

[LAF](../../people/LAF.md) argued that ISO 8601 is not tied to a locale, whereas Gregorian can carry week info, and was concerned about week numbering. [SFC](../../people/SFC.md) wanted to consult CLDR, [FYT](../../people/FYT.md) held that a subdivision could legislate its own first day of week and so the whole locale should count, and [ZB](../../people/ZB.md) explained the mozIntl origin (date pickers). [RCA](../../people/RCA.md) had no strong opinion but flagged possible conflict with Temporal. **Conclusion: [SFC](../../people/SFC.md), [FYT](../../people/FYT.md) and [LAF](../../people/LAF.md) agree that the whole locale (including extension subtags) should influence the weekInfo; [FYT](../../people/FYT.md) to share these notes with Anba and wait for follow-up.**

## JS Input Masking 🎭

- proposal: [js-input-masking explainer](https://github.com/tomayac/js-input-masking/blob/main/README.md)
- slide: [link](https://goo.gle/ecma-402-js-input-masking)

TOM presented (with a JS polyfill) a proposal for formatting input values such as phone numbers. Feedback: [FYT](../../people/FYT.md) said formats that do not vary by region (e.g. ISBN) do not belong in Intl, suggested postcodes and validation, and recalled libphonenumber as a full-time effort; [EAO](../../people/EAO.md) described the side-channel error-reporting problem and advised against formatting while typing; [ZB](../../people/ZB.md) listed parsing, bidi, placeholders and address-formatting scope issues and recommended building a foundational library first; [RCA](../../people/RCA.md) noted scope and customisation concerns; [YSZ](../../people/YSZ.md) asked about `<input type="phonenumber"/>`; [MCM](../../people/MCM.md) asked for use cases that form inputs cannot cover. [SFC](../../people/SFC.md) recommended approaching the Unicode Consortium about a working group to avoid a "15th standard". No formal conclusion is recorded.

## Accept plural forms of unit in Intl.NumberFormat

- proposal: [ecma402#564](https://github.com/tc39/ecma402/issues/564)

[SFC](../../people/SFC.md) laid out three approaches (only singular, plurals for all units, special-casing duration units); [EAO](../../people/EAO.md) pointed out pluralisation is hard for units like "inches" and "kilometers-per-hour". CJR, [RCA](../../people/RCA.md) and [RGN](../../people/RGN.md) came down against accepting plurals. **Conclusion: stay consistent with CLDR, and add a normative reference to CLDR if there isn't already one.**
