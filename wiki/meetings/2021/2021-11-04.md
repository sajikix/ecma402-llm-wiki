## Overview

Co-moderated by [SFC](../../people/SFC.md). TG2 approved two normative PRs (#572, #571) and settled two [NumberFormat v3](../../proposals/intl-numberformat-v3.md) questions (stricter `selectRange` argument checks; `ToIntlMathematicalValue` keeps full precision for strings). In the notes `ZBI` is [ZB](../../people/ZB.md), and `FYI` (in the `textInfo.direction` and `toLocaleString` discussions) is [FYT](../../people/FYT.md).

## Strictness of selectRange #65

- wiki: [Intl.NumberFormat V3](../../proposals/intl-numberformat-v3.md)
- proposal: [proposal-intl-numberformat-v3#65](https://github.com/tc39/proposal-intl-numberformat-v3/issues/65)

[SFC](../../people/SFC.md) asked whether `selectRange` should be strict like `formatRange` or follow the looser behaviour of `select`. [RGN](../../people/RGN.md) and [RCA](../../people/RCA.md) both preferred alignment with `formatRange`. **Conclusion: be strict; the spec gets an extra check that throws a `TypeError` when `start` or `end` is `undefined`.**

## Should ToIntlMathematicalValue accept non-decimal number strings?

- wiki: [Decimal](../../proposals/decimal.md), [Intl.NumberFormat V3](../../proposals/intl-numberformat-v3.md)
- proposal: [proposal-intl-numberformat-v3#54](https://github.com/tc39/proposal-intl-numberformat-v3/issues/54)

[YSZ](../../people/YSZ.md) worried about knock-on effects. [SFC](../../people/SFC.md) argued the proposal intends to keep full precision: accept every grammar already accepted, and only change the resolved value to be a mathematical value instead of being downcast to Number (ICU cannot do arbitrary precision, so implementations would convert). [FYT](../../people/FYT.md) suggested asking ICU to support it; [RGN](../../people/RGN.md) generally agreed with preserving the extra precision of string input. **Conclusion: adopt [SFC](../../people/SFC.md)'s recommendation, pending additional feedback from [RGN](../../people/RGN.md).**

## Intl.Segmenter V2

- wiki: [Intl.Segmenter](../../proposals/intl-segmenter.md)
- proposal: [proposal-intl-segmenter-v2](https://github.com/FrankYFTang/proposal-intl-segmenter-v2)

[FYT](../../people/FYT.md) wants to present at the next TC39 meeting: clients consistently ask for line-break segmentation, and a "batch mode" would cut per-call overhead when splitting a whole string. [MCM](../../people/MCM.md) said the two features should be discussed independently, thought batch mode passes the smell test if benchmarks in a couple of browsers back it up, and doubted line breaking is useful without font metrics, pointing to the Houdini layout work. [FYT](../../people/FYT.md)'s use case is short one-or-two-line labels (e.g. pie-chart titles); [ZB](../../people/ZB.md) asked why font information invalidates the API; [SFC](../../people/SFC.md) listed code-size reduction as the motivation. [SFC](../../people/SFC.md) suggested wrapping it as a Stage 1 proposal. **Conclusion: [FYT](../../people/FYT.md) will present a Stage 1 proposal at the next ECMA-402 meeting.**

## textInfo.direction is a very simplified model of reality

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#59](https://github.com/tc39/proposal-intl-locale-info/issues/59)

Raised after the topic came up at the Unicode Conference: the field returns only `ltr`/`rtl`, while real direction handling is more complicated (vertical scripts, text orientation). [FYT](../../people/FYT.md) explained it is based on Mozilla's existing API and answers "what is the default direction for this language" (including text alignment) when there is no text to detect from, e.g. an empty text box. [CCN](../../people/CCN.md) asked how much of the directionality complexity needs to be covered. [MCM](../../people/MCM.md) questioned the field and proposed removing it: the `dir` attribute with `auto` covers common cases and a localized site already knows its direction. [ZB](../../people/ZB.md) defended it for direction-dependent UI such as iconography and pointed to Gecko and Closure (`goog.i18n.bidi`) prior art. [SFC](../../people/SFC.md) noted the proposal is Stage 3 and this is not the place to make big changes, the likely outcome being to put the discussion on record; the action item was to get ICU's opinion, make sure the API stays extensible, and have [FYT](../../people/FYT.md) tie up loose ends. [ZB](../../people/ZB.md) asked that [MCM](../../people/MCM.md)'s concern not be ignored; [MCM](../../people/MCM.md) said it was not a formal objection. **Conclusion: no change to the proposal; [FYT](../../people/FYT.md) to follow up (ICU input, extensibility).**

## Change Array.prototype.toLocaleString to use ListFormat

- proposal: [ecma402#422](https://github.com/tc39/ecma402/issues/422)

[SFC](../../people/SFC.md) summarised the open questions: web compatibility and how to pass options to the element formatters (a name-spaced options bag, a second options argument, or a single bag with namespaces to avoid collisions). [RGN](../../people/RGN.md) said ECMA-262 `toLocaleString` methods take at most two parameters and a further argument would need agreement from the 262 authors; [FYT](../../people/FYT.md) would rule out changing the signature. The `style` option already means different things in `DateTimeFormat` and `NumberFormat`, which would be ambiguous for heterogeneous arrays. [FYT](../../people/FYT.md) and [RGN](../../people/RGN.md) favoured cutting losses and leaving it, [ZB](../../people/ZB.md) agreed the complexity could explode, and [SFC](../../people/SFC.md) still considered it solvable and wanted it in the backlog. No conclusion recorded; [SFC](../../people/SFC.md) added it to the backlog to revisit later.
