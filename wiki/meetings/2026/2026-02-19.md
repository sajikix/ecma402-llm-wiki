## Overview

Moderated by [SFC](../../people/SFC.md) (co-moderator). TG2 agreed to proceed with the Intl Mathematical Value limits PR (#1022) after addressing [WH](../../people/WH.md)'s feedback, gave approval for [Intl Keep Trailing Zeros](../../proposals/intl-keep-trailing-zeros.md) to go to Stage 3 (pending final reviews by [RGN](../../people/RGN.md), [SFC](../../people/SFC.md) and [YSZ](../../people/YSZ.md)), and approved Intl Era Month Code for Stage 4 (pending open PRs). [EAO](../../people/EAO.md) walked through the reworked [Amount](../../proposals/amount.md) proposal (README PRs to settle before Stage 2), and [SFC](../../people/SFC.md) opened the [Intl Unit Protocol](../../proposals/intl-unit-protocol.md) design questions (conflicting units, object-bag shape). [PFC](../../people/PFC.md) and [SFC](../../people/SFC.md) discussed the Temporal Stage 4 PR (#1044) and how to sequence moves into ECMA-262, and the group debated whether `dateStyle`/`timeStyle` patterns should be reachable via component options (#1043). [RGN](../../people/RGN.md) spoke throughout but is not in the attendee list.

## IntlMV limit

- proposal: [ecma402#1022](https://github.com/tc39/ecma402/pull/1022)

[SFC](../../people/SFC.md) summarised the PR's bounds for Intl mathematical values: TG2 had given conditional approval, deferred to TG1 on the bounds, and TG1 accepted what the PR has. ICU and ICU4X are fine with them; the only hesitation is that the effective limit today is about 400 significant digits, and the new combined bound raises it to 10,000. [DLM](../../people/DLM.md) confirmed implementations could raise the limit later but not lower it, and [SFC](../../people/SFC.md) explained that [WH](../../people/WH.md) thought raising bounds later might not be web-compatible, hence doing it now. **Conclusion: proceed with the PR as written after addressing [WH](../../people/WH.md)'s feedback; come back to TG2 if it changes.**

## Amount update

- wiki: [Amount](../../proposals/amount.md)
- proposal: [proposal-amount#81](https://github.com/tc39/proposal-amount/pull/81)

[EAO](../../people/EAO.md) presented two README PRs. One covers `usage` and unit conversion (`convertTo`, apply the same digit options as `Intl.NumberFormat`), with `convertTo` in ECMA-262 and the locale/`usage` handling defined as a 402 override; [RGN](../../people/RGN.md) supported a narrow normative reference from 262 to CLDR data, and [SFC](../../people/SFC.md) preferred a one-line 262 `toLocaleString`. PR 81 makes `Amount` keep a `Number`, `BigInt` or decimal string and drops the `fractionalDigits`/`significantDigits` accessors, so `toString` yields a value plus `[unit]` that does not parse as a `Number`. [SFC](../../people/SFC.md) found the overall shape covers the needs and agreed to prioritise reviewing these two PRs over keep-trailing-zeros, so spec text can be written for a Stage 2 request; the default precision for `convertTo` was left as a Stage 2 matter.

## Intl Unit Protocol Handling conflicting units #3

- wiki: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md)
- proposal: [proposal-intl-unit-protocol#3](https://github.com/sffc/proposal-intl-unit-protocol/issues/3)

[SFC](../../people/SFC.md) asked what `new Intl.NumberFormat("en", {style: "unit", unit: "meter"}).format(...)` should do when the input carries a different unit such as `"kilometer"`; throwing a `RangeError` was the assumed default, with implicit override, implicit conversion or an explicit option (an `overrideUnit`-style option) as alternatives. [EAO](../../people/EAO.md) argued that if [Amount](../../proposals/amount.md) gets `convertTo`, a unit on the formatter could convert between valid unit pairs, and that [Unit Protocol](../../proposals/intl-unit-protocol.md) might be the place to add `usage`. [SFC](../../people/SFC.md) agreed implicit conversion would be fine then, and that if [Unit Protocol](../../proposals/intl-unit-protocol.md) advances first it should start with `RangeError`; [RGN](../../people/RGN.md) supported this and [JMN](../../people/JMN.md) liked keeping the option open. No formal conclusion was recorded.

## Intl Unit Protocol Interop with Amount #2

- wiki: [Amount](../../proposals/amount.md)
- proposal: [proposal-intl-unit-protocol#2](https://github.com/sffc/proposal-intl-unit-protocol/issues/2)

[SFC](../../people/SFC.md) compared reading two plain fields (`number`/`value` plus `unit`) with an iterator-like protocol of Symbol-keyed functions; plain fields work with object literals, and classes such as [Amount](../../proposals/amount.md) can expose them as getters. [EAO](../../people/EAO.md) agreed, noting the string/unit split in the new [Amount](../../proposals/amount.md) fits. **Draft conclusion: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md) should use the object bag approach.**

## 402 issue 1043

- proposal: [ecma402#1043](https://github.com/tc39/ecma402/issues/1043)

[PFC](../../people/PFC.md) relayed anba's observation that some `dateStyle`/`timeStyle` formats cannot be produced by the format matcher from individual field options, likely an artifact of how CLDR is structured, and floated requiring `DateTimeStyleFormat` to return a format the matchers could return. [EAO](../../people/EAO.md) objected: locales define their own preferred formats, the output should be opaque, and the user benefit is unclear. [SFC](../../people/SFC.md) said the fields are in practice consistent per length and that aligning would make output consistent across `Date` and Temporal inputs and between single dates and ranges, but favoured keeping the issue open and waiting for the CLDR issue (CLDR-1993) before revisiting, without enforcing before implementations do. No decision was made.
