## Overview

Moderated by [SFC](../../people/SFC.md) (co-moderator). A discussion-heavy meeting without normative approvals: [RGN](../../people/RGN.md) merged the well-known intrinsics table cleanup (#1078) after no objections; the group converged on how `Amount`, [Intl Sequence Units](../../proposals/intl-sequence-units.md) and the [Intl Unit Protocol](../../proposals/intl-unit-protocol.md) fit together (array-valued `.value`, no `.values` field, protocol entry by field presence); and the approach to letting engines ship locale data for `Accept-Language` locales was confirmed. [SFC](../../people/SFC.md)'s idea of formatting rationals through new fractional units received questions about motivation and developer experience. Stage 2 proposals without recent updates ([More Currency Display Choices](../../proposals/intl-currency-display-choices.md), Intl [Era Display](../../proposals/intl-eradisplay.md), [Intl Energy Units](../../proposals/intl-energy-units.md)) were reviewed for next steps.

## PR #1078: Update Well-Known Intrinsic Objects table to match 262 — Choice between two approaches for fixing the "Global Name" column.

- proposal: [ecma402#1078](https://github.com/tc39/ecma402/pull/1078)

The ECMA-262 change (#3881) removed the sub-object rows from the well-known intrinsics table; this is the ECMA-402 equivalent, keeping `%Intl%` but not the dotted rows, with intrinsic names formatted as in ECMA-262. [SFC](../../people/SFC.md) had no strong objection (few people rely on the full list). No objections were raised and [RGN](../../people/RGN.md) merged it.

## Amount Issue #118: Amount + Sequence Units — API design for representing multiple combined measures, specifically how this ties in with Intl Unit Protocol and Intl Sequence Units.

- wiki: [Amount](../../proposals/amount.md), [Intl Sequence Units](../../proposals/intl-sequence-units.md)
- proposal: [proposal-amount#118](https://github.com/tc39/proposal-amount/issues/118)

Following an hour-long JS Numerics discussion, `.value` returning a numeric primitive is not a good idea; a polymorphic `.value` that returns an array for sequence units is preferred, e.g. `format({ value: [10, 50], unit: "meter-and-centimeter" })`. [RGN](../../people/RGN.md) found a primitive, uniform representation fine but did not feel strongly; on mixing numeric types in the array, [RGN](../../people/RGN.md) found it distasteful but [EAO](../../people/EAO.md)'s use case (a `bigint` for leading integer units and an exact-decimal string for the last) and [SFC](../../people/SFC.md)'s support persuaded them not to object. All agreed there is no need for a `.values` field, so the [Intl Unit Protocol](../../proposals/intl-unit-protocol.md) should not look for one, and that a multi-element array passed through `Number` yields `NaN`, which is a convenient property.

## Intl Unit Protocol Issue #5: Fallback logic for existing, non-protocol implementing, object parameters — Sniffing criteria for the new interface, requiring both value and the type of measurement.

- wiki: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md)
- proposal: [proposal-intl-unit-protocol#5](https://github.com/tc39/proposal-intl-unit-protocol/issues/5)

Proposal: the protocol is entered when both `.value` and `.unit` are present (not `undefined`) on the object, and once entered there is no fallback to `ToPrimitive`; failures throw instead. [EAO](../../people/EAO.md) and [RGN](../../people/RGN.md) agreed. `Amount` represents an absent unit with `null`/tilde, but unit formatting requires a supported unit, so an unsupported unit error is thrown; serialization of tildes is not an Intl issue.

## Issue #1010: Allow engines to ship data for locales in Accept-Language — Dynamic expansion of supported cultures based on user preferences without increasing fingerprinting risk.

- proposal: [ecma402#1010](https://github.com/tc39/ecma402/issues/1010)

[HJS](../../people/HJS.md) recalled the group was OK with this when it was discussed in October. [SFC](../../people/SFC.md) asked where it should live; [EAO](../../people/EAO.md) believed the spec already allows it, and [SFC](../../people/SFC.md) located the sentence in the implementation-dependencies section that the initial locale set should be the same for all users sharing the same user-agent string, to which "and Accept-Language" would be added. Once that is changed, engines can implement it on their own timeline; [EAO](../../people/EAO.md) noted TG1 approval will also be needed.

## Amount Issue #23: Rationals — Modeling fraction-based measures in the API to support formatting without full arithmetic.

- wiki: [Amount](../../proposals/amount.md)
- proposal: [proposal-amount#23](https://github.com/tc39/proposal-amount/issues/23)

[SFC](../../people/SFC.md) proposed formatting rationals such as ¾ mile or 1 ⅓ cup by defining new fractional units (`quarter-mile`, `third-of-cup`) and combining them with sequence units (`mile-and-quarter-mile`), leveraging existing machinery and requiring no JS API changes or new rational type. [HJS](../../people/HJS.md) asked for evidence of web developer demand (and how bad decimals are; Scandinavian miles are in CLDR but mapping apps show kilometres), and [EAO](../../people/EAO.md) worried the developer experience is poor unless the caller already knows the fraction out of band and suggested a rational option on number formatting instead. [SFC](../../people/SFC.md) answered that `Amount.convertTo` plus `toLocaleString` covers the conversion and that each new unit needs the same payload-motivated justification as the energy units; [LAF](../../people/LAF.md) supported it and raised quarter hours. [EAO](../../people/EAO.md) considered such units to be yet another proposal. Open; no decision.

## Proposal intl era display
