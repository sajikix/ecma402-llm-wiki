## Overview

## PR #1086: Take language subtag into account in locale hour cycle lookup — Scope expansion of the two-tiered lookup algorithm to include CalendarsOfLocale.

- proposal: [ecma402#1086](https://github.com/tc39/ecma402/pull/1086)

The PR makes the hour cycle lookup consider the language subtag (affecting e.g. `en-CA` versus `fr-CA`). [SFC](../../people/SFC.md) wanted #1051 (already approved) to land first since it rewrites the algorithm, then to make the abstract operations self-consistent, and will work on editorial comments with [PFC](../../people/PFC.md); [SFC](../../people/SFC.md) is happy with the normative part. [EAO](../../people/EAO.md), [DLM](../../people/DLM.md) and [YSZ](../../people/YSZ.md) found the change sensible. **Conclusion: TG2 approval.**

## PR #1085: Undo unintentional normative change in CalendarsOfLocale — Consent to merge approved regression fix.

- proposal: [ecma402#1085](https://github.com/tc39/ecma402/pull/1085)

A regression from #1067, which had been handled as an editorial change: `CalendarsInUse` can contain non-canonical IDs, so the fix restores the intended behaviour. [SFC](../../people/SFC.md) approved and, since it landed very recently (not even in ES2026), saw no need for TG1 approval; [EAO](../../people/EAO.md) agreed the editorial change stays editorial.

## Sequence Units Issue #13: Consider adding arcminute and arcsecond — Whether to include these units in this proposal vs. a standalone proposal.

- wiki: [Intl Sequence Units](../../proposals/intl-sequence-units.md)
- proposal: [proposal-intl-sequence-units#13](https://github.com/tc39/proposal-intl-sequence-units/issues/13)

## Sequence Units Issue #11: Handling of zero-valued units in sequences — Architectural layer for zero-omission (NumberFormat option vs. Amount usage patterns).

- wiki: [Amount](../../proposals/amount.md), [Intl Sequence Units](../../proposals/intl-sequence-units.md)
- proposal: [proposal-intl-sequence-units#11](https://github.com/tc39/proposal-intl-sequence-units/issues/11)

`DurationFormat` can toggle zero-valued fields because it has about ten units, which sequence units cannot do. [SFC](../../people/SFC.md) preferred showing zeros and letting callers remove fields from the input (or using an option on `Amount.convertTo`, e.g. with person-height), not overloading `NumberFormat`'s `trailingZeroDisplay`. [EAO](../../people/EAO.md) mildly preferred making `trailingZeroDisplay` work here but said "6ft 0in" strippable while "0ft 6in" is not looks odd; [DLM](../../people/DLM.md) agreed with [SFC](../../people/SFC.md). **Conclusion: (1) default behaviour is to show zero-valued fields; (2) an option to hide them may be considered in the future, but not in this proposal.**

## Sequence Units Issue #9: Should sequence units allow non-integer multiples? — Alignment with CLDR on permitting fractional unit multiples.

- wiki: [Intl Sequence Units](../../proposals/intl-sequence-units.md)
- proposal: [proposal-intl-sequence-units#9](https://github.com/tc39/proposal-intl-sequence-units/issues/9)

CLDR agreed with descending magnitude order but pushed back on the requirement of integer multiples between units, saying combinations like `mile-and-meter` or `kilogram-and-ounce` are not so outlandish. [EAO](../../people/EAO.md) and [DLM](../../people/DLM.md) saw no use case and preferred to be opinionated at first; [SFC](../../people/SFC.md) noted it is fine for the proposal to be stricter than CLDR. **Conclusion: stick with the stricter table approved at Stage 2; it can be revisited in a future proposal.**

## Harmonize formatting option standarization between Unicode, ECMA, and WHATWG #1089

- proposal: [ecma402#1089](https://github.com/tc39/ecma402/issues/1089)

[EAO](../../people/EAO.md) raised the need to coordinate option names and capabilities across ECMA-402, Unicode MessageFormat and HTML (for example the `time` element adopting the MessageFormat datetime options bag, and its timezone style versus `timeZoneName`). [SFC](../../people/SFC.md)'s position is a layering: CLDR at the base, ECMA-402 a subset of it, then HTML and MessageFormat on top, so anything reachable through HTML or MessageFormat should also be reachable from JS, and new option styles should come to TC39 first; [EAO](../../people/EAO.md) countered that MessageFormat does not need permission from TG2 and that "should" is more realistic than "must". They discussed adding semantic skeletons to `Intl.DateTimeFormat` in a surgical way (a new option such as date fields that overrides `dateStyle`), which [SFC](../../people/SFC.md) considered a Stage 2 design concern. **Conclusion: [SFC](../../people/SFC.md) gave [EAO](../../people/EAO.md) TG2 approval to bring a Stage 1 proposal for datetime formatting options (a subset of existing capabilities in a different, semantic-skeleton-style shape); [EAO](../../people/EAO.md) also needs internal support at Mozilla.**
