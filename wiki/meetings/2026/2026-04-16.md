## Overview

Moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md) (co-moderators). No formal conclusions were recorded. Discussion covered Intl Unit Protocol fallback logic (#5, left open until Amount reaches Stage 2), sequence unit formatting (#398, direction leaning towards `NumberFormat` supporting `-and-` units via `ListFormat`), a skeptical reception of `String.toTitleCase`/`titlecaseSegment` (#294, to be raised with the wider web platform first), and triage of new issues from anba, in particular `Intl.Locale.prototype.getTimezones`. [HJS](../../people/HJS.md) reported Firefox 150 shipping ICU4X-based normalisation and collation. [RGN](../../people/RGN.md) joined partway through and is not in the attendee list.

## Updates from the Editors

[USA](../../people/USA.md) said the editors are in a position to cut a new version of the official spec, with Era Monthcode and Temporal not included in the cut.

## Updates from the MessageFormat Working Group

[EAO](../../people/EAO.md) reported it was quiet (last meeting cancelled for lack of agenda), with work continuing in the W3C i18n WG, whose charter covers incubating Message Resources. The main blocker is the ICU4C implementation, which still needs review help. [SFC](../../people/SFC.md) said adoption needs implementations first and a cohesive story for plenary (ICU4C, ICU4X, Angular and React implementations, Message Resources); July or September plenary are possible targets, but presenting too early would not be a good story.

## Updates from Implementers

[HJS](../../people/HJS.md) reported that Firefox 150 (release candidate, shipping the following Tuesday) replaces the normalizer and collator backends with ICU4X. Visible effects are that unpaired surrogates are treated as replacement characters, Hangul in search collation behaves as in sort mode, and Montenegrin now picks the sensible collation (ICU4X did not reproduce a CLDR/ICU4C bug). They also noted one web-compat report from the CLDR change to stop applying locale-specific abbreviations to time zones for dates before the Unix epoch. [SFC](../../people/SFC.md) welcomed the shipping feedback for ICU4X, and [YSZ](../../people/YSZ.md) had no updates.

## Updates from the W3C i18n Group

[EAO](../../people/EAO.md) had nothing beyond the MessageFormat update.

## Intl Unit Protocol: continuation on fallback logic for existing, non-protocol implementing, object parameters

- proposal: [proposal-intl-unit-protocol#5](https://github.com/sffc/proposal-intl-unit-protocol/issues/5)

Continuing from March: [SFC](../../people/SFC.md) recalled the open question of how to detect a protocol object (presence of the fields, via `in` or via `Get` checking `null`); [EAO](../../people/EAO.md) recalled agreeing to check only for presence of `value` and `unit`, possibly with a new abstract operation that also returns the value so the prototype chain is walked once. [RGN](../../people/RGN.md), after joining, agreed that a new operation distinguishing absent from `undefined` only helps if `undefined` is an accepted unit, and that representing "no unit" with `null` would be better (also for `Amount.prototype.toString` serialization, as [EAO](../../people/EAO.md) noted). The decision on `{ value: 123, unit: undefined }` versus `unit: null` was left to be settled with Amount; [SFC](../../people/SFC.md) will document the discussion and keep the issue open until Amount is at Stage 2, and [JMN](../../people/JMN.md) will file an Amount issue.

## Sequence Units follow-up

- proposal: [ecma402#398](https://github.com/tc39/ecma402/issues/398)

[SFC](../../people/SFC.md) observed that LDML defines sequence-unit formatting in terms of `ListFormat`, so it can already be composed by hand (a `NumberFormat` per component glued with `ListFormat`); big-endian order is used by all locales and balancing/overflow normalisation should be left to `convertTo` (as with `Temporal.Duration` versus `DurationFormat`), keeping custom units possible. Whether to add sugar was debated: [EAO](../../people/EAO.md) wanted `-and-` to work in `NumberFormat` for least surprise; [RGN](../../people/RGN.md) was fine with `NumberFormat` accepting mixed-unit Amounts via `ListFormat`, or with an `AmountFormat`, but not with `Amount.prototype.toLocaleString` alone being defined outside Intl formatters ([EAO](../../people/EAO.md) and [JMN](../../people/JMN.md) +1). [SFC](../../people/SFC.md) worried about drifting from the constructor-for-efficiency model but said that if it is in Intl, `NumberFormat` is the only place. Side discussions covered `-per-` with currencies and case-sensitivity of currency codes versus units like `cup`/`CUP`. No formal conclusion; the proposal will return to TG2 for Stage 2 with this scope.

## String.toTitleCase, String.toLocaleTitleCase, with a focus on recent comments about titlecaseSegment

- proposal: [ecma402#294](https://github.com/tc39/ecma402/issues/294)

[SFC](../../people/SFC.md) described ICU4X's `TitlecaseMapper`/`titlecase_segment`, which titlecases only the start of a segment and leaves the rest to `Intl.Segmenter`, presented as a building block. [RGN](../../people/RGN.md), [CDA](../../people/CDA.md) and [EAO](../../people/EAO.md) raised concerns about prefixes such as French d' and Dutch IJ, naming ([RGN](../../people/RGN.md) advised avoiding "titlecase"), and stopwords not being codified; [DLM](../../people/DLM.md) and [HJS](../../people/HJS.md) argued this belongs in CSS first (`text-transform: capitalize`) and found the name confusing, while [SFC](../../people/SFC.md) and [CDA](../../people/CDA.md) said CSS cannot cover complex cases and the two paths are not mutually exclusive. [EAO](../../people/EAO.md) suggested a `String.prototype.capitalize` matching CSS as an alternative. **No conclusion; [SFC](../../people/SFC.md)'s summary was that a `titlecase-segment` equivalent may be a good approach but that TG2 should first engage with the rest of the web platform.**

## Triage some new issues filed by Anba

- proposal: [ecma402 issues](https://github.com/tc39/ecma402/issues)

[SFC](../../people/SFC.md) had already put uncontroversial bugs in the milestone (to be renamed 2027) for [BAN](../../people/BAN.md) to pull. The one discussed was `new Intl.Locale("en-US").getTimezones()` (spec 15.5.13), which returns many time zones, including obsolete and merged ones, while `"fr-FR"` returns one and omits overseas territories; which time zones belong to a region is implementation-defined. [RGN](../../people/RGN.md) said the API implies a specialised, opinionated list (e.g. for a time zone picker) and that the `en-US` result is too big; [EAO](../../people/EAO.md) suggested CLDR as the authority for locale-specific results (e.g. `en-CA` vs `fr-CA`), and [HJS](../../people/HJS.md) questioned use cases for `world` or continent regions. No decision; [SFC](../../people/SFC.md) will record the notes on the issue and asked delegates to review the other issues and anba's PR.
