## Overview

Moderated by [SFC](../../people/SFC.md) (co-moderator). The main topic was the IANA time zone IDs such as `EST5EDT`, which were un-deprecated and are now primary zones in tzdb; [JGT](../../people/JGT.md) agreed to write an ECMA-402 PR that bans these IDs as canonical identifiers while leaving aliasing up to implementations. TG2 also settled three [Intl Unit Protocol](../../proposals/intl-unit-protocol.md) design questions (keep `value` coercion as is, read the protocol only for `unit`/`currency` styles, highlight validation timing for Stage 2.7 review), postponed a Sequence Units issue, and decided that [SFC](../../people/SFC.md) will propose a TPAC breakout on title-casing. Robert Bastian (Google, listed in the attendees without an abbreviation) spoke during the time zone discussion; the notes give no delegates.txt abbreviation, so the name is kept as written. [PFC](../../people/PFC.md) and [LAF](../../people/LAF.md) are listed as attendees but do not speak in the notes.

## Time Zone Issue

- proposal: [ecma402#1103](https://github.com/tc39/ecma402/issues/1103)

[JGT](../../people/JGT.md) presented the fallout of tzdb un-deprecating zones such as `EST5EDT`, which makes them primary zones that would now be enumerated by `Intl.supportedValuesOf` and appear in time zone pickers. The options were to treat it as an edge case, revert the change (tzdb and CLDR are unlikely to), or change how enumeration works. [HJS](../../people/HJS.md) noted that Safari rejects these IDs while Firefox and Chrome treat them as aliases of city-based IDs, which suggests the web may not need them; [JGT](../../people/JGT.md) preferred keeping them as aliases because ECMAScript also runs outside browsers and the spec currently accepts every tzdb ID. Robert Bastian said CLDR follows tzdb for stability and advised against aliasing them to specific cities, since US and Canadian jurisdictions may diverge once DST ends; reading the system time zone and accepting input to `DateTimeFormat` can be handled separately. [SFC](../../people/SFC.md) preferred to explore a longer-term enumeration option (for example a "comprehensive" versus "recommended" set) and to let Safari remain compliant. [EAO](../../people/EAO.md) proposed banning these IDs as canonical identifiers, which keeps the status quo in all three major browsers while keeping them out of enumeration, and asked about the SystemV-prefixed IDs, which Node.js enumerates ([JGT](../../people/JGT.md) found they are not in Node.js 26.x). [SFC](../../people/SFC.md) agreed, noting the spec can be written without reifying non-compliant behaviour, and that process need not block Chrome and Firefox from staying aligned in the meantime. **Conclusion: no formal conclusion recorded; [JGT](../../people/JGT.md) will make a PR banning these IDs as canonical identifiers (leaving alias handling to implementations), to go through TG1.**

## Amount Issue #139: Duration / time units in Amount — Use Intl.DurationFormat?

- wiki: [Amount](../../proposals/amount.md)
- proposal: [proposal-amount#139](https://github.com/tc39/proposal-amount/issues/139)

[Intl Sequence Units](../../proposals/intl-sequence-units.md) does not support time units, which leaves open whether `Amount` should format them through `Intl.DurationFormat`. [EAO](../../people/EAO.md) argued that unlocalizable time units would be very odd and accepted a polymorphic options bag as the least bad cost; [SFC](../../people/SFC.md) disliked an options bag with two shapes, and said `DurationFormat` was deliberately made distinct from `NumberFormat` and that `Amount` already formats only a small subset of units, so throwing for time sequence units is tolerable. [RGN](../../people/RGN.md) sided with [EAO](../../people/EAO.md), noting only the three of them have opinions. [SFC](../../people/SFC.md) floated `Amount.prototype.toDuration` (throwing for non-duration units); [EAO](../../people/EAO.md) suggested `Temporal.Duration.from` accepting an `Amount`. **Conclusion: [SFC](../../people/SFC.md) to file an issue about conversion from [Amount](../../proposals/amount.md) to Temporal.Duration.**

## Unit Protocol Issue #6: Should we coerce the value field?

- wiki: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md)
- proposal: [proposal-intl-unit-protocol#6](https://github.com/tc39/proposal-intl-unit-protocol/issues/6)

[SFC](../../people/SFC.md) questioned whether `ToIntlMathematicalValue` coercion (including `Symbol.toPrimitive`) should apply to the protocol's `value` field. [RGN](../../people/RGN.md) and [EAO](../../people/EAO.md) argued the only real coercion is `ToPrimitive` and the rest is bookkeeping, so user code runs once at consumption; [EAO](../../people/EAO.md) had a weak preference for not coercing. [SFC](../../people/SFC.md) ended up saying the long-standing support for custom numeric types in `NumberFormat` is sufficient precedent for the [unit protocol](../../proposals/intl-unit-protocol.md) too. No conclusion is recorded; [SFC](../../people/SFC.md) intends to keep the current behaviour.

## Unit Protocol Issue #7: Should we check for the protocol even if the formatter is not a unit/currency formatter?

- wiki: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md)
- proposal: [proposal-intl-unit-protocol#7](https://github.com/tc39/proposal-intl-unit-protocol/issues/7)

Currently `NumberFormat.prototype.format` always reads the protocol fields. [EAO](../../people/EAO.md) clarified that the protocol should only be checked when the style is `unit` or `currency` ([SFC](../../people/SFC.md) had misread an earlier comment), and [RGN](../../people/RGN.md) was comfortable with "option 4". This is a normative change to the proposal. **Conclusion: go with option 4; [SFC](../../people/SFC.md) to submit the normative change to the next TG1.**

## Issue #816 - Cyclic year doesn't show up in resolvedOptions

- proposal: [ecma402#816](https://github.com/tc39/ecma402/issues/816)

MP asked what should change in the spec, since the earlier agreement was to take Anba's fix while Anba's comment says the spec is right and implementations are wrong. [SFC](../../people/SFC.md) confirmed the spec is still correct: `resolvedOptions` reads `year` from the format pattern, which has a `relatedYear` field as seen in `formatToParts`. **Conclusion: needs a test262 test validating how Table 15 is used by `Intl.DateTimeFormat.prototype.resolvedOptions()`; engines are not compliant.**
