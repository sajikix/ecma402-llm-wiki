## Overview

A pre-plenary meeting (the May plenary in Amsterdam, 2026-05-19, was two weeks away). The bulk of the time went to Stable Formatting: TG2 discussed four PRs against the proposal and [EAO](../../people/EAO.md) received TG2 support to ask TG1 for Stage 2, with a spin-off `und` behaviour proposal for `Collator`, `Segmenter` and `String.prototype.toLocale{Lower,Upper}Case` to be presented separately at Stage 1. [SFC](../../people/SFC.md) walked through the Intl Sequence Units open issues and, with two caveats (strict rounding, an explicit list of combinable unit categories), had support from [EAO](../../people/EAO.md), [RGN](../../people/RGN.md) and [YSZ](../../people/YSZ.md) for Stage 2. Anba's two normative PRs were deferred to the next TG2. The group also discussed the W3C i18n/CSS liaison questions.

## Stable Formatting for Stage 2?

- proposal: [proposal-stable-formatting](https://github.com/tc39/proposal-stable-formatting)

[EAO](../../people/EAO.md) wants to advance Stable Formatting to Stage 2 (TG1-like behaviour for TG2 interfaces, hence discussed in TG2 first, then at the plenary in Amsterdam). Spec-text work led to four PRs, discussed below. After the discussion [EAO](../../people/EAO.md) asked for TG2 consensus to seek Stage 2; [RGN](../../people/RGN.md) gave "enthusiastic approval" and [SFC](../../people/SFC.md) agreed that defining `zxx` as deterministically stable behaviour ([RGN](../../people/RGN.md)'s version) is a good definition, but was not ready for a special meaning of `und`.

### Use Intl.STABLE instead of null

- proposal: [proposal-stable-formatting#21](https://github.com/tc39/proposal-stable-formatting/pull/21)

Instead of `null` as a locale identifier (which would make `null` and `undefined` behave differently), the PR uses `zxx` ("no localizable content") as the identifier, exposed as a constant `Intl.STABLE`. [SFC](../../people/SFC.md) asked about a symbol instead, since CLDR has not given permission for `zxx` with that meaning; [HJS](../../people/HJS.md) preferred a value inside BCP 47 space so it can flow through to ICU4X. [EAO](../../people/EAO.md) would keep `Intl.STABLE` so the identifier can be changed later. [SFC](../../people/SFC.md) asked that CLDR/Mark Davis be consulted before the plenary; [EAO](../../people/EAO.md) will file a Jira issue.

### Define behaviour for Intl.Locale

- proposal: [proposal-stable-formatting#22](https://github.com/tc39/proposal-stable-formatting/pull/22)

The spec text has fallbacks for nearly everything; the one intended divergence is that the default calendar for `zxx` should be `iso8601` rather than `gregory`. [PFC](../../people/PFC.md) and [SFC](../../people/SFC.md) raised the machine-versus-human calendar distinction (`iso8601` is not intended for formatting; a test using `zxx` and runtime using `en` might yield different semantics), while [HJS](../../people/HJS.md) and [EAO](../../people/EAO.md) argued the constraint is weak and pointed to existing `iso8601` requirements in `Intl.supportedValuesOf`/`AvailableCalendars`. [PFC](../../people/PFC.md) noted `ToLocalTime` should probably not refer to `gregory` either (a separate question). For Stage 2, [RGN](../../people/RGN.md) was strongly in favour of `iso8601`; [SFC](../../people/SFC.md) said it needs more thought but is not a Stage 2 concern.

### Use easier-to-specify stable behaviour for DurationFormat

- proposal: [proposal-stable-formatting#23](https://github.com/tc39/proposal-stable-formatting/pull/23)

[EAO](../../people/EAO.md) proposed defining stable `DurationFormat` output via existing `NumberFormat` unit formatting plus `ListFormat` (digital durations with colons, unit identifiers regardless of width) rather than emitting ISO 8601 "P" strings, since `DurationFormat` is already specified in terms of those two. [PFC](../../people/PFC.md) noted P-strings already exist via `Temporal.Duration.prototype.toString`; [RGN](../../people/RGN.md) initially preferred P-strings but was swayed once it was clear `DurationFormat` inherently returns list-format output; [DLM](../../people/DLM.md) and [SFC](../../people/SFC.md) leaned toward [EAO](../../people/EAO.md)'s approach. For `RelativeTimeFormat`, [EAO](../../people/EAO.md) used P-like output without the `P` for quarters (ISO 8601 has no duration of N quarters, [PFC](../../people/PFC.md) checked); [SFC](../../people/SFC.md) suggested signed unit format instead ("-1 day"/"+1 day") and [EAO](../../people/EAO.md) invited an issue.

### Define und behaviour for Collator, Segmenter & String.p.toLocale{Lower,Upper}Case

- proposal: [proposal-stable-formatting#24](https://github.com/tc39/proposal-stable-formatting/pull/24)

PR 24 gives APIs that also consume localized content access to the root locale via `und`, behaviour that is locale-independent but not fully stable. [SFC](../../people/SFC.md) and [RGN](../../people/RGN.md) worried that this stretches "stable" (e.g. changes across Unicode versions); [HJS](../../people/HJS.md) wanted a well-defined way to reach root collation but rejected a frozen/never-changing `Collator` (codepoint order is better done outside `Collator`) and did not find [RGN](../../people/RGN.md)'s blockchain determinism use case compelling. [RGN](../../people/RGN.md) distinguished `und` (locale-relevant but locale-independent) from `zxx` (deterministic for all time). [EAO](../../people/EAO.md) proposed keeping `zxx` as-is, asking TG1 whether `und` should be a separate proposal, and opening an issue about `Collator` with `zxx`. [SFC](../../people/SFC.md) and [RGN](../../people/RGN.md) approved presenting the `und` behaviour as a separate Stage 1 proposal.

## Intl Sequence Units for Stage 2?

- proposal: [proposal-intl-sequence-units](https://github.com/tc39/proposal-intl-sequence-units)

[SFC](../../people/SFC.md) presented the now-proper proposal (no unit compatibility check, so `foot-and-pound` is accepted) and went through open issues. [EAO](../../people/EAO.md) noted `arcminute` and `arcsecond` are not supported in ECMA-402 today; [SFC](../../people/SFC.md) said those could be future direction. Outcomes per issue:

- [#1](https://github.com/tc39/proposal-intl-sequence-units/issues/1) (scalar vs structure): structured input preferred ([RGN](../../people/RGN.md), [JMN](../../people/JMN.md), [DLM](../../people/DLM.md)), independent of unit conversion.
- [#2](https://github.com/tc39/proposal-intl-sequence-units/issues/2) (missing unit): throw `TypeError` ([RGN](../../people/RGN.md), [EAO](../../people/EAO.md) and another delegate agreed).
- [#4](https://github.com/tc39/proposal-intl-sequence-units/issues/4) (extraneous units): only format units named in the identifier, ignore others ([RGN](../../people/RGN.md) agreed).
- [#5](https://github.com/tc39/proposal-intl-sequence-units/issues/5) (out-of-range, e.g. 5 feet 20 inches): no semantic meaning attached ([JMN](../../people/JMN.md), [RGN](../../people/RGN.md), [EAO](../../people/EAO.md)).
- [#6](https://github.com/tc39/proposal-intl-sequence-units/issues/6) (negatives): same sign is fine, mixed signs throw `RangeError`, minus sign on the first unit ([RGN](../../people/RGN.md), [YSZ](../../people/YSZ.md)).
- [#3](https://github.com/tc39/proposal-intl-sequence-units/issues/3) (rounding of more-significant units): throw when a non-smallest unit is non-integer, consistent with `Temporal.Duration`/`DurationFormat` ([RGN](../../people/RGN.md), [EAO](../../people/EAO.md); [SFC](../../people/SFC.md) accepted despite disliking situational errors).
- [#7](https://github.com/tc39/proposal-intl-sequence-units/issues/7) (`inch-and-foot` vs `foot-and-inch`): after a debate ([RGN](../../people/RGN.md): order is a localization matter, so restrict; [EAO](../../people/EAO.md): YAGNI, validate by unit category), [SFC](../../people/SFC.md) will specify the categories of units that can be combined and the magnitude order in the spec.

**Conclusion: with the two changes (strict rounding; explicit list of combinable unit categories and magnitude order), [SFC](../../people/SFC.md) asked for Stage 2 support and [EAO](../../people/EAO.md), [RGN](../../people/RGN.md) and [YSZ](../../people/YSZ.md) said they support it.**
