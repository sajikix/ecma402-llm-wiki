## Overview

Moderated by [SFC](../../people/SFC.md). About half the meeting was a long exploratory discussion of user preferences (calendar info, `Accept-Language`, Unicode extension keys, a possible `userPreferences` API or client hint) that ended without a decision. TG2 also closed the per-category default locale issue (#257), agreed to mark Annex A as fingerprintable (#110), accepted Anba's proposed behaviour for canonicalising Unicode extension options (proposal-intl-locale#96), and heard [LEO](../../people/LEO.md) announce that the editor role might soon be open. MGR and MIH speak but are not in the attendee list; `ZBI` is [ZB](../../people/ZB.md), `FYI` (once) is [FYT](../../people/FYT.md), and the speaker `MGM` in the default-locale discussion could not be mapped and is left out.

## User Preferences

- proposal: [ecma402#6](https://github.com/tc39/ecma402/issues/6)

[SFC](../../people/SFC.md) framed the theme as user preferences beyond `firstDayOfWeek`, starting from issue #6 on `Intl.getCalendarInfo()`. [ZB](../../people/ZB.md) pointed to Firefox's internal `mozIntl` services, used for three years, and described the design as a man-in-the-middle that can override CLDR defaults with OS preferences. [JSW](../../people/JSW.md) found reading such info via a constructed locale and `resolvedOptions` convoluted, preferring a `getCalendarInfo`-style function or getters on `Intl.Locale`. Two directions emerged: encode preferences as Unicode extension keys in locale strings (consistent between server and client) or expose a separate preferences object (`Intl.userPreferences`). Concerns: [JSW](../../people/JSW.md) said enlarging `Accept-Language` is a hard sell; [MCM](../../people/MCM.md) stressed fingerprinting and that browsers must be able to mask the data; [ZB](../../people/ZB.md) opposed exposing anything that looks like a pattern; [FYT](../../people/FYT.md) noted that not everything fits a Unicode extension. [SFC](../../people/SFC.md) suggested a new `Accept-Locales` header or `navigator.locales`; [MCM](../../people/MCM.md) said it should be a "client hint". Open follow-ups: contact the client hints champions, W3C i18n (MGR suggested Richard Ishida) and IETF. No conclusion was recorded; [ZB](../../people/ZB.md) confirmed "this is not simple".

## Allow for different default locale per category #257

- proposal: [ecma402#257](https://github.com/tc39/ecma402/issues/257)

[ZB](../../people/ZB.md) asked whether the default locale could differ by context (for example datetime vs. other formatting); MIH said Android allows different regions within the same language and script. Opinions: MGR saw cases where users keep English but want other formats; [LEO](../../people/LEO.md) wanted consistency across implementations; MIH thought a fully separate locale is too far and "knobs" are better; [FYT](../../people/FYT.md) raised POSIX `LC_*` as precedent, which MIH dismissed. [ZB](../../people/ZB.md) noted the most popular knobs are hour cycle, first day of week and date/time style, and that it is better to talk about a chain of locales. [JSW](../../people/JSW.md) checked that the default locale in `[[AvailableLocales]]` cannot include Unicode extensions. **Conclusion: Close the issue.**

## Consider marking DefaultLocale as a fingerprinting vector #110

- proposal: [ecma402#110](https://github.com/tc39/ecma402/issues/110)

MGR and [MCM](../../people/MCM.md) wanted fingerprinting called out so readers know the tradeoffs, not marked everywhere; [FYT](../../people/FYT.md) asked why not say everything is fingerprintable; [CLA](../../people/CLA.md) questioned the audience and whether flagging helps attackers. [ZB](../../people/ZB.md) argued that the only real fingerprintable bit is the default locale, so marking it in one place could suffice. [LEO](../../people/LEO.md), as editor, agreed with Allen Wirfs-Brock's view that this belongs in a generic Annex A treatment or in HTML. [SFC](../../people/SFC.md) noted Annex A already defines fingerprintable items. **Conclusion: Mark Annex A as fingerprintable.**
