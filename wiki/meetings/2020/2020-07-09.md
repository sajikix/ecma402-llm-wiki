## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). A broad triage meeting: the group discussed `formatRange` edge cases ahead of its planned Stage 4 request in September, the ECMA-402 "Conformance" section, two `Intl.DisplayNames` design questions (a mandatory `type`, and whether to canonicalise region and script codes), and the inconsistency that `era` and `timeZoneName` cannot be formatted alone. [RGN](../../people/RGN.md)'s plan for taking `Intl.Segmenter` to Stage 3 was reviewed. Four normative PRs were walked through (#459 and #471 to go to TC39; #347 and #346 deferred). The meeting closed with the first discussion of sequence unit formatting (ecma402#398), whether unit arithmetic is in scope for ECMA-402. [RCA](../../people/RCA.md) (MessageFormat WG liaison) did not attend.

## PartitionDateTimeRangePattern may need additional date-time fields not present in the formatter #21

- proposal: [proposal-intl-DateTimeFormat-formatRange#21](https://github.com/tc39/proposal-intl-DateTimeFormat-formatRange/issues/21)

`formatRange` can emit fields (e.g. a date when a time range crosses midnight) that the `DateTimeFormat` was not constructed with, so `resolvedOptions()` does not describe them. [EAO](../../people/EAO.md) expected that feeding `resolvedOptions()` into a new formatter would reproduce the output; [FYT](../../people/FYT.md) argued `resolvedOptions()` describes the object, not a result that depends on the range passed in; [SFC](../../people/SFC.md) suggested the `dateStyle`/`timeStyle` model (not everything is in `resolvedOptions()` as long as it round-trips). Options floated: throw if the range is too large (an `anba` suggestion that needs no ICU change), or always add larger fields when needed to differentiate the two ends. FBN noted the plan to ask for Stage 4 in September; [SFC](../../people/SFC.md) wants Stage 4 without redoing ICU and CLDR. No conclusion; [FYT](../../people/FYT.md) asked whether the odd minutes behaviour is a Chrome or ICU bug.

## Update "Conformance" section for new options/constructors #467

- proposal: [ecma402#467](https://github.com/tc39/ecma402/issues/467)

[SFC](../../people/SFC.md) explained that the Conformance section allows extra locale matchers, usages and styles, but newer options such as units use an exclusive list, and no browser is known to implement extras. [MCM](../../people/MCM.md) saw two paths: remove the section, or make the optional behaviour well-defined. [ZB](../../people/ZB.md) recalled that the list existed to allow deviation in order to use the Windows internationalization APIs. Agreed path: check whether deleting the list contradicts web reality ([LEO](../../people/LEO.md) to reach out to Caridy), otherwise delete the list while keeping the rest of the section.

## Should "type" be changed to a mandatory option instead of defaulting it to "language"? #73

- proposal: [proposal-intl-displaynames#73](https://github.com/tc39/proposal-intl-displaynames/issues/73)

[FYT](../../people/FYT.md) asked whether a mandatory `type` is acceptable given that options bags are normally optional. [RKG](../../people/RKG.md) noted there is no precedent for requiring a non-empty options bag; [SFC](../../people/SFC.md) preferred making it explicit, and [JSW](../../people/JSW.md) said `Intl.DisplayNames` is a different kind of class from the other Intl objects. [ZB](../../people/ZB.md) and [EAO](../../people/EAO.md) supported. **Conclusion: overwhelming support to make the options bag and `type` required (explicit), including Yusuke's suggestion that the parameters be required rather than optional.**

## Should we map the code if the type is region ? #81

- proposal: [proposal-intl-displaynames#81](https://github.com/tc39/proposal-intl-displaynames/issues/81)

`anba` suggested canonicalising region codes by alias, not just by case. [FYT](../../people/FYT.md) said there is no standalone algorithm in UTS 35 (deprecated `SU` maps to some 13 regions depending on the language; [JSW](../../people/JSW.md) cited `ab-SU` and `ru-SU`). [ZB](../../people/ZB.md) proposed not mapping at all and returning the code itself when no display name exists, as for any well-formed code, which [SFC](../../people/SFC.md) accepted; [FYT](../../people/FYT.md) preferred case-correcting only. [JSW](../../people/JSW.md) was a little wary. Next step: [JSW](../../people/JSW.md), [FYT](../../people/FYT.md) and `anba` to sync offline; [SFC](../../people/SFC.md) agreed with [ZB](../../people/ZB.md) that canonicalising a region in `DisplayNames` differs from canonicalising one in a locale.

## Cannot output only era or timeZoneName #461

- proposal: [ecma402#461](https://github.com/tc39/ecma402/issues/461)

[FYT](../../people/FYT.md): `{era: 'long'}` or `{timeZoneName: 'long'}` cannot be formatted alone, unlike every other field. [PFC](../../people/PFC.md) noted this came up as Temporal feedback. [USA](../../people/USA.md) favoured adding it for consistency since it breaks nothing; [EAO](../../people/EAO.md) first agreed and then withdrew support; [SFC](../../people/SFC.md) and [JSW](../../people/JSW.md) thought single-field era and time zone name belong in `Intl.DisplayNames`, though [SFC](../../people/SFC.md) would not oppose a PR. [SFC](../../people/SFC.md) to add the issue to the 2021 milestone.

## Old-style language tags is too vague

- proposal: [ecma402#159](https://github.com/tc39/ecma402/issues/159)

The question is whether supporting `zh-Hant-TW` implies supporting `zh-TW`. [SFC](../../people/SFC.md) thinks yes (supporting `ll-Ssss-RR` implies `ll-RR`) and is fine leaving the spec as-is. [RKG](../../people/RKG.md) said SpiderMonkey and JSC carry unexplained mapping lists that should shrink, and V8 already has a corresponding step, so spec text would reflect web reality. [SFC](../../people/SFC.md) labelled it "help wanted".

## Intl.Segmenter for Stage 3

- proposal: [proposal-intl-segmenter](https://github.com/tc39/proposal-intl-segmenter)

[RGN](../../people/RGN.md) planned to put Stage 3 on the TC39 agenda that day, with two blockers to resolve first (proposal-intl-segmenter#96 and #116). To address SES-style concerns about exposing non-primitive slot values from a getter, the segments object will link back neither to the segmenter nor to the input string; the string is still reachable via iteration results. [SFC](../../people/SFC.md) agreed with punting (the segmenter or string can be added later), and [FYT](../../people/FYT.md) said the plan is much better.

## Sequence unit formatting #398

- proposal: [ecma402#398](https://github.com/tc39/ecma402/issues/398)

[SFC](../../people/SFC.md) asked whether the arithmetic involved in sequence units (e.g. "10 meters and 35 centimeters") is in scope for ECMA-402. [ZB](../../people/ZB.md) accepted that 12 months per year is i18n data but doubted that 100 centimeters per meter is, and was unsure how much of unit conversion belongs in 402. [FYT](../../people/FYT.md) considered the 7 days per week in ECMA-262; [SFC](../../people/SFC.md) countered that Gregorian is defined there but other calendars are implementation-dependent. [SFC](../../people/SFC.md) regards it as a high-demand use case with data available, subject to a separation-of-concerns worry. No conclusion; feedback on the issue and discussion next month.
