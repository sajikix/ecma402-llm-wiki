## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). TG2 recorded consensus on `@@toStringTag` for the `Intl` namespace object (#487) and gave Stage 1 consensus to two new proposals: [Intl Locale Info](../../proposals/intl-locale-info.md) API ([FYT](../../people/FYT.md) champion; [ZB](../../people/ZB.md) declined to co-champion) and `Intl.DisplayNames` V2. `Intl.Enumeration` drew privacy and fingerprinting concerns from [ZB](../../people/ZB.md), and the group agreed a privacy expert should be involved. Also discussed: repository permissions, an Airtable alternative to the status wiki, `formatRange` on its way to Stage 4, the Conformance section (#467), and making GetOption's options handling stricter (#480).

## Intl Enumeration API

- proposal: [proposal-intl-enumeration](https://github.com/tc39/proposal-intl-enumeration)

[FYT](../../people/FYT.md) reported Stage 1 in July, added time zone options and was working on region options, and asked for questions before Stage 2. [ZB](../../people/ZB.md) has deep reservations about fingerprinting and overlap with HTML pickers (HTML could handle privacy better); [FYT](../../people/FYT.md) countered that the available set depends on the browser or OS version and is not user-changeable like fonts; [USA](../../people/USA.md) noted non-picker use cases and that results track the user agent. [ZB](../../people/ZB.md) worried about precedent and about asynchronous loading of extra data, and wants a design so a V2 need not be incompatible. [SFC](../../people/SFC.md) pointed to the repo's privacy issue (#3) and concluded the high bit is getting a privacy expert involved; [EAO](../../people/EAO.md) asked whether results would vary between browsers, and [SFC](../../people/SFC.md) answered that the source is CLDR data (tied to the OS version in Safari, the browser version in Chrome and Firefox). [RCA](../../people/RCA.md) asked what `getSupported` adds if the lists are fixed per version. No conclusion.

## Intl Locale Info API

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info](https://github.com/tc39/proposal-intl-locale-info)

[FYT](../../people/FYT.md) presented (based on ecma402 issues #6 and #205) three areas: week data (first day, weekend, minimal days in the first week), language direction ("is it bi-di", since no language, not even Arabic, is strictly right-to-left) and measurement system, exposed either as `Intl.Locale` getters or as a function on `Intl`. [JSW](../../people/JSW.md) and [ZB](../../people/ZB.md) supported. [SFC](../../people/SFC.md) liked the idea but pointed to #409 ([DE](../../people/DE.md)'s `preferredCalendar`-style getters) and the need for locale-extension keywords to take precedence over locale data, aligned with the user-preferences vision; [FYT](../../people/FYT.md) and [SFC](../../people/SFC.md) agreed this can be answered during Stage 1. [ZB](../../people/ZB.md) could help with specific requests but declined to commit to co-championing. [JSW](../../people/JSW.md), [EAO](../../people/EAO.md) and [USA](../../people/USA.md) gave +1. **Conclusion: consensus for Stage 1.**

## Intl.DisplayNames V2

- proposal: [intl-displaynames-v2](https://github.com/FrankYFTang/intl-displaynames-v2/)

With `Intl.DisplayNames` at Stage 3, [FYT](../../people/FYT.md) proposed enhancements: weekday and month names (dropped from V1 due to leap-month calendars and [Temporal](../../proposals/temporal.md)), unit names, time zone names, numbering system and calendar names, and dialect support. Discussion: [JSW](../../people/JSW.md) asked about the time zone use case (pickers); [SFC](../../people/SFC.md) argued localised metazone names ("India Standard Time" in Hindi) are useful; [ZB](../../people/ZB.md) said weekday and month names are the most requested; [SFC](../../people/SFC.md) suggested using [Temporal](../../proposals/temporal.md)'s year-month type to avoid leap-month problems and calling the weekday data "modern weekdays"; [JSW](../../people/JSW.md) also wanted quarter, day period and datetime field; [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md) cautioned that day period is culturally tricky and CLDR has two definitions. [SFC](../../people/SFC.md) noted `DateTimeFormat` with a single field works but forces the developer to construct a `Date`. Volunteers for use cases: [YMD](../../people/YMD.md) (calendars), [RCA](../../people/RCA.md) (week and month names), [SFC](../../people/SFC.md) (unit names, for Apple; compound units only if explicit in CLDR). [SFC](../../people/SFC.md) had Stage 2 concerns about weekday, month and day period but was fine with Stage 1. **Conclusion: consensus for Stage 1.**

## Require options to be an object #480

- proposal: [ecma402#480](https://github.com/tc39/ecma402/issues/480)

[PFC](../../people/PFC.md): [Temporal](../../proposals/temporal.md) plans options bags like ECMA-402's, so the GetOption abstract operation should move to ECMA-262, and the current 402 version, which boxes primitives with `ToObject`, makes little sense. The PR has an editorial commit and a normative one (throw `TypeError` instead of boxing). [JSW](../../people/JSW.md) saw risk only in accidental callers relying on defaults. [SFC](../../people/SFC.md) suggested keeping the old behaviour as a legacy operation, or moving the type check into a single "NormalizeOptions" step called once at the top; [RGN](../../people/RGN.md) said the type check is not observable but [FYT](../../people/FYT.md) thought repeated calls would be. Continued on the issue tracker.
