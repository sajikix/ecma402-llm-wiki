## Overview

Moderated by [SFC](../../people/SFC.md). [PFC](../../people/PFC.md) pitched [Temporal](../../proposals/temporal.md) to the group, and the discussion centred on which calendar wins when a [Temporal](../../proposals/temporal.md) object is formatted with `toLocaleString`. Most of the meeting went to `Intl.NumberFormat` v3 design questions (range formatting settings, grouping strategies, where `scale` belongs) and to how to make `PluralRules` easier to use correctly; none of these produced a formal conclusion in the notes, but [SFC](../../people/SFC.md) pulled the `scale` option from the proposal for now. The notes write "US" for [USA](../../people/USA.md) once (US: "What about RefISOYear?"), normalised to [USA](../../people/USA.md) per delegates.txt. [RGN](../../people/RGN.md) is listed as an attendee but had left before the status updates.

## MessageFormat Working Group

[RCA](../../people/RCA.md) could not attend. ## Temporal

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal-temporal#262](https://github.com/tc39/proposal-temporal/issues/262)

After [PFC](../../people/PFC.md)'s pitch, [SFC](../../people/SFC.md) picked one calendar issue of interest to TG2: which calendar takes precedence when `toLocaleString` is called on a [Temporal](../../proposals/temporal.md) object, the object's or the `Intl.DateTimeFormat`'s. [PFC](../../people/PFC.md) preferred the principle of least surprise and siding with the `Intl.DateTimeFormat` calendar, as [PDL](../../people/PDL.md) had suggested in the issue; [USA](../../people/USA.md) noted this gives the same result as `toLocaleString` on a legacy `Date`. [DE](../../people/DE.md) asked about `MonthDay` and `YearMonth` ([SFC](../../people/SFC.md) showed a `MonthDay` example) and suggested always using the [Temporal](../../proposals/temporal.md) calendar, to which [SFC](../../people/SFC.md) replied: "I'd be happy with that, as long as the default calendar on [Temporal](../../proposals/temporal.md) is set to the regional preferences instead of ISO." [SFC](../../people/SFC.md) considered `RefISOYear` [Temporal](../../proposals/temporal.md)-internal and not to be exposed. No conclusion was recorded.

## What settings to include for range formatting? #6

[SFC](../../people/SFC.md) asked whether range formatting should expose settings or stay with defaults; the `collapse: auto` heuristic is meant to be replaced by CLDR data. [ZB](../../people/ZB.md), [FYT](../../people/FYT.md) and [SFC](../../people/SFC.md) agreed to start with a small API surface and add options when requested, and [FYT](../../people/FYT.md) and [SFC](../../people/SFC.md) agreed the default should be single-value rather than an "approximately" format ([SFC](../../people/SFC.md) doubts the locale data quality; [FYT](../../people/FYT.md) said "approximately" is a different feature that should be dealt with separately). [ZB](../../people/ZB.md) objected that leaving collapsing behaviour (e.g. repeating `$` but not `CHF`) to ICU makes ICU the standard that non-ICU implementers would have to copy. [DE](../../people/DE.md) pointed to the precedent of `Intl.ListFormat`, where the spec defines a data schema although CLDR lacks it, and [SFC](../../people/SFC.md) proposed specifying the algorithm while keeping the decisions implementation-defined. [ZB](../../people/ZB.md) said that recipe was satisfactory.

## What grouping strategies to include? #3

ICU has several grouping strategies (for example `min2`) while `useGrouping` today is only true or false, and `auto` behaviour is buggy. [SFC](../../people/SFC.md) proposed expanding `useGrouping` to accept strings (`true` to `auto`, `false` to `never`, plus `always` and perhaps `min2`), leaving out a "thousands" strategy. [FYT](../../people/FYT.md) worried about the observable change (including `resolvedOptions` no longer returning a boolean); [ZB](../../people/ZB.md) suggested a locale-dependent `min` instead of `min2`, which [SFC](../../people/SFC.md) will take to CLDR, and said neither ICU nor CLDR needs to block TG2. A separate issue will cover the `resolvedOptions` question.

## Move scale to the format method? #1

- wiki: [Intl.NumberFormat V3](../../proposals/intl-numberformat-v3.md)
- proposal: [proposal-intl-numberformat-v3#1](https://github.com/tc39/proposal-intl-numberformat-v3/issues/1)

[SFC](../../people/SFC.md) presented the options for placing `scale` (constructor options bag vs. a `format` argument); the motivation is formatting BigInt values (for example cents) without converting to a double and losing precision, as [DE](../../people/DE.md)'s BigDecimal user survey also found. [ZB](../../people/ZB.md) preferred the options bag as the last parameter, while [FYT](../../people/FYT.md) and [JSW](../../people/JSW.md) questioned the need or suggested a separate method; [SFC](../../people/SFC.md) objected to a combinatorial growth of `format*` methods and to cross-browser differences where an older browser silently ignores the option. [DE](../../people/DE.md) and [ZB](../../people/ZB.md) discussed relying on `resolvedOptions` and on education versus the risk to trust in ECMA-402. [SFC](../../people/SFC.md) then changed their mind: the proposal can go forward without this feature, and it is put on pause for later ([DE](../../people/DE.md) was disappointed and hoped for a solution within a few months). The name `scale` and a power-of-10 interpretation ([SFC](../../people/SFC.md), [DE](../../people/DE.md) and [FYT](../../people/FYT.md) in favour) are to be handled in a separate issue.

## Plural rules (ecma402#397)

- proposal: [ecma402#397](https://github.com/tc39/ecma402/issues/397)

[SFC](../../people/SFC.md) presented four options to make `PluralRules` usage with `NumberFormat` output easier to get right, noting that the status quo is to educate developers about `resolvedOptions`; none of the options adds capability that does not already exist. [FYT](../../people/FYT.md) argued that developers must read documentation regardless, so adding API surface does not solve the problem, and [ZB](../../people/ZB.md) and [DE](../../people/DE.md) suggested filing an MDN issue in the ecma402-mdn repo. [MCM](../../people/MCM.md) called it scary to rely on documentation, since TG2 cannot control what tutorials say. [SFC](../../people/SFC.md) suggested fixing through education now and deciding later whether the API is still needed. No formal conclusion was recorded.
