## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). The main debate was [ZB](../../people/ZB.md)'s call for explicit scope guidelines for ECMA-402 (#442), which ended with [SFC](../../people/SFC.md) volunteering a CONTRIBUTING.md PR listing tech-debt items. TG2 reached consensus that ECMA-402 should not be the source of the web platform's default time zone and should not expose a hook for it (#507), held back normative PR #500 for more review, and first discussed the `eraDisplay` option (#426) without a conclusion. [FBN](../../people/FBN.md) previewed `Intl.DisplayNames` for Stage 4 in January, and [FYT](../../people/FYT.md) reported a reshaped Intl Enumeration API. All attendees speak at some point except [CCN](../../people/CCN.md), who is listed but does not appear in the discussion.

## Liaison Updates

[RCA](../../people/RCA.md) reported on the MessageFormat Working Group: a Unicode Conference talk, early consensus on message references and parameters passed by reference, and upcoming discussion of top-level selectors. [EAO](../../people/EAO.md) noted that MessageFormat V2 is starting to look quite different from V1 while V1-to-V2 portability is maintained. [RCA](../../people/RCA.md) asked TG2 for more use cases and is concerned about lossless conversion (open issues such as #119 may need help).

## API surface and scope guidelines #442

- proposal: [ecma402#442](https://github.com/tc39/ecma402/issues/442)

[ZB](../../people/ZB.md) argued that adding every feature with a use case leads to "everything", and asked for agreement that ECMA-402 stays a subset: cut features early, add those that are widely requested or significantly enable a multilingual web, and push back on features needing much more data or logic ("a kitchen sink approach"). [SFC](../../people/SFC.md) preferred case-by-case judgement, noting that it is already a Stage 2 requirement; [LEO](../../people/LEO.md) agreed that case-by-case is easiest but wanted ways to mitigate its cost and suggested weighting community input more. [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md) noted that tech debt and spec cleanup have no champions and little meeting time, while LHO offered to help with spec quality for polyfills' sake. [SFC](../../people/SFC.md) proposed summarising the technical-debt items as bullet points in the repo and pointing to them when promoting proposals to Stage 2, without letting tech debt block feature proposals. **Conclusion: [SFC](../../people/SFC.md) to make a PR adding this list to a CONTRIBUTING.md file ([EAO](../../people/EAO.md) and [RGN](../../people/RGN.md) +1); no formal scope rule was adopted.**

## Intl.DisplayNames for Stage 4

- proposal: [proposal-intl-DateTimeFormat-formatRange#30](https://github.com/tc39/proposal-intl-DateTimeFormat-formatRange/issues/30)

[FBN](../../people/FBN.md) is targeting the January plenary and wanted to discuss two issues first.

### startRange vs shared vs endRange #30

LHO questioned whether the `startRange`/`shared`/`endRange` split in `formatRangeToParts` output is a bug at all, since the spec does not require a given part to be tagged one way. [FBN](../../people/FBN.md) said following CLDR data as-is is an implementation decision rather than spec text, while noting the spec trusts the locale data to follow the shape it describes. [ZB](../../people/ZB.md) leaned towards allowing multiple forms of the data. [SFC](../../people/SFC.md) called it a Chromium or ICU bug that does not justify a spec change, and said that in 2021 the group should take a global look at how much of the locale data format the spec specifies; [FYT](../../people/FYT.md) will look into the bug. No spec change.

### Firefox Implementation of formatRange

- proposal: [Bugzilla 1653024](https://bugzilla.mozilla.org/show_bug.cgi?id=1653024)

[JSW](../../people/JSW.md) said two bugs block the Firefox implementation. [FBN](../../people/FBN.md) believed resolutions exist and was waiting for Anba's reply.

## Include Set Timezone WebDriver extension to allow testing of different timezone? #507

- proposal: [ecma402#507](https://github.com/tc39/ecma402/issues/507)

[FYT](../../people/FYT.md), working on an HTML `timezonechange` event, needs a way to set the time zone for a web platform test and asked where such a hook should be specified (ECMA-402, ECMA-262, or WebDriver). [RGN](../../people/RGN.md) and [LEO](../../people/LEO.md) argued ECMA-402 is a consumer, not a source, of this information and that a standard should not be shaped just to enable a test; [JGT](../../people/JGT.md) said letting apps set the system time zone is a bad idea. [SFC](../../people/SFC.md) noted Temporal also needs the default time zone, which argues that ECMA-402 should not be the source. **Conclusion: consensus ([SFC](../../people/SFC.md), [RGN](../../people/RGN.md), [USA](../../people/USA.md)) that ECMA-402 should not be the source of the web platform's default time zone and should not expose a hook for it.**

## Normative: Use OrdinaryHasInstance in normative optional steps #500

- proposal: [ecma402#500](https://github.com/tc39/ecma402/pull/500)

[RGN](../../people/RGN.md) asked whether the change is breaking. [FYT](../../people/FYT.md) said it could be but the PR author (Anba) argues it is unlikely, and JSC already behaves this way; [FYT](../../people/FYT.md)'s own position is not to change without a reason. [SFC](../../people/SFC.md) said that where web reality is inconsistent the better behaviour should be adopted. **Conclusion: more review required; will not be brought to TC39 next week.**

## Option eraDisplay in Intl.DateTimeFormat() #426

- wiki: [eraDisplay option for Intl.DateTimeFormat](../../proposals/intl-eradisplay.md)
- proposal: [ecma402#426](https://github.com/tc39/ecma402/issues/426)

[SFC](../../people/SFC.md) likened the option to the `hourCycle` / `dayPeriod` distinction. [FBN](../../people/FBN.md) asked whether it should be generalised, for example hiding the year when it is the current year. [EAO](../../people/EAO.md) compared the logic to date ranges deciding which fields to show depending on whether days, months or years are spanned. [SFC](../../people/SFC.md) thought separate flags for [era display](../../proposals/intl-eradisplay.md) and year display would make sense, and [ZB](../../people/ZB.md) asked whether nested options could work. No conclusion was recorded.
