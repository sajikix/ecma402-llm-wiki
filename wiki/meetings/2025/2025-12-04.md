## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). The main topics were the `iso8601` calendar in `Intl.DateTimeFormat` and the handling of the `islamic` calendars in Intl Era and MonthCode. On `iso8601`, the group tentatively favoured a human-readable format (year-month-day fields with localized weekday and other parts) and referred it to the CLDR design group, with [BAN](../../people/BAN.md) assigned. TG2 agreed that the list of calendars should be a closed set like the sanctioned units, and settled that `islamic-rgsa` is dropped from the spec text while the `islamic` to `islamic-tbla` fallback keeps its warning. A PR that fixes an assertion for `Intl.DisplayNames` `languageDisplay` prompted a discussion of "editorial" vs "normative". PCO in the notes is read as [PFC](../../people/PFC.md).

## Updates from the Editors

[BAN](../../people/BAN.md) had nothing meaningful. [USA](../../people/USA.md) merged anba's PR fixing an assertion failure for `languageDisplay` in `Intl.DisplayNames.prototype.resolvedOptions` when the option is not given ([ecma402#1037](https://github.com/tc39/ecma402/pull/1037)). [FYT](../../people/FYT.md) argued this changes observable behaviour and so is normative, while [USA](../../people/USA.md), [PFC](../../people/PFC.md), [RGN](../../people/RGN.md) and [SFC](../../people/SFC.md) saw it as a spec bug (a failing `Assert:`) that no implementation follows, which by convention is treated as editorial. [SFC](../../people/SFC.md) suggested asking the ECMA-262 editors for a third category between editorial and normative; [EAO](../../people/EAO.md) cited the "how we work" definition (normative means observable change).

## iso8601 as DateTimeFormat calendar #1036

- proposal: [ecma402#1036](https://github.com/tc39/ecma402/issues/1036)

[PFC](../../people/PFC.md)'s issue asks whether `iso8601` should really be a `DateTimeFormat` calendar. [SFC](../../people/SFC.md) noted that CLDR is inconsistent on it (Chrome and Firefox differ today) and that specifying and implementing a stable format would be a mini-proposal, and floated retracting the calendar; [USA](../../people/USA.md), [EAO](../../people/EAO.md), [HJS](../../people/HJS.md) and [RGN](../../people/RGN.md) wanted it kept, with big-endian numeric fields (`yyyy-mm-dd`, colon-separated time) but localized weekday and other parts, e.g. `2025-12-04, วันพฤหัสบดี`. [FYT](../../people/FYT.md) argued ISO 8601 defines no canonical output and users should be pointed to [Temporal](../../proposals/temporal.md) `toString`; [RGN](../../people/RGN.md) and [EAO](../../people/EAO.md) replied this is for human-readable output, not stable machine formatting. No formal conclusion: [SFC](../../people/SFC.md) accepted that a human-oriented `iso8601` format is a reasonable way to fill the gap the spec already creates, to be taken to the CLDR design group, and assigned the issue to [BAN](../../people/BAN.md).

## Normative: Ignore "islamic-rgsa" calendar in DateTimeFormat #99

- wiki: [Intl Era/Month Code](../../proposals/intl-era-month-code.md)
- proposal: [proposal-intl-era-monthcode#99](https://github.com/tc39/proposal-intl-era-monthcode/pull/99)

[BAN](../../people/BAN.md)'s PR drops `islamic-rgsa` (no known use) while `islamic` already falls back to `islamic-tbla` with a warning. [EAO](../../people/EAO.md) and [HJS](../../people/HJS.md) would rather treat both alike (fallback to `islamic-tbla` with a warning; [HJS](../../people/HJS.md) noted `islamic-rgsa` is backward-looking only and unsuitable for [Temporal](../../proposals/temporal.md)), while [SFC](../../people/SFC.md) preferred to ignore it and keep the door open. [FYT](../../people/FYT.md) questioned whether anyone uses these, noting macOS lists four Islamic calendars, and [HJS](../../people/HJS.md) said nothing shows use outside ICU. Discussion continued into the next topics and the item was revisited below.

## DateTimeFormat/constructor-options-calendar-islamic-fallback.js should allow other fallback values #4677

- proposal: [test262#4677](https://github.com/tc39/test262/issues/4677)

[FYT](../../people/FYT.md) argued the test over-constrains implementations, since the spec says implementations must support the calendars in the table but not that they support only those. [HJS](../../people/HJS.md), [SFC](../../people/SFC.md) and [EAO](../../people/EAO.md) preferred to change the spec to make the table the closed list, like the sanctioned units and unlike numbering systems, because an unshared calendar cannot fall back gracefully and breaks [Temporal](../../proposals/temporal.md) interop. [FYT](../../people/FYT.md) still disagreed that numbering systems are simple; [PFC](../../people/PFC.md) said the aim is not to make TG2 the authority on calendar algorithms, and [SFC](../../people/SFC.md) described the process for adding a calendar (add rows for the algorithm, era codes, month codes and ISO year conversion). [RGN](../../people/RGN.md) noted a closed set only makes an implementation non-conforming if the spec says so explicitly. **Outcome: [HJS](../../people/HJS.md) and [EAO](../../people/EAO.md) supported making the list of available calendars a closed list; no objection was raised in the notes.**

## Revisit Normative: Ignore "islamic-rgsa" calendar in DateTimeFormat #99

- wiki: [Intl Era/Month Code](../../proposals/intl-era-month-code.md)
- proposal: [proposal-intl-era-monthcode#99](https://github.com/tc39/proposal-intl-era-monthcode/pull/99)

With a closed calendar list, dropping `islamic-rgsa` is less risky. [EAO](../../people/EAO.md) wanted a warning for any unsupported calendar, but [SFC](../../people/SFC.md), [RGN](../../people/RGN.md) and [HJS](../../people/HJS.md) were wary of a generic warning (a formatter created in a loop would warn repeatedly, and it would be a first for ECMA-402); [FYT](../../people/FYT.md) does not know how to implement warnings. **Conclusion: drop `islamic-rgsa` from the spec text so it is handled like any other unsupported calendar, and keep the warning text for `islamic` (possibly revised based on [FYT](../../people/FYT.md)'s feedback); [BAN](../../people/BAN.md), [HJS](../../people/HJS.md) and [EAO](../../people/EAO.md) agreed.**
