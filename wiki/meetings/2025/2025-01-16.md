## Overview

Moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md) (co-moderators). With the February meeting being the last one for ES2025, TG2 planned the work: [RGN](../../people/RGN.md) will open a PR fixing locale resolution for `toLocaleLowerCase`/`toLocaleUpperCase` (#896), and TG2 agreed a three-step direction for making option-reading order comprehensible (#747). Review of the open `Intl.LocaleInfo` issues suggested `minimalDays` should be dropped and that the proposal is not ready for Stage 4, and the currency display proposal (with `formalSymbol` vs `longSymbol` naming) and a Decimal + Measure unification were discussed without formal conclusions.

[SFC](../../people/SFC.md) asked what is being done to prepare for ES2025. [USA](../../people/USA.md) proposed filing a tracking issue, aiming for the same cutoff as ECMA-262 (mid-year) and adding a label for normative changes, which [SFC](../../people/SFC.md) left to the editors. [HJS](../../people/HJS.md) pointed to the W3C i18n group's draft note on string searching (for example searching "jail" might find "gaol"), and [SFC](../../people/SFC.md) asked delegates to cross-reference anything relevant to 402.

## toLocaleLowerCase/toLocaleUpperCase should better align with the rest of ECMA-402 #896

- proposal: [ecma402#896](https://github.com/tc39/ecma402/issues/896)

[RGN](../../people/RGN.md) said these 262 methods take only the first element of the locale list, with no options and no best-fit matching. [HJS](../../people/HJS.md) agreed consistency makes sense for the list handling but not more options, since in practice this is a boolean for Turkic behaviour (and Lithuanian `"lt"`), which could theoretically become three-way if German sharp-S handling changes. [SFC](../../people/SFC.md) preferred allowing browsers to claim all locales for case mapping, with the principle of falling back only when it is unknown whether a locale uses Turkic behaviour. **Conclusion: [RGN](../../people/RGN.md) to make a pull request** (fixing the locale resolution, leaving the options point unchanged).

## Can the order in which properties are read be more comprehensible? #747

- proposal: [ecma402#747](https://github.com/tc39/ecma402/issues/747)

[RGN](../../people/RGN.md) argued the current observable read order is emergent and implied, with double reads possible, and that reading options in defined phases would be less complex even if the spec grows; [SFC](../../people/SFC.md) worried about spec and implementer complexity, since options are currently read only when needed and it is easy to introduce spec bugs. [SFC](../../people/SFC.md) suggested starting with editorial restructuring of a simple constructor such as `Collator` or `PluralRules`, and both agreed normative changes to existing APIs need runway and do not belong in ES2025 (related: #132). **Conclusion: (1) pursue guidelines and spec patterns that are easily checked against them; (2) backport those patterns to existing APIs through editorial changes; (3) consider normative changes to existing APIs.**

## minimalDays

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#86](https://github.com/tc39/proposal-intl-locale-info/issues/86)

[SFC](../../people/SFC.md) said Google Calendar has used ISO week numbers in all locales since 2021, which suggests locale-dependent week numbering is not needed, though first-day-of-week is. [EAO](../../people/EAO.md) added that after Temporal only ISO week numbers exist in JS, so `minimalDays` could mislead, and [HJS](../../people/HJS.md) said HTML `type=week` accepts only ISO weeks. The expected result is that `minimalDays` will not be in the `Intl.LocaleInfo` proposal; [EAO](../../people/EAO.md) wanted implementations of the final spec before Stage 4 and [HJS](../../people/HJS.md) wanted Anba's issues addressed first. [SFC](../../people/SFC.md) judged `Intl.LocaleInfo` not ready for ES2025.

## DurationFormat

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)

[SFC](../../people/SFC.md) said Safari and Firefox have implemented `DurationFormat` but Chrome has not, and planned to ping implementers. [SFC](../../people/SFC.md) believed the issue is a spec bug rather than a normative change and should be fixed soon.

## Currency display

- proposal: [proposal-intl-currency-display-choices#3](https://github.com/tc39/proposal-intl-currency-display-choices/issues/3)

[SFC](../../people/SFC.md) said there is little data in CLDR for `US$` versus `$` and thought this should land in CLDR first, and that the proposal reached Stage 2 at TG1 although TG2 had only approved it for Stage 1 in December. [EAO](../../people/EAO.md) said the data is indirectly present (e.g. `US$` in `en-001`), that TG2 acts as an end user asking for an API, and that this is a Stage 2.7 blocking concern; both acknowledged the misunderstanding. On naming, `formalSymbol` had no established CLDR name and the group weighed `wideSymbol`, `mediumSymbol` and `longSymbol` (fitting `short`/`narrow`/`long`); [SFC](../../people/SFC.md) ended by suggesting "formal symbol" and "long symbol" as the options and filing an issue, and [EAO](../../people/EAO.md) will raise it with the CLDR design team. No formal conclusion.

## Decimal + Measure proposal

- proposal: [ecma402#952](https://github.com/tc39/ecma402/issues/952)
- proposal: [proposal-decimal#185](https://github.com/tc39/proposal-decimal/issues/185)

[JMN](../../people/JMN.md) proposed unifying Decimal and Measure, presenting a two-class option (Decimal for normalised values, Measure built from Numbers, strings or Decimals) or a three-class option that adds a full non-normalised Decimal. [SFC](../../people/SFC.md) supported the direction and wanted both proposals to advance to Stage 2 in the same meeting, arguing Measure with a generic numeric type weakens Decimal's motivation; [USA](../../people/USA.md) agreed this is the window to unify. [EAO](../../people/EAO.md) doubted Decimal's motivation and wanted Measure to preserve the original value it was given, and asked for a clearer case for the synthesis. No formal conclusion; [JMN](../../people/JMN.md) accepted the challenge to present the benefits of a unified whole.
