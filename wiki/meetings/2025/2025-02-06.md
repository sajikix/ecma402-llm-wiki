## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). The bulk of the meeting went to case-mapping locale resolution (ecma402#956) and to the [Stable Formatting](../../proposals/stable-formatting.md) proposal's move to a null (`zxx`) locale, neither of which reached a decision. [PFC](../../people/PFC.md)'s PR to stop adding default date-time formatting for a lone `era` or `timeZoneName` (#957) drew web-compat concerns and is to be split, with HTTP Archive evidence needed for `era`. Two [Intl Locale Info](../../proposals/intl-locale-info.md) items were settled: text directionality is editorial, and `minimalDays` is to be dropped from the Stage 3 proposal before any Stage 4 request. [RGN](../../people/RGN.md) spoke throughout but is not in the attendee list.

## Updates from the MessageFormat Working Group

[EAO](../../people/EAO.md) reported a proposal to delay the final MessageFormat release so the ICU4J implementation can stabilise, possibly by half a year, and asked [SFC](../../people/SFC.md) whether missing the CLDR 47 deadline would be high risk. [SFC](../../people/SFC.md) replied that all the issues they raised have clear runways and only need engineering cycles. [EAO](../../people/EAO.md) also noted that percentage formatting has two distinct routes in `Intl.NumberFormat`; a ballot on it may follow.

## Updates from Implementers

[FYT](../../people/FYT.md) is working on deprecating V8's non-standard `v8BreakIterator` (starting with a warning message, then removal); about 0.2% of page loads use it, mostly for word break. [YSZ](../../people/YSZ.md) had no update.

## Normative: Update String toLocale{Lower,Upper}Case to ResolveLocale with best-fit matching #956

- proposal: [ecma402#956](https://github.com/tc39/ecma402/pull/956)

[RGN](../../people/RGN.md)'s PR makes `toLocaleLowerCase`/`toLocaleUpperCase` use `ResolveLocale` with best-fit matching like the rest of ECMA-402. [HJS](../../people/HJS.md) objected that no locale data exists to tell "en" (root behaviour) apart from unknown locales: implementations only special-case the few languages in Unicode's special-casing file (tr, az, lt), so the API shape does not reflect the data. [RGN](../../people/RGN.md)'s goal is `"I".toLocaleLowerCase(["en", "tr"]) === "i"` while `["tt", "tr"]` gives dotless `ı`; [SFC](../../people/SFC.md) compared this to content locales versus formatting locales (as in `Segmenter`) and said the PR as written does not achieve its goal for `["en", "tr"]`, so a discussion upstream (CLDR/Unicode) about which locales are vetted for case mapping is needed. On the `und`/`zxx` question, [SFC](../../people/SFC.md) answered (and [RGN](../../people/RGN.md) accepted) that lists such as `["und", "tr"]` and `["zxx", "tr"]` should simply fall back to `tr`. No decision on the PR; open pending the upstream data discussion.

## Normative: Don't add default formatting to lone era or timeZoneName #957

- proposal: [ecma402#957](https://github.com/tc39/ecma402/pull/957)

[PFC](../../people/PFC.md) proposed that passing only `era` or `timeZoneName` to `Intl.DateTimeFormat` should no longer add default date/time fields (as already the case for `dayPeriod`). [SFC](../../people/SFC.md) and [HJS](../../people/HJS.md) worried about web compat, since `new Intl.DateTimeFormat("en", { era: "long" }).format(new Date())` is plausible code and the change has been shipping for over a year. [SFC](../../people/SFC.md) could accept the `timeZoneName` change alone, and [HJS](../../people/HJS.md) asked for an HTTP Archive search. [PFC](../../people/PFC.md) will split the PR in two and pursue `era` first with web-compat research; it will not go to the upcoming TG1 meeting, since gathering the evidence before the agenda deadline is unrealistic.

## Select null locale as proposed solution & add Intl API specifics #18

- wiki: [Stable Formatting](../../proposals/stable-formatting.md)
- proposal: [proposal-stable-formatting#18](https://github.com/tc39/proposal-stable-formatting/pull/18)
- slide: [link](https://docs.google.com/presentation/d/14KQA1Gyy0reIyouHtzp5ofYRrcwRjkY6GajeknLWhg0/edit#slide=id.p)

[EAO](../../people/EAO.md) asked whether TG2 accepts the "null locale" direction (solution #2) for [Stable Formatting](../../proposals/stable-formatting.md) and walked through a sketch per API. [SFC](../../people/SFC.md) preferred solution #2, and [EAO](../../people/EAO.md) read the silence as tacit agreement while noting that [ZB](../../people/ZB.md) has concerns. Per-API points: `Collator` follows root collation; `DisplayNames` might simply not support `zxx` ([SFC](../../people/SFC.md) favoured echo-back, [USA](../../people/USA.md) and [RGN](../../people/RGN.md) favoured a hole); `DurationFormat` and unit formatting need short SI-style identifiers, with [RGN](../../people/RGN.md) and [USA](../../people/USA.md) suggesting the ISO 8601 duration format instead; `NumberFormat` output would match the `StrNumericLiteral` grammar, which [RGN](../../people/RGN.md) thought too broad. [SFC](../../people/SFC.md) and [EAO](../../people/EAO.md) agreed that permanent holes should be avoided while temporary ones can be filled later, and [RGN](../../people/RGN.md) wanted a bare `zxx` to end locale matching and be special-cased only with no further subtags. [HJS](../../people/HJS.md) distinguished [stable formatting](../../proposals/stable-formatting.md) from APIs that process input (segmentation, collation), which need a "no locale-specific behaviour" mode instead.

## LocaleInfo minimalDays

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#86](https://github.com/tc39/proposal-intl-locale-info/issues/86)

[SFC](../../people/SFC.md), [EAO](../../people/EAO.md) and [HJS](../../people/HJS.md) recalled deciding in January to leave `minimalDays` out of the API, since the only locales where it matters use ISO weeks. [FYT](../../people/FYT.md) will reduce the scope of the Stage 3 proposal accordingly. The group also agreed the proposal is not ready for Stage 4 until [ABL](../../people/ABL.md)'s issues are resolved.
