## Overview

Co-moderated by [SFC](../../people/SFC.md), with invited expert KAP (Kaleb Pace) as a guest. TG2 approved one normative PR (#1032, `PluralRules` `compactDisplay`) for TG1. ## Normative: In PluralRules, set compactDisplay only if notation is "compact" #1032

- proposal: [ecma402#1032](https://github.com/tc39/ecma402/pull/1032)

`PluralRules` currently stores `compactDisplay` unconditionally (so `resolvedOptions()` reports `"short"` even for non-compact notation), whereas `NumberFormat` only sets it for compact notation. [FYT](../../people/FYT.md)'s PR aligns the two, leaving the slot undefined otherwise. [SFC](../../people/SFC.md), [DLM](../../people/DLM.md) (who also relayed anba's endorsement) and [YSZ](../../people/YSZ.md) supported it. [SFC](../../people/SFC.md) noted this is the third PR on this topic and asked everyone to review more thoroughly, and [FYT](../../people/FYT.md) suggested having tests and a prototype ready before landing. **Conclusion: TG2 approves. Bring to the TG1 meeting.**

## Fix corner-case issues identified in testing #10

- proposal: [proposal-intl-keep-trailing-zeros#10](https://github.com/tc39/proposal-intl-keep-trailing-zeros/pull/10)

[SFC](../../people/SFC.md) read out [EAO](../../people/EAO.md)'s comment: validating the spec text against a patched FormatJS fork showed that leading zeros, an elided leading zero (`.45`) and exponent or percent scaling must be accounted for when counting string digits. [SFC](../../people/SFC.md) thought it a good change to bring to TG1 (as a reviewer, still to review). No implementation exists yet since the proposal is at Stage 2.7.

## Trailing zeros are retained also after rounding long input without trailing zeros #11

- proposal: [proposal-intl-keep-trailing-zeros#11](https://github.com/tc39/proposal-intl-keep-trailing-zeros/issues/11)

The proposal also keeps trailing zeros in the formatted output when a long string input is rounded (e.g. `nf.format('1.96')` with `maximumFractionDigits: 1` gives `'2.0'` rather than `'2'`), a wider behaviour change than previously noted. The Numerics call judged this correct but broader than expected, which raises the question of whether the old behaviour needs an opt-back option. HJS asked why opting into the old rather than the new behaviour, and about web compatibility; [SFC](../../people/SFC.md) said [EAO](../../people/EAO.md) and the group consider the web-compat risk low given earlier string-formatting changes. No decision was made.

## Add trailingZeroDisplay: 'stripToMinimum' option value #12

- proposal: [proposal-intl-keep-trailing-zeros#12](https://github.com/tc39/proposal-intl-keep-trailing-zeros/pull/12)

[EAO](../../people/EAO.md) proposed a `trailingZeroDisplay: 'stripToMinimum'` value that gives the current float/BigInt behaviour for strings too, with `"auto"` taking the new behaviour. [SFC](../../people/SFC.md)'s updated view is that the option is more motivated than before (e.g. decimal strings with more significant digits than a float holds) but still not motivated enough for TG2 to add proactively. TG2 stayed quiet and left it to feedback from the Tokyo plenary, where [EAO](../../people/EAO.md) has a topic. **Conclusion: [SFC](../../people/SFC.md) read the room as TG2 being happy with the champions' recommendation, without many further opinions.**

## Section 9.1 AvailableLocales shouldn't require base language if script is present #947

- proposal: [ecma402#947](https://github.com/tc39/ecma402/issues/947)

The spec requires that if a narrow tag such as `zh-TW` is available, so are its less narrow tags; the Translator API (dynamic model loading) wanted to reuse this fallback. HJS and [RGN](../../people/RGN.md) questioned why ECMA-402 should constrain that API, and [RGN](../../people/RGN.md) noted that ECMA-402 has no concept of failure (resolving to default data is fine) and that dynamic lists differ from the spec's static `[[AvailableLocales]]`. [SFC](../../people/SFC.md) concluded that the Translator API, which rejects when a locale is unsupported, is different enough that this requirement need not carry over, and [RGN](../../people/RGN.md) agreed. No change to ECMA-402 was decided.

## Add kilowatt-hour unit to Intl.NumberFormat #739

- proposal: [ecma402#739](https://github.com/tc39/ecma402/issues/739)

KAP, from the energy forecasting industry, asked for `watt`, `kilowatt` and `kilowatt-hour` (all already in CLDR). [SFC](../../people/SFC.md) explained the roughly 40 sanctioned units were limited for data size and that there are around 10 open user-filed requests for more. [DLM](../../people/DLM.md), [FYT](../../people/FYT.md) and [YSZ](../../people/YSZ.md) supported the motivation and preferred a small, narrowly scoped proposal that keeps to what is really needed. [SFC](../../people/SFC.md) agreed that narrow proposals advance more smoothly. **Conclusion: no formal vote; next step is a Stage 1 proposal (the README is enough, and KAP need not present), aiming for Stage 2 in January once spec text exists.**
