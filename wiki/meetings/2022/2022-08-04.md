## Overview

Moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md) (co-moderators). TG2 settled the `useGrouping` web-compatibility question for `Intl.NumberFormat` v3 (map the strings "true" and "false" to "auto", reject all other unspecified strings), and asked [USA](../../people/USA.md) to revert or justify two [Temporal](../../proposals/temporal.md)-driven changes to `Intl.DateTimeFormat` (field access order in `InitializeDateTimeFormat`, and `RangeError` vs `TypeError` in `formatRange`). For `Intl.DurationFormat`, [USA](../../people/USA.md) was asked to proceed on the assumption that `formatToParts` exposes numeric part types. AP (W3C I18N WG) presented an explainer on a localizable string type with language and direction metadata; no decision was sought. [MCM](../../people/MCM.md) spoke during that discussion but is not in the attendee list. Tomomi Imura is listed as an attendee without an abbreviation and did not speak in the notes.

## Updates from the Editors

[USA](../../people/USA.md) reported merging a couple of PRs; no normative PRs were on the agenda ("none this month").

## Web compatibility: Allow the string "true" for "useGrouping"? #74

- wiki: [Intl.NumberFormat V3](../../proposals/intl-numberformat-v3.md)
- proposal: [proposal-intl-numberformat-v3#74](https://github.com/tc39/proposal-intl-numberformat-v3/issues/74)

Because [NumberFormat v3](../../proposals/intl-numberformat-v3.md) adds new `useGrouping` values, [KG](../../people/KG.md) raised the question of what to do with unrecognised strings. Before v3 any non-empty string was treated as true (and "false" briefly threw), so browsers already ship that behaviour. [USA](../../people/USA.md) floated splitting into two options, but [SFC](../../people/SFC.md) argued shipped web reality should be ruled out first, since this is a Stage 3 proposal; [FYT](../../people/FYT.md) preferred throwing for "false" while [EAO](../../people/EAO.md), [YSZ](../../people/YSZ.md) and [KG](../../people/KG.md) favoured preserving what works today. [KG](../../people/KG.md) distinguished breaking "in theory" from "in practice" and recommended special-casing only the known strings. **Conclusion: map both "true" and "false" to "auto" and reject all other strings not otherwise defined.**

## Changes to InitializeDateTimeFormat break web compatibility #2363

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal-temporal#2363](https://github.com/tc39/proposal-temporal/issues/2363)

[FYT](../../people/FYT.md) reported that [Temporal](../../proposals/temporal.md)'s changes to `Intl.DateTimeFormat` alter the observable order in which option fields are read, which fails existing test262 tests; [FYT](../../people/FYT.md) said the [Temporal](../../proposals/temporal.md) polyfill's `toLocaleString` entry point does not exercise the constructor, which is why the polyfill's test262 runs did not catch it. [YSZ](../../people/YSZ.md) asked whether the change is mandatory for [Temporal](../../proposals/temporal.md) or merely a refactor, and [SFC](../../people/SFC.md) suspected a refactor. [FYT](../../people/FYT.md) also asked that [Temporal](../../proposals/temporal.md)'s ECMA-402 changes get more discussion in TG2. **Conclusion: [USA](../../people/USA.md) to attempt to revert the behaviour changes.**

## formatRange(ToParts)? throw RangeError instead of TypeError #1932

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal-temporal#1932](https://github.com/tc39/proposal-temporal/issues/1932)

[Temporal](../../proposals/temporal.md) changed the error thrown by `formatRange` / `formatRangeToParts` from `RangeError` to `TypeError`. [KG](../../people/KG.md) said changing an error type has in practice not been a web-compat problem (HTML has a policy to that effect), while [FYT](../../people/FYT.md) objected to changes without justification, and to the memory footprint of [Temporal](../../proposals/temporal.md)'s pattern handling in `DateTimeFormat`. [SFC](../../people/SFC.md) asked [Temporal](../../proposals/temporal.md) champions to be more explicit about ECMA-402 changes and suggested `DateTimeFormat` errors be consistent with the rest of [Temporal](../../proposals/temporal.md), and encouraged [FYT](../../people/FYT.md) and others to open issues with implementer feedback. **Conclusion: [USA](../../people/USA.md) to investigate and either revert the behaviour change or return to TG2 with the proposed change and its motivation for an explicit decision.**

## Include individual numeric parts #19

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#19](https://github.com/tc39/proposal-intl-duration-format/issues/19)

The question is whether `Intl.DurationFormat` `formatToParts` should expose numeric parts as `NumberFormat` does. [FYT](../../people/FYT.md) and [SFC](../../people/SFC.md) favoured following the `DateTimeFormat` / `RelativeTimeFormat` precedent, while [USA](../../people/USA.md) worried that verbosity would hinder the common case. [ZB](../../people/ZB.md) and [SFC](../../people/SFC.md) cited styling of numbers and units separately as a familiar use case, and [SFC](../../people/SFC.md) noted multiple numeric parts are uncommon in practice (few units take fraction digits, grouping is rare). **Conclusion: [USA](../../people/USA.md) to move forward with the assumption of using numeric types, and come back with a more specific PR to discuss next month.**

## Presentation from Addison Philips, chair of the W3C Internationalization WG

AP presented an [explainer](https://github.com/w3c/i18n-discuss/blob/gh-pages/explainers/string-meta-explainer-402.md) asking whether ECMAScript could gain a type for localizable strings carrying language and base-direction metadata, so formatter output (for example `Intl.DurationFormat`, `ListFormat`) need not rely on out-of-band annotation or inserted RLM marks. [FYT](../../people/FYT.md) questioned the added value over composite existing types, and [SFC](../../people/SFC.md) (with a Records and Tuples aside) and [EAO](../../people/EAO.md) (String instances have no `toJSON`) raised alternatives and concerns; [SFC](../../people/SFC.md) wanted discussion of the problem and ECMA-402 use cases (`formatToParts`, MessageFormat v2, text layout, spoken text) before a solution. [ZB](../../people/ZB.md) (voice interfaces, mixed-script Arabic strings) and [MCM](../../people/MCM.md) (fit across web APIs, tree of strings sharing metadata) commented. No conclusion was recorded.
