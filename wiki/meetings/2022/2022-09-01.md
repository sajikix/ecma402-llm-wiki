## Overview

Moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md) (co-moderators). TG2 approved PR #708 (adding `microsecond` and `nanosecond` to the sanctioned unit identifiers, needed by `Intl.DurationFormat`), confirmed that unspecified `useGrouping` strings should throw `RangeError` ([RCA](../../people/RCA.md) to write the PR), and worked through a batch of `Intl.DurationFormat` issues. Consensus was reached on `style: "digital"` defaulting hours, minutes and seconds to always displayed ([USA](../../people/USA.md) to present to plenary), on `"short"` as the default `style`, and on `"short"` rather than `"narrow"` for non-numeric units under the digital style. [EAO](../../people/EAO.md)'s MessageFormat update led to a discussion of splitting bundles (message resources) from single messages.

## Updates from the Editors

[USA](../../people/USA.md) noted a new normative PR from [FYT](../../people/FYT.md) adding microseconds and nanoseconds as required by `Intl.DurationFormat`, which lets it use the unit formatting mode of `Intl.NumberFormat` (#708, discussed below).

## MessageFormat Working Group

[EAO](../../people/EAO.md) reported work continuing towards technical previews: the JS `Intl.MessageFormat` polyfill exists, [ZB](../../people/ZB.md) is working on a Rust implementation and an ICU4X PR, and Mihai on an ICU4J PR. [EAO](../../people/EAO.md) is also trying to set up a working group for message resources (files containing multiple messages), which the ECMA-402 `Intl.MessageFormat` proposal currently depends on alongside single messages. [SFC](../../people/SFC.md) suggested presenting first to TG2 and then to the November plenary a split into two Stage 1 proposals, so the single-message proposal can proceed to Stage 2 early next year; [EAO](../../people/EAO.md) said bundle support is a single entry point returning a map of `Intl.MessageFormat` instances, so unbundling is easy at the API level, and agreed to aim for November because the next plenary cannot be met. [FYT](../../people/FYT.md) worried that the bundle proposal might acquire extra dependencies (for example message references).

## Proposal Status Changes

[FYT](../../people/FYT.md) reported that `Intl.NumberFormat` v3 ships in Chrome M106 (beta already available) and asked for bug reports; [FYT](../../people/FYT.md) is now working on the `Intl.DurationFormat` implementation and needs to sync with [USA](../../people/USA.md).

## Normative: Add "microsecond" and "nanosecond" to IsSanctionedSingleUnitIdentifier #708

- proposal: [ecma402#708](https://github.com/tc39/ecma402/pull/708)

[SFC](../../people/SFC.md) noted new unit identifiers are normally avoided because of data size, but `Intl.DurationFormat` needs this data, so it should be exposed through `Intl.NumberFormat`. [FYT](../../people/FYT.md) measured about 15K in Chromium for the two units, needed anyway for `Intl.DurationFormat`. [USA](../../people/USA.md) found the units useful, [EAO](../../people/EAO.md) gave +1, and [USA](../../people/USA.md) relayed a +1 from Anba. **Conclusion: TG2 consensus.**

## Web compatibility: Allow the string "true" for "useGrouping"? #74

- proposal: [proposal-intl-numberformat-v3#74](https://github.com/tc39/proposal-intl-numberformat-v3/issues/74)

[SFC](../../people/SFC.md) recapped last month's agreement (map "true" and "false" to "auto", undo the other truthy-string mappings) and relayed [RCA](../../people/RCA.md)'s clarifying question: throw `RangeError` for any other string not in the spec. [FYT](../../people/FYT.md) wanted the PR written to get an affirmative answer, and the PR is to be presented at the Tokyo plenary. **Conclusion: throw `RangeError` on unspecified strings; [RCA](../../people/RCA.md) to make a PR.**

## The resolved plural class is wrong in the current spec of PartitionDurationFormatPattern #118

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#118](https://github.com/tc39/proposal-intl-duration-format/issues/118)

The bug came from an edge case where `Intl.DurationFormat` used `NumberFormat` in decimal mode plus `PluralRules`. Now that it delegates to `NumberFormat` unit formatting, the `PluralRules` instance is no longer needed; [USA](../../people/USA.md) thought a dangling instance remained, and [FYT](../../people/FYT.md) replied the line had already been removed. [FYT](../../people/FYT.md) noted the dependency on the NumberFormat v3 PR and the two additional units. **Conclusion: this issue seems to be obsolete.**

## Normative: Make ToDurationRecord same order as ToTemporalPartialDurationRecord #117

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#117](https://github.com/tc39/proposal-intl-duration-format/pull/117)

[FYT](../../people/FYT.md) proposed splitting the unit table and using Temporal's order only in the relevant abstract operation. [SFC](../../people/SFC.md) explained Temporal uses alphabetical order because `Date` has no calendar-independent order by magnitude, whereas the duration order is specified, so Temporal could be asked to adopt that order for durations only; [FYT](../../people/FYT.md) considered that a hard sell after Stage 3 but wanted to avoid the dependency, and [USA](../../people/USA.md) agreed to talk to the Temporal champions. **Conclusion: discuss with Temporal first so work is not duplicated.**

## Should default style be "short" instead of "long"? #116

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#116](https://github.com/tc39/proposal-intl-duration-format/issues/116)

[USA](../../people/USA.md) said consistency of the default `style` across Intl constructors matters more than the choice itself, and recalled the original text used "short" before "long" was adopted over ambiguity worries. [SFC](../../people/SFC.md) noted `Intl.NumberFormat` defaults to "short" and `Intl.ListFormat` to "long" because defaults should follow each formatter's common use case; [FYT](../../people/FYT.md) asked that the change be communicated well to other implementers. [YSZ](../../people/YSZ.md) gave +1. **Conclusion: use "short" as the default.**

## the output of minutes + seconds and hours+minutes in "digital" format could be the same #54

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#54](https://github.com/tc39/proposal-intl-duration-format/issues/54)

With every unit defaulting to `display: "auto"`, different inputs (hours+minutes, minutes+seconds) can produce the same string; [FYT](../../people/FYT.md) proposed that `style: "digital"` default hour, minute and second to always display. [USA](../../people/USA.md) worried about educational burden since `Intl.DurationFormat` is otherwise hide-by-default, but [SFC](../../people/SFC.md) was swayed by [FYT](../../people/FYT.md) (the digital style already has many special cases and it is less code to derive h:m or m:s from h:m:s), and [RCA](../../people/RCA.md), [EAO](../../people/EAO.md) and [YSZ](../../people/YSZ.md) supported; [USA](../../people/USA.md) said it could be lived with. **Consensus: move forward with hour/minute/second defaulting to always displayed with the digital style; [USA](../../people/USA.md) to present it to plenary at the next meeting.**

## Should the default digital non-numeric style be short or narrow? #85

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#85](https://github.com/tc39/proposal-intl-duration-format/issues/85)

[SFC](../../people/SFC.md) argued for "short" as the non-ambiguous choice, and [FYT](../../people/FYT.md) wondered whether it might reduce testing complexity (not certain). [USA](../../people/USA.md) had chosen "narrow" as the closest to numeric as a best-effort option, was neutral on the outcome, and worried it might create noise in plenary. **Conclusion: use "short".**

## Too easy create incoherent result without enough restriction #115

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#115](https://github.com/tc39/proposal-intl-duration-format/issues/115)

[FYT](../../people/FYT.md) was concerned about testing complexity from the very permissive option design. [USA](../../people/USA.md) and [SFC](../../people/SFC.md) replied that the current design was the only one that handled digital formatting and zero-valued fields, and the test surface is limited since most options bubble down to already-tested formatters; [SFC](../../people/SFC.md) mentioned an alternative of two per-field settings (always/auto display, numeric/non-numeric). **Conclusion: [USA](../../people/USA.md) to drive the relationship with [PFC](../../people/PFC.md) (test262 maintainers) on a testing strategy.**
