## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). The meeting opened with a walk through the proposal status wiki, where the group agreed to start tracking the ECMA-402 side of Temporal and the calendar specification work. TG2 then agreed to add bounds to the mathematical-value exponent in the NumberFormat v3 proposal (about +/-10K), chose option 2 for the `roundingIncrement` default fraction digits problem, and concluded that `Intl.DurationFormat` should be decoupled from Temporal. The notes record MessageFormat WG speaker `EOA` once; it is normalised to [EAO](../../people/EAO.md).

## Editor's Update

[RGN](../../people/RGN.md) had no big updates. [FYT](../../people/FYT.md) asked about the PDF of the 2022 edition; [USA](../../people/USA.md) noted ECMA was trying to get professional help with the PDF, and [RGN](../../people/RGN.md) pointed to the `es2022-candidate` release, which includes PDFs.

## MessageFormat Working Group

[RCA](../../people/RCA.md) reported work on syntax issues to get ready for a release next fall. [EAO](../../people/EAO.md) said the group is under time pressure (ICU wants code to land by mid August) and asked everyone to comment on the open syntax issues. [SFC](../../people/SFC.md) asked how the two competing syntax proposals would be reconciled and argued that the larger proposal should be considered as a whole; [EAO](../../people/EAO.md) replied that doing so had been tried twice without results, so the WG is now looking for divisive issues and discussing them one by one.

Review of the [status wiki](https://github.com/tc39/ecma402/wiki/Proposal-and-PR-Progress-Tracking). PR #615 was judged effectively abandoned and to be closed unless it is in a milestone. [FYT](../../people/FYT.md) said Locale Info and Enumeration were not quite ready for Stage 4 (perhaps July), and that `Intl.NumberFormat` v3 had remaining implementation work in V8 (about 80% confident of finishing by the end of Q3). [USA](../../people/USA.md) reported progress on `Intl.DurationFormat`.

[FYT](../../people/FYT.md) and [USA](../../people/USA.md) argued that the ECMA-402 parts of Temporal (Section 15, era and calendar handling) should be tracked in this group's wiki; [SFC](../../people/SFC.md) noted that Temporal's Intl surface is about as large as all of ECMA-402, that the group had a Temporal deep dive in February, and that material discussion belongs in the Temporal champions meeting. The group agreed to track the 402 section of Temporal and, as an additional row, [USA](../../people/USA.md)'s calendar specification work; [RCA](../../people/RCA.md) took the action to update the wiki (a "dependencies" note in the comments was floated). [FYT](../../people/FYT.md) described a V8 Temporal implementation with very awkward code for the leading month in the Chinese calendar, and [SFC](../../people/SFC.md) said implementers were hitting a wall without a Unicode-level calendar specification, which is expected to land as a new Technical Report.

On Stage 1 items, [SFC](../../people/SFC.md) said the [Era Display](../../proposals/intl-eradisplay.md) questions had all been discussed and it looked ready for Stage 2 ([SFC](../../people/SFC.md) as champion, aiming for July), with [LAF](../../people/LAF.md) supporting. Segmenter V2 was described as abandoned; the MessageFormat proposal was waiting on the Unicode work. [SFC](../../people/SFC.md) said the Unit Preferences work still had to decide whether to build a stronger impact case or argue from the multilingual web.

## Limit exponent of intl mathematical value #98

- proposal: [proposal-intl-numberformat-v3#98](https://github.com/tc39/proposal-intl-numberformat-v3/issues/98)

[SFC](../../people/SFC.md) explained that with unbounded mathematical values the library must handle arbitrary exponents (ICU does, ICU4X does not) and operations such as `LessThan` are tricky on strings. The proposal is being revised to a +/-10K exponent: a double needs a 16-bit exponent, ICU4X stores a 16-bit exponent (32K), and rounding to a power of 10 gives about 10K. [FYT](../../people/FYT.md) supported +/-10K but was unsure about a significant-digits limit; [YSZ](../../people/YSZ.md) noted a string length check cannot bound the exponent (`"1.0E10000"`), so parsing is still needed. [SFC](../../people/SFC.md) cited `Number.prototype.toExponential` and the Date range as prior art. [GPT](../../people/GPT.md), [ZB](../../people/ZB.md) and [LAF](../../people/LAF.md) were neutral to mildly in favour, noting a limit can later be lifted but not added later. **Conclusion: OK to add limits; [SFC](../../people/SFC.md) to follow up with a specific PR.**

## Only passing roundingIncrement will throw an error. #97

- proposal: [proposal-intl-numberformat-v3#97](https://github.com/tc39/proposal-intl-numberformat-v3/issues/97)

[YSZ](../../people/YSZ.md) raised that `{ roundingIncrement: 100 }` throws because the default minimum and maximum fraction digits differ. [SFC](../../people/SFC.md) laid out three options: (1) status quo; (2) if `roundingIncrement` is present, set the default maximum fraction digits equal to the minimum default, so the bare increment no longer throws but mismatched explicit digits still do; (3) if only one of the two digit options is set, copy it to the other. [SFC](../../people/SFC.md) voted for 2 because the constraint can later be relaxed, and [EAO](../../people/EAO.md) noted 2 can later be extended to 3. [FYT](../../people/FYT.md), [USA](../../people/USA.md) and [YSZ](../../people/YSZ.md) also preferred option 2. **Conclusion: move forward with option 2.**

## editorial: move necessary AOs from Temporal #96

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#96](https://github.com/tc39/proposal-intl-duration-format/pull/96) (follow-up to [#92](https://github.com/tc39/proposal-intl-duration-format/pull/92))

[USA](../../people/USA.md) explained that PR #92, meant as an unrelated bug fix, made the spec reference Temporal's `ToTemporalDurationRecord`, introducing a dependency of one Stage 3 spec on another and, through the Duration string grammar, a long chain of Temporal abstract operations. The group distinguished two dependencies: input coercion (easy to decouple by accepting only option-bag durations) and arithmetic (`largest/smallest unit`); [SFC](../../people/SFC.md) asked that the spec's editor's note reflect what was recorded on GitHub. [SFC](../../people/SFC.md) and [FYT](../../people/FYT.md) said the Stage 2 to 3 review should have caught the linkage. [USA](../../people/USA.md) proposed removing [DurationFormat](../../proposals/intl-durationformat.md)'s abstraction references and later adding string handling by pointing to Temporal; [EAO](../../people/EAO.md) asked whether the proposal could be split into two Stage 3 proposals, which [SFC](../../people/SFC.md) left open. [RCA](../../people/RCA.md), [LAF](../../people/LAF.md) and [YSZ](../../people/YSZ.md) supported decoupling. **Conclusion: decouple the two proposals; the exact mechanism is to be discussed.**
