## Overview

Moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md) (co-moderators). TG2 reached consensus on the Gregorian BC(E) era fix (#729), while two `fractionalSecondDigits` PRs (#733 to accept 0, #715 for 4-9 digits) were sent back to the backlog or to a later revisit, mainly on implementer objections. [RGN](../../people/RGN.md)'s proposal to allow numeric-offset host time zones (#683) and the direction of supporting the UTS 35 subtag set (#580) got a go-ahead, the `Intl.Locale` info getters-to-methods question (#65) was left open with the group "OK with either conclusion", and TG2 settled the plural naming status quo for `Intl.DurationFormat` (#44). [FYT](../../people/FYT.md) reported that Intl Enumeration was approved for Stage 4 and [SFC](../../people/SFC.md) that Intl NumberFormat v3 would go for Stage 4 in January.

## Proposal Status Changes

[FYT](../../people/FYT.md): Intl Enumeration is approved for Stage 4 and ready for the editors to merge. [SFC](../../people/SFC.md): Intl NumberFormat v3 will go for Stage 4 in January.

## Normative: Correct Gregorian calendar BC(E) era to signed years less than 1 AD #729

- proposal: [ecma402#729](https://github.com/tc39/ecma402/pull/729)

[RGN](../../people/RGN.md) described this as an off-by-one error in the spec that no implementation follows, so it is purely a spec bug. [FYT](../../people/FYT.md) agreed (without having had time to review it before TC39) and [LAF](../../people/LAF.md) confirmed it is the correct way of counting years. **Conclusion: TG2 consensus.**

## Normative: support fractionalSecondDigits to be 0 #733

- proposal: [ecma402#733](https://github.com/tc39/ecma402/pull/733)

[FYT](../../people/FYT.md) opposed: accepting 0 would make `resolvedOptions()` differ from the input (or require retaining the difference between `undefined` and 0). [SFC](../../people/SFC.md) first argued an option taking a number should accept every sensible number, but was persuaded that this is a papercut not worth fixing, while [RGN](../../people/RGN.md) saw a clear use case for 0 and [USA](../../people/USA.md) supported the patch as the smallest spec diff. [FYT](../../people/FYT.md) could live with accepting 0-3 and returning 0 in `resolvedOptions()`, which the PR does not currently do, and [USA](../../people/USA.md) preferred a PR that bubbles 0 through the spec. **Conclusion: put the issue on the backlog.**

## Normative: Updates on fractionalSecondDigits in preparation for Temporal #715

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [ecma402#715](https://github.com/tc39/ecma402/pull/715)

[FYT](../../people/FYT.md) and [RGN](../../people/RGN.md) agreed that setting 4-9 digits to `undefined` is bad, and [FYT](../../people/FYT.md) warned that ICU cannot support more than 3 digits (its API takes a 64-bit double) and that a new ICU API could delay [Temporal](../../proposals/temporal.md) by 6 to 9 months. [USA](../../people/USA.md) felt ICU limits should not hold the spec back and that a best-effort format would be acceptable; [FYT](../../people/FYT.md) and [DLM](../../people/DLM.md) objected to specifying a feature that cannot be supported, and [USA](../../people/USA.md) agreed it should return to the [Temporal](../../proposals/temporal.md) discussion. [SFC](../../people/SFC.md) suggested backlogging the issue while upgrading ICU in parallel; `Intl.DurationFormat` is unaffected because it uses `NumberFormat`. **Conclusion: revisit in the future.**

## ECMA-402 should allow numeric-offset host time zones #683

- proposal: [ecma402#683](https://github.com/tc39/ecma402/issues/683)

[RGN](../../people/RGN.md) explained that [Temporal](../../proposals/temporal.md) time zones can be numeric offsets such as "+01:00", which ECMA-402 currently rejects, forcing [Temporal](../../proposals/temporal.md) to override between 402 and 262; supporting them in 402 ahead of [Temporal](../../proposals/temporal.md) would be more convenient (e.g. `new Intl.DateTimeFormat("en", { timeZoneName: "+01:00" })`, as [SFC](../../people/SFC.md) framed it). [SFC](../../people/SFC.md) noted CLDR, ICU and ICU4X support this, so there are no implementation blockers; the format is a sign plus hours and optional minutes, with no seconds. [LAF](../../people/LAF.md), [YSZ](../../people/YSZ.md) and [DLM](../../people/DLM.md) were fine with it and [FYT](../../people/FYT.md) needed more time to think. **Conclusion: move forward with a PR; no formal approval until the PR is reviewed.**

## Normative: Change the getters to methods #65

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#65](https://github.com/tc39/proposal-intl-locale-info/pull/65)

[RGN](../../people/RGN.md) raised the mixture of getters that return objects and proposed `.getXXX` names for those, so a `get` prefix signals a function call; [DLM](../../people/DLM.md) leaned that way. [ZB](../../people/ZB.md) disagreed with the problem, citing `keys()`/`values()`/`entries()` prior art and the Rust community's push to drop `get`, and thought it should go to TG1. [SFC](../../people/SFC.md) noted getters should return primitives and that [Temporal](../../proposals/temporal.md) recently proposed `getCalendar()` and `getTimeZone()`; [FYT](../../people/FYT.md) would add the prefix and saw a side benefit for the time zone issue raised by Anba, but the `get` name had not actually been presented in plenary. **Conclusion: continue discussion on the issue and tag in people who may be opinionated; the group is OK with either outcome.**

## List of preferences to be exposed #3

- proposal: [user-locale-client-hints#3](https://github.com/romulocintra/user-locale-client-hints/issues/3)

[SFC](../../people/SFC.md) wanted to decide which preferences go into an initial bucket. [YSZ](../../people/YSZ.md) said exposing the data without a permission prompt or explicit user choice is a non-starter and would discuss the privacy side internally at Apple. [FYT](../../people/FYT.md) worried a single bucket steers the discussion and proposed at least separating time-related preferences (first day of week, calendar) from others (numbering system, collation, currency, script), whose privacy impact differs; [SFC](../../people/SFC.md) noted a per-property bucket lets the permission model be abstracted away. **Conclusion: pass this feedback to [RCA](../../people/RCA.md); [YSZ](../../people/YSZ.md) will follow up.**

## Add support for more subtags #580

- proposal: [ecma402#580](https://github.com/tc39/ecma402/issues/580)

[USA](../../people/USA.md) asked how to catch up with the existing set of Unicode locale subtags and how to stay caught up. [SFC](../../people/SFC.md) argued ECMA-402 should support every subtag that influences its formatters; [FYT](../../people/FYT.md) pointed out that `cu` is explicitly excluded (PR #581), so `cf` should not be supported either, and [SFC](../../people/SFC.md) took the existing exclusion text as implying everything else is intended to be supported. **Conclusion: OK to move in the direction of supporting what is in UTS 35.**

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)

## singular/plural consistency of property in "Table 1: Components of Duration Instances" against Temporal and Intle.DateTimeFormat #44

- wiki: [Intl.DurationFormat](../../proposals/intl-durationformat.md)
- proposal: [proposal-intl-duration-format#44](https://github.com/tc39/proposal-intl-duration-format/issues/44)

[FYT](../../people/FYT.md) framed three things: (A) `Temporal.Duration.from` field names (plural), (B) `Intl.DurationFormat` option and `resolvedOptions` keys, and (C) unit names in `smallestUnit` and similar (singular); the question is whether (B) should follow (A) or (C). [RGN](../../people/RGN.md) found consistency with `Temporal.Duration` the most compelling, [FYT](../../people/FYT.md) stressed consistency with `NumberFormat`, and [SFC](../../people/SFC.md) noted polyfill authors may pass these options to `NumberFormat`, which [RGN](../../people/RGN.md) said is not a constituency to optimise for. **Conclusion: (A) is plural, (B) is plural (believed to be the status quo), (C) is singular; action item is to ensure the spec is fully internally consistent.**
