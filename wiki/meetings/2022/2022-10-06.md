## Overview

Moderated by [SFC](../../people/SFC.md) (co-moderator). Intl Enumeration API was cleared to go to Stage 4 once PR #43 is merged, while [Intl Locale Info](../../proposals/intl-locale-info.md)'s planned Stage 4 slot was withdrawn so the `Intl.Locale` info getters (#62, #33) could be sorted out. `proposal-intl-temporal` was renamed `proposal-intl-era-and-month-codes`, and message resources were split out of the MessageFormat proposal (approved for Stage 1). PR #709 was approved with conditions, while PRs #715 and #714 were deferred. [Intl.DurationFormat](../../proposals/intl-durationformat.md) was said to be close to Stage 4, with a request possible in January 2023. TIA is listed as an attendee but does not speak.

## Editor's Update

[RGN](../../people/RGN.md) reported that the layering between ECMA-262 and ECMA-402 has been clarified: an ECMA-262 normative change (time zones accepting offset strings) will have normative consequences for ECMA-402, and the ECMA-402 constraint on the default time zone goes away. [FYT](../../people/FYT.md) asked about implementations and test262; [RGN](../../people/RGN.md) said current implementations cannot output a numeric offset and will take the test262 question to the test262 folks.

## MessageFormat Working Group

[RCA](../../people/RCA.md): the technical preview PR has landed and will be available in ICU 72; announcements and a press release are being prepared.

## Proposal Status Changes

[Intl.DurationFormat](../../proposals/intl-durationformat.md): [YSZ](../../people/YSZ.md) said Apple has implemented per the proposal and still has to look at the `formatToParts` decision; [FYT](../../people/FYT.md) said the V8 implementation is in progress with bugs mostly around `formatToParts`. [SFC](../../people/SFC.md) thought the proposal is close to ready for Stage 4 and could ask for advancement at the January meeting.

## Normative: Update spec to align with MDN & preparation for Temporal

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [ecma402#715](https://github.com/tc39/ecma402/pull/715)

The PR peels off changes (`fractionalSecondDigits` accepting 0 without throwing, and support for 4-9 digits) from the [Temporal](../../proposals/temporal.md) monolith. [FYT](../../people/FYT.md) questioned pulling it out separately and wondered about supporting 4-9 digits if [Temporal](../../proposals/temporal.md) never ships, while [PFC](../../people/PFC.md) and [SFC](../../people/SFC.md) argued that peeling changes off is worthwhile and that the two issues it solves are independent. **Conclusion: [FYT](../../people/FYT.md), [PFC](../../people/PFC.md), [SFC](../../people/SFC.md) and [RCA](../../people/RCA.md) to discuss offline and come up with a resolution for the next meeting.**

## Normative: Add new numbering systems "kawi" and "nagm" #714

- proposal: [ecma402#714](https://github.com/tc39/ecma402/pull/714)

The new numbering systems come with Unicode 15 / ICU 72. [FYT](../../people/FYT.md) recalled that in similar cases the group held off until the ICU release. **Conclusion: ICU should be released by the next meeting, so revisit then.**

## Normative: Read date-time options only once when creating DateTimeFormat objects

- proposal: [ecma402#709](https://github.com/tc39/ecma402/pull/709)

[FYT](../../people/FYT.md) noted the change passes test262 as-is but is an observable behaviour change that could break web compatibility. [RGN](../../people/RGN.md) considered it necessary and suggested usage counters; [FYT](../../people/FYT.md) asked to list the affected test262 tests to look for red flags, and [RGN](../../people/RGN.md) agreed to do that and work on the test changes (using engine262). [EAO](../../people/EAO.md) and [YSZ](../../people/YSZ.md) supported. **Conclusion: review the test262 impact; further discussion is not necessary in this group unless red flags show up. Approved with conditions.**

## Intl Enumeration API for Stage 4

- proposal: [proposal-intl-enumeration](https://github.com/tc39/proposal-intl-enumeration)

[FYT](../../people/FYT.md) presented. [SFC](../../people/SFC.md) asked how the three open issues affect Stage 4: #39 (default fallbacks should simply be ignored from the enumerated list) has no contradiction and could be closed or tagged editorial, and #37 has a PR (#43) that adds the word "canonical". [PFC](../../people/PFC.md) and [SFC](../../people/SFC.md) disagreed on taking the PR to plenary, and [SFC](../../people/SFC.md) argued none of the issues block Stage 4 and suggested continuing offline. Merging #43 was accepted, with [YSZ](../../people/YSZ.md), [EAO](../../people/EAO.md) and [DLM](../../people/DLM.md) agreeing. **Conclusion: merge PR #43 and go to Stage 4, then work on the 3 remaining issues.**

## Intl Locale Info API for Stage 4

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#62](https://github.com/tc39/proposal-intl-locale-info/issues/62), [proposal-intl-locale-info#33](https://github.com/tc39/proposal-intl-locale-info/issues/33)

[FYT](../../people/FYT.md) presented. Issue #62 (getters return a different object each time): [RGN](../../people/RGN.md) wanted the same object returned; [SFC](../../people/SFC.md) noted the API is Stage 3 and already shipped in V8, so changes could affect implementations, and listed four options for plenary discussion (make it a function, leave it, return a frozen object, wait a year and return a Record/Tuple). [EAO](../../people/EAO.md) suggested leaving it and waiting for Records. Issue #33 (no preference data for collations): [RGN](../../people/RGN.md) and [SFC](../../people/SFC.md) favoured alphabetical order like time zones, dropping the API was considered but not pursued. [DLM](../../people/DLM.md) said Mozilla's implementation is half landed and awaiting further feedback. [FYT](../../people/FYT.md) said Stage 4 no longer felt comfortable and moved the agenda slot. **Conclusion: delay Stage 4 advancement and wait for Mozilla feedback; meanwhile fix the alphabetical sort.**

- proposal: [proposal-intl-messageformat#16](https://github.com/tc39/proposal-intl-messageformat/pull/16), [proposal-intl-message-resource](https://github.com/eemeli/proposal-intl-message-resource)

[EAO](../../people/EAO.md) discussed splitting resource parsing out of the MessageFormat proposal. [SFC](../../people/SFC.md), [DLM](../../people/DLM.md), [RCA](../../people/RCA.md) and [YSZ](../../people/YSZ.md) supported; [YSZ](../../people/YSZ.md) asked whether the resource format itself would be specified, and [EAO](../../people/EAO.md) said that is being done in Unicode. **Conclusion: approved message resources for Stage 1, split from the main proposal.**

## Can we rename proposal-intl-temporal?

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [FrankYFTang/proposal-intl-temporal](https://github.com/FrankYFTang/proposal-intl-temporal)

[PFC](../../people/PFC.md) (with [RCA](../../people/RCA.md)) suggested a new name to avoid confusion with [Temporal](../../proposals/temporal.md) and unnecessary questions in TG1, since the proposal also serves `DateTimeFormat`. [FYT](../../people/FYT.md) explained the core is the era for each calendar and the meaning of each month, intended as a minimal spec to close a gap that blocks [Temporal](../../proposals/temporal.md) implementation. [SFC](../../people/SFC.md)'s "intl-calendar-proposal" was thought too large in scope; [PFC](../../people/PFC.md) proposed `intl-era-and-month-codes`, and [FYT](../../people/FYT.md), [RCA](../../people/RCA.md) and [SFC](../../people/SFC.md) agreed. **Conclusion: approved the change of name to proposal-intl-era-and-month-codes.**
