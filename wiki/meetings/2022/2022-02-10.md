## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). TG2 gave "consensus for Stage 1" to [Intl.MessageFormat](../../proposals/intl-messageformat.md) after [EAO](../../people/EAO.md)'s presentation, discussed localized Temporal calendar and time zone names with [PFC](../../people/PFC.md) and [JGT](../../people/JGT.md), agreed to defer the eras-sequence issue to a bigger calendar-display or date-picker proposal, and agreed to extend the Temporal Annex for property-bag `calendar` and `timeZone` in `toLocaleString()` options. The editors' update noted Intl.Segmenter moving to Stage 4.

## Editor's Update

[USA](../../people/USA.md): Updates Intl.Segmenter to Stage 4.

## MessageFormat Working Group

[RCA](../../people/RCA.md) reported weekly Extended meetings covering aliases/macros, message references versus aliases, XLIFF compatibility, the function registry, case selection, UI elements, metadata and comments, and the container format (message-format-wg#220 and #221 for the previous summary and next agenda). [EAO](../../people/EAO.md) added that feedback from CLDR-TC about the MFWG proposals should help unblock progress, and that more frequent meetings are expected to speed it up.

## Temporal Presentation

[PFC](../../people/PFC.md) presented slides on Temporal. [USA](../../people/USA.md) asked whether localized representations of time zone names and calendars (as DisplayNames enabled) were wanted, and a `toLocaleString` on the Temporal prototype. [JGT](../../people/JGT.md) noted that time zone display names depend on the instant (standard versus daylight time), so a `TimeZone` `toLocaleString` needs context that a calendar does not; [SFC](../../people/SFC.md) added that DisplayNames v2 had already dropped the idea over complexity, that ECMA-402 already has extensive time zone name options from the extend-timezone-name proposal, and that a time zone has no canonical display name (CLDR's "exemplar city" names are not carried because of data size and no compelling use case). [USA](../../people/USA.md) saw calendars as the simpler case with likely support for `toLocaleString`. [PFC](../../people/PFC.md) offered to open a Temporal v2 issue laying out the complexity; [JGT](../../people/JGT.md) and [PFC](../../people/PFC.md) agreed that this should be a follow-on rather than part of the Stage 3 proposal, and [USA](../../people/USA.md) clarified no change to Temporal was being proposed right now.

## Accessing the sequence of eras of a calendar #598

- proposal: [ecma402#598](https://github.com/tc39/ecma402/issues/598)

[LAF](../../people/LAF.md) explained that eras are not sequential in the same way across calendars (the Japanese calendar in particular), so neither numeric era indexes nor a plain array works everywhere. [JGT](../../people/JGT.md) summarised two sub-questions: enumerating eras for a dropdown (still open) and numeric indexes for eras (decided against in Temporal). [USA](../../people/USA.md) recalled consensus against numeric identifiers; [SFC](../../people/SFC.md) asked to start from the use case, such as what is needed to build an Intl-aware date picker. **Conclusion: Revisit this issue as part of a bigger proposal about calendar display names or datetime picker components.**

## In .toLocaleString() options, property-bag form of calendar and timeZone will throw #2005

- proposal: [proposal-temporal#2005](https://github.com/tc39/proposal-temporal/issues/2005)

[JGT](../../people/JGT.md) introduced the issue: `DateTimeFormat` should accept Temporal `calendar` and `timeZone` objects (property-bag form) in options. [SFC](../../people/SFC.md) had discussed it in the Temporal Champions meeting and supported it; [YSZ](../../people/YSZ.md) and [GPT](../../people/GPT.md) were fine with it, [GPT](../../people/GPT.md) noting the added overhead but accepting the coupling to Temporal. **Conclusion: [JGT](../../people/JGT.md): We will extend the Temporal spec annex to support this, given the consensus here.**

## Editorial: refactor intl spec #1928

- proposal: [proposal-temporal#1928](https://github.com/tc39/proposal-temporal/pull/1928)

[USA](../../people/USA.md) described the PR as part of a bigger effort on non-Gregorian calendars, specifying the Intl-specific operations (is a month code a string, is the month a 1-based integer, and so on) as a first step toward documenting calendar-specific facts such as eras and where they start, with sources shared between Temporal and ICU4X. [JGT](../../people/JGT.md) separated the all-calendar behaviour in this PR from calendar-specific behaviour, which is out of scope. [LAF](../../people/LAF.md) asked which calendars should be supported (Unicode lists several Muslim calendars but no Julian calendar), and [USA](../../people/USA.md) was open to collaborating on that. **Conclusion: Continue to address comments and questions on the issue.**

## Intl.MessageFormat for Stage 1

- wiki: [Intl.MessageFormat](../../proposals/intl-messageformat.md)
- slide: [link](https://docs.google.com/presentation/d/1oThTeL_n5-HAfmJTri-i8yU2YtHUvj9AakmWiyRGPlw/edit)

[EAO](../../people/EAO.md) presented. [SFC](../../people/SFC.md) asked about the number of new primordials (Temporal added seven) and suggested Records and Tuples for data-focused classes; [EAO](../../people/EAO.md) replied that the proposal has only two primordial classes, `MessageFormat` and `MessageResource`. [SFC](../../people/SFC.md) also asked why the resource should be mutable given that Intl objects are immutable; [EAO](../../people/EAO.md) explained that `MessageFormat` builds on user data and that adding resources after construction (as in Firefox) lets an unhandled message be resolved later without reconstructing the instance. [JGT](../../people/JGT.md) asked how date-time formatting would map onto Temporal types, to which [EAO](../../people/EAO.md) answered that it is still to be decided. [SFC](../../people/SFC.md), [USA](../../people/USA.md), [LAF](../../people/LAF.md) and [YSZ](../../people/YSZ.md) supported Stage 1; [YSZ](../../people/YSZ.md) noted much remained to be worked out (syntax and more) before Stage 2, and [SFC](../../people/SFC.md) called it probably the biggest discussion of the year. **Conclusion: We have consensus for Stage 1 and add this for upcoming TC39 meetings.**

## Should we consider hiding lower-power fields in scope? #7

- wiki: [eraDisplay option for Intl.DateTimeFormat](../../proposals/intl-eradisplay.md)
- proposal: [proposal-intl-eradisplay#7](https://github.com/tc39/proposal-intl-eradisplay/issues/7)

[LAF](../../people/LAF.md) introduced the issue. [JGT](../../people/JGT.md) said hiding the era in the default (the "CE" case) is the priority and that a straightforward workaround exists for the general case; [USA](../../people/USA.md) noted that special-casing the era is not unusual. [SFC](../../people/SFC.md) and [GPT](../../people/GPT.md) worried about implementation cost, since `DateTimeFormat`'s constructor corresponds to a single pattern and supporting several patterns would add complexity; [GPT](../../people/GPT.md) and [JGT](../../people/JGT.md) preferred a workaround for now. **Conclusion: Focus on solving the eras issue and look into the general case in further detail in future.**
