## Overview

## Meta: Clarify the layering relationship between ECMA-262 and ECMA-402

- proposal: [ecma402#690](https://github.com/tc39/ecma402/pull/690)

[RGN](../../people/RGN.md) explained the PR: ECMA-262 is purely additive, nothing permitted by 402 is prohibited or constrained by 262, and nothing required by 402 is incompatible with the implementation freedom 262 allows. It matters for agreeing on the default time zone and on which time zones and calendars a 262-only implementation may allow (402 constraints such as the IANA list or CLDR calendars should be mirrored in 262). [SFC](../../people/SFC.md) saw it as a model for modular specs, with Temporal a possible parallel. [RCA](../../people/RCA.md) and [LAF](../../people/LAF.md) supported. **Conclusion: consensus on #690.**

## Clarification on what "precision" means in roundingPriority: morePrecision/lessPrecision #96

- proposal: [proposal-intl-numberformat-v3#96](https://github.com/tc39/proposal-intl-numberformat-v3/issues/96)

[PFC](../../people/PFC.md)'s issue ([SFC](../../people/SFC.md) called it a proposal by "Philip") describes surprising behaviour where an explicit minimum significant digits causes fraction digits to be ignored, so a value expected to format as `1.00` formats as `1.0`; the proposed fix changes the basis on which the conflict is resolved. [SFC](../../people/SFC.md) liked the model but weighed it against changing a Stage 3 proposal; the change would need a spec change and an ICU 72 change. [FYT](../../people/FYT.md) was slightly in favour and [RCA](../../people/RCA.md) in favour but wary of the impact; there was no opposition. **Conclusion: [SFC](../../people/SFC.md) to draft the normative change, implement it in ICU, check that it works with compact notation, and then request review.**

## CollationsOfLocale() order #33

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#33](https://github.com/tc39/proposal-intl-locale-info/issues/33)

[SFC](../../people/SFC.md) restated the long-running question of what order `getCollations()` should return. The four options were: default first with the rest implementation-defined in descending preference; default first with the rest deferred to UTS 35; default first with the rest lexicographic; or everything lexicographic. [SFC](../../people/SFC.md) noted that `Intl.Collator` does not accept `"standard"` and `"search"` as collation values (it uses `usage`), whereas UTS 35 does, that `"default"` is allowed by ECMA-402 though `en-u-co-default` is not valid in UTS 35, and favoured reverting PR #36 and putting a `"default"` entry first, which [SFC](../../people/SFC.md) logged on #33. CCN asked to avoid implementation-dependent behaviour and [YSZ](../../people/YSZ.md) had no strong opinion. **Conclusion: no solid conclusion; odd that ECMA-402 differs from UTS 35; see whether a value can be prepended to the list to indicate the default collation.**

## Intl.Segmenter with URLs, email addresses, and acronyms #656

- proposal: [ecma402#656](https://github.com/tc39/ecma402/issues/656)

[FYT](../../people/FYT.md) said Chromium carries an old patch that breaks differently from the Unicode default rules. [RGN](../../people/RGN.md) observed that ECMA-402 defers to Unicode, and the default rules (WB6 and WB7 in UAX #29) do not allow a break inside a domain name, so [SFC](../../people/SFC.md) agreed it is a Chrome bug. [RCA](../../people/RCA.md) took the action to add a test262 test, and [RGN](../../people/RGN.md) offered to suggest an explanatory note near WB6 in UAX #29 to the Unicode editors. **Conclusion: this needs to be fixed in V8, not a spec bug; [RGN](../../people/RGN.md) to write up a note for TR29.**
