## Time Zone Canonicalization

[JGT](../../people/JGT.md) recapped the problems (implementations diverge, e.g. `Europe/Kiev` in Chrome and Safari versus `Europe/Kyiv` in Firefox; `===` comparison of IDs breaks code when canonical IDs change) and the design: stop canonicalizing IDs the user provided, add a `Temporal.TimeZone.prototype.equals`, and plan to ask for Stage 2 at the upcoming TG1 meeting. On whether `resolvedOptions().timeZone` should be canonicalized, [SFC](../../people/SFC.md), [EAO](../../people/EAO.md) and [RGN](../../people/RGN.md) favoured case-normalization only, and [FYT](../../people/FYT.md) was fine with it while doubting the distinction will be clear to developers; [FYT](../../people/FYT.md)'s per-object memory concern was answered by [RGN](../../people/RGN.md) and [JGT](../../people/JGT.md) (about 10 bits per object, already needed by the existing time zone slot), and [RGN](../../people/RGN.md) and [EAO](../../people/EAO.md) discussed the "canonical"/"ID" terminology, with [JGT](../../people/JGT.md) to consider an issue on naming. For `DefaultTimeZone` when the OS ID differs from the engine's canonical ID, [EAO](../../people/EAO.md) wanted the spec to say only that a returned ID must be accepted as input; [SFC](../../people/SFC.md) preferred consistency across environments per engine version, while [YSZ](../../people/YSZ.md) preferred consistency with the platform (JSC has no problem here today, and a hard-coded list would regress iOS). [JGT](../../people/JGT.md) proposed, and [EAO](../../people/EAO.md) accepted with the caveat of checking Android's two-year timeframe, that the spec gives high-level recommendations, states this is implementation-defined, and warns developers not to assume equal values across engines. On when engines should adopt new canonical IDs (Firefox follows IANA immediately, V8 and Safari follow ICU and never change), [SFC](../../people/SFC.md) sketched three phases (old ID canonical with alias known, OS returns different values, new ID canonical) with no strict normative timing and [EAO](../../people/EAO.md) agreed; [FYT](../../people/FYT.md) questioned the benefit and enforceability, and [YSZ](../../people/YSZ.md) asked about separating ID from string form. [SFC](../../people/SFC.md) advised putting the proposal on the TG1 agenda before the next day's deadline. [JGT](../../people/JGT.md)'s closing list of normative changes includes the `equals` method, case-normalising instead of canonicalizing before storing slots, and removing the canonicalization requirement from `DefaultTimeZone`. It also reads "Also canonicalize in resolvedOptions().timeZone", which the notes do not explain against the discussion above.

## Add support for -u-fw and other Unicode extensions that could impact the result

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal-intl-locale-info#68](https://github.com/tc39/proposal-intl-locale-info/issues/68)

[FYT](../../people/FYT.md) hesitated to change a Stage 3 proposal, since supporting `-u-fw` means listing extension keywords, adding a getter, and reading a `firstDayOfWeek`-style option like `hourCycle`. [FYT](../../people/FYT.md) expected to manage a PR by July rather than May, ideally at the in-person meeting in Bergen; [YSZ](../../people/YSZ.md) said integrating it in June or July is fine and implementation would follow later. **Conclusion: Plan to propose it as normative PR in July.**

## Intl.supportedValuesOf('timeZone') for UTC, Etc/GMT\*, and other non-contintent/non-ocean time zone identifiers #778

- proposal: [ecma402#778](https://github.com/tc39/ecma402/issues/778)

[JGT](../../people/JGT.md) asked what `supportedValuesOf` should return for non-location time zones; it currently returns only canonical IDs, since the main use case is a dropdown where `Europe/Kiev` and `Europe/Kyiv` should not both appear. [SFC](../../people/SFC.md) felt `UTC` and `Etc/GMT*` should be returned but not the other unusual zones (which [EAO](../../people/EAO.md) described as names like Eastern European Time), and [FYT](../../people/FYT.md) asked about half-hour offsets. [JGT](../../people/JGT.md) replied that half-hour zones do not exist under `Etc/`, which covers areas not under any country's jurisdiction. [SFC](../../people/SFC.md) wanted any agreed invariant written into the spec but the group was out of time.
