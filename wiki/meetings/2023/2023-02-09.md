## Overview

Co-moderated by [SFC](../../people/SFC.md). Main outcomes: the group agreed that implementations may differ on `usage: "search"` versus `"sort"` collation data (ecma402#256) and that this should be documented in prose; the MessageFormat WG reported its error-handling design and asked how much alignment is wanted on built-in formatters (skeleton strings versus options bags); a long user-preferences discussion on privacy and "buckets" of preferences; and a first TG2 discussion of how `Temporal.ZonedDateTime` should interact with `Intl.DateTimeFormat`, with no agreement yet. [USA](../../people/USA.md), [PFC](../../people/PFC.md) and [JGT](../../people/JGT.md) spoke but are not in the attendee list. In the notes, `PCO` (one speaker line in the Temporal discussion) is a typo for [PFC](../../people/PFC.md).

## MessageFormat Working Group

[EAO](../../people/EAO.md) reported that the MessageFormat WG merged a section on error handling: formatting something that cannot be formatted no longer throws, but returns a best-effort approximation and reports the error through a side channel, which influences what an `Intl.MessageFormat` API may look like. [EAO](../../people/EAO.md) then asked how much shared surface is wanted between implementations for the built-in formatters, noting that ICU formatters take skeleton strings while the JavaScript preference is options bags. [USA](../../people/USA.md) said Bloomberg relies heavily on skeletons, but that ECMAScript deliberately favours options bags for developers new to i18n, and that Bloomberg's case is niche enough that conversion would be acceptable. [SFC](../../people/SFC.md) pointed out that skeletons convert to options bags (pattern strings do not). [EAO](../../people/EAO.md) said that without skeleton support in JavaScript they would keep working on bringing MessageFormat to JS without skeleton strings, and offered two libraries that convert date/time skeletons to options bags.

## What should happen with the usage: "sort" vs "search" choice in implementations? #256

- proposal: [ecma402#256](https://github.com/tc39/ecma402/issues/256)

[HJS](../../people/HJS.md) argued that ECMA-402 has no substring-search API, so the `search` collation data (kept in Firefox's data set, unlike Chrome and Safari which use collator-based find-in-page) has little demonstrable use beyond whole-string matching, mainly German, Finnish, Swedish, Catalan and archaic Hangul differences. [FYT](../../people/FYT.md) countered that usage of a locale is not a good criterion and that the spec already makes sort and search data implementation-defined; MWS explained that search tailorings are designed for equality rather than ordering. [YSZ](../../people/YSZ.md) said that if the data is unwanted the venue is CLDR. [SFC](../../people/SFC.md) asked whether an implementation may return the regular collation for `search` and proposed recording that differences are acceptable and documenting the intended use (spec or MDN); [BAN](../../people/BAN.md), MWS, [EAO](../../people/EAO.md), [YSZ](../../people/YSZ.md), [LAF](../../people/LAF.md) and [RCA](../../people/RCA.md) agreed. [HJS](../../people/HJS.md) opposed adding new API (such as [FYT](../../people/FYT.md)'s suggested equality method) merely because the data exists. **Conclusion: proceed as [SFC](../../people/SFC.md) suggested (implementations may differ; document what `usage` is for, e.g. on MDN).**

## User Preferences #580 and #409

[RCA](../../people/RCA.md) reported two follow-ups from the previous meeting: sequencing (return only values the user explicitly changed, after checking privacy settings) and separating preferences into buckets. Two buckets were proposed, Date/Time and Language/Region, delivered through Client Hints such as a Locale-Preferences-LanguageRegion header with a similar JavaScript API. [YSZ](../../people/YSZ.md) said Apple will not adopt anything that adds a fingerprinting vector without user consent, and asked how consent would work for request headers; [RCA](../../people/RCA.md) promised to confirm the flow. [HJS](../../people/HJS.md) questioned relying on Chrome's high-entropy hints and its privacy budget (not explicit consent), and asked who the use cases are for and how many people are driven by en-US being an untranslated default with unusual units and hour cycle. [SFC](../../people/SFC.md) stated the goal (let web apps use settings that native apps already get, instead of guessing from `Accept-Language`) and asked for end-user-experience clarity; [USA](../../people/USA.md) said a navigator getter is possible if implementers prefer it, and described en-IN as a case where many users override defaults. [SFC](../../people/SFC.md) suggested revisiting monthly, with documented answers to [HJS](../../people/HJS.md) and [YSZ](../../people/YSZ.md)'s questions as the goal for the next meeting. No conclusion was recorded.

## Temporal issues: #2479 prevent loss of TimeZone information

- proposal: [proposal-temporal#2479](https://github.com/tc39/proposal-temporal/pull/2479)

[PFC](../../people/PFC.md) explained that `Temporal.ZonedDateTime` formatting ignored the object's own time zone because of a spec oversight, and framed three questions (via [JGT](../../people/JGT.md)): should optionless `ZonedDateTime.prototype.toLocaleString()` and optionless `Intl.DateTimeFormat.prototype.format(zdt)` use the ZDT's time zone, and how a conflicting `timeZone` option is handled. [FYT](../../people/FYT.md) wanted to block the PR as written because the same `DateTimeFormat` could produce different time zones, violating its construct-time resolution, and raised implementation cost. For `toLocaleString`, the group converged on option 3: use the ZDT's time zone and throw if a `timeZone` option is provided, even one that matches ([SFC](../../people/SFC.md), [FYT](../../people/FYT.md), [JGT](../../people/JGT.md), [PFC](../../people/PFC.md); [USA](../../people/USA.md) preferred not erroring on an implicit case). For `DateTimeFormat.prototype.format`, [SFC](../../people/SFC.md) listed seven options (reject ZDT, require matching zones, use the ZDT's zone only when the DTF's zone is undefined, always use the ZDT's, always use the DTF's, add a constructor option, or add `Intl.ZonedDateTimeFormat`); [JGT](../../people/JGT.md) and [USA](../../people/USA.md) leaned to the third, [FYT](../../people/FYT.md) objected to it and to the fourth on consistency and performance grounds, and [SFC](../../people/SFC.md) found no option near consensus. **No conclusion was recorded; [SFC](../../people/SFC.md) said the list would be posted to the PR for follow-up.**
