## Overview

A dense agenda covering `Intl.Locale` open questions (full `-u` extension canonicalization, no default locale, grandfathered tags), a decision to drop the Segmenter `lw`/`ss` options for now, ICU tickets needed by the proposals, and three new-proposal decisions: the unified `NumberFormat` keeps the `style` option, `IntervalFormat` returns a flat `formatRangeToParts()` array and is exposed as `formatRange`, and `UnitFormat` is folded into the unified `NumberFormat`. Abbreviations are normalised to delegates.txt: SL → [SRL](../../people/SRL.md), CC → [CCN](../../people/CCN.md), FB → [FBN](../../people/FBN.md), and the names Shane → [SFC](../../people/SFC.md), Steven → [SRL](../../people/SRL.md), Dan → [DE](../../people/DE.md), Ciric → [NC](../../people/NC.md), Zibi → [ZB](../../people/ZB.md), Eemeli → [EAO](../../people/EAO.md), Caridy → [CP](../../people/CP.md), Felipe → [FBN](../../people/FBN.md), Jack → JH, Jungshik → JS, and Myles → [MCM](../../people/MCM.md) (inferred: the notes give only "Myles" and "Apple/Microsoft" in the same section). Jeff Genovy has no delegates.txt abbreviation and is written by name. [SFC](../../people/SFC.md), [CP](../../people/CP.md) and [MCM](../../people/MCM.md) speak but are not in the attendee list.

## Normative: Add calendar and numberingSystem options

- proposal: [ecma402#175](https://github.com/tc39/ecma402/pull/175)

The resolution recorded from the previous meeting was to validate the shape of the values but not the actual contents. [DE](../../people/DE.md) was working on test262, V8 and spec patches. **Conclusion: continue with this.**

## Segmenter: Should we add all the options (lw, ss), or just lb?

- wiki: [Intl.Segmenter](../../proposals/intl-segmenter.md)
- proposal: [proposal-intl-segmenter#23](https://github.com/tc39/proposal-intl-segmenter/issues/23)

JS was against `lw` (ICU does not really support it, and it needs part-of-speech data, which is not useful for Chinese and Japanese) and unsure about `ss`, whose exception list is only around 30 entries per language, so small. [SRL](../../people/SRL.md) found sentence suppressions useful (for example not splitting after "Dr." or "Mr.") but was wary that the spec might be too implementation-specific; [DE](../../people/DE.md) noted Intl has never passed down all the ICU keys. [ZB](../../people/ZB.md) asked what the problem is with adding options later, and [SRL](../../people/SRL.md) replied that this sounded like the path forward (no formal conclusion line; the effect is `lb` first, others later).

## Locale

- proposal: [proposal-intl-locale#14](https://github.com/tc39/proposal-intl-locale/issues/14), [proposal-intl-locale#15](https://github.com/tc39/proposal-intl-locale/issues/15), [proposal-intl-locale#12](https://github.com/tc39/proposal-intl-locale/issues/12), [ecma402#177](https://github.com/tc39/ecma402/issues/177)

Three issues were handled. For full Unicode extension canonicalization per RFC 6067 (#14) the notes answer "Yes", and JS asked whether a well-formed but unrecognised value would be dropped (No). For `Intl.Locale()` with an absent tag (#15) the discussion was between mapping `undefined` to the root locale and throwing; [NC](../../people/NC.md), [ZB](../../people/ZB.md) and [SRL](../../people/SRL.md) preferred that `Locale` be an identifier rather than a service that exposes the default locale, and everyone was fine with throwing. **Conclusion: keep the spec as is (throw, do not return defaults).**

On spec questions (#12), JH noted `caseFirst` is not supported in Windows globalization, which raised the broader question ([ZB](../../people/ZB.md)) of what is mandatory versus optional for compliance (an implementation lacking data might fall back to `en` for everything); [DE](../../people/DE.md) did not want to widen the surface of optionality, and this was continued offline. On regular and irregular grandfathered tags, [SRL](../../people/SRL.md) argued for mapping them to modern tags (transparently, as Java does with `he` → `iw`), [DE](../../people/DE.md) said this belongs in the `Intl.Locale` spec, applies wherever a locale is input and needs test262 tests, and [ZB](../../people/ZB.md) said grandfathered tags add complexity to SpiderMonkey. [SRL](../../people/SRL.md) took the lead and the group inclined to handle deprecated tags the same way.

## ICU tickets to support existing advanced proposals and APIs

- proposal: [ICU-13256](https://unicode-org.atlassian.net/browse/ICU-13256), [ICU-12936](https://unicode-org.atlassian.net/browse/ICU-12936), [ICU-13268](https://unicode-org.atlassian.net/browse/ICU-13268), [ICU-12756](https://unicode-org.atlassian.net/browse/ICU-12756)

Items discussed: `RelativeDateTimeFormatter` field-position output (ICU-13256; needed for `formatToParts`, to be raised in the ICU design meeting by [SRL](../../people/SRL.md), with JS noting parsing output is often broken), `-0` handling in `RelativeDateTimeFormatter` (ICU-12936; [SFC](../../people/SFC.md) thought it a 2-3 line change, owner pinged, [SRL](../../people/SRL.md) to add an ECMA label for JS-related tickets), `TimeZone::getOffset()` repeated/skipped wall time (ICU-13268; JS wrote a patch and would send an icu-design proposal), and supported locales for `PluralRules` (ICU-12756; [ZB](../../people/ZB.md) and [SRL](../../people/SRL.md): all locales are expected to support it; [EAO](../../people/EAO.md) noted ordinal rules are only "strongly recommended" in CLDR's minimal data). For APIs promoted to stable in ICU 61, Apple, Microsoft and Mozilla said they can only use ICU C APIs, so any new proposed API needs a C API, not just C++; action items were recorded for JS (file a timezone ticket) and for those three implementers (comment on [SFC](../../people/SFC.md)'s NumberFormat C API ticket ICU-13597). Other item: SpiderMonkey's feedback from merging ICU 61.

## NumberFormat changes

- proposal: [ecma402#215](https://github.com/tc39/ecma402/issues/215)

Two questions: whether to deprecate the `style` option (Option 1) or keep it first-class (Option 2), and whether unit modifiers go top-level (Option A) or nested under the unit key (Option B). People generally liked top-level (A). [SFC](../../people/SFC.md) said Google design meetups favoured dropping `style` but that keeping it made sense given the arguments from [EAO](../../people/EAO.md) (library authors need `style`; an ignored currency without `style` is surprising but a "middle ground" could relax that), [ZB](../../people/ZB.md) (the explicit style lets someone state a preference without choosing), [CP](../../people/CP.md) (TC39 sticks with the status quo unless there is a significant improvement; several cases would break) and [DE](../../people/DE.md) (`style: currency` cannot change for web compatibility); JH added that percent is indicated only by `style`. [SFC](../../people/SFC.md) said that if `style: currency` stays, a `style: measure` would be wanted. **Conclusion: keep `style` (A 2, that is Option 2 plus top-level modifiers); naming details to follow once there is a draft spec.**

## IntervalFormat

- proposal: [ecma402#188](https://github.com/tc39/ecma402/issues/188)

[FBN](../../people/FBN.md) asked how `formatRangeToParts()` should represent tokens shared by the start and end dates. [CP](../../people/CP.md) recalled that `formatToParts` was designed so one can zip through the parts to reproduce `format`, which nesting would hinder; [ZB](../../people/ZB.md) wanted a pattern reusable for NumberFormat and preferred an extra field to nesting. **Conclusion: use a flat array with a new attribute marking which date (start/end) a part belongs to.** [FBN](../../people/FBN.md) also reported that an additional formatter versus a second `DateTimeFormat` method had been discussed and settled on `formatRange`; [SFC](../../people/SFC.md) liked it as a pattern for keeping option counts down.

## UnitFormat

- proposal: [proposal-intl-unit-format](https://github.com/tc39/proposal-intl-unit-format) ([ecma402#32](https://github.com/tc39/ecma402/issues/32))

Asked whether UnitFormat is still relevant given [SFC](../../people/SFC.md)'s proposal, the answer was no, except for list formatting. The question on API for compound units (such as 9.8 m/s^2) was noted as supported by NumberFormat. **Conclusion: UnitFormat is folded into the new "unified" NumberFormat; for a "list number format" (for example "10 meters and 35 centimeters") introduce a list format.**
