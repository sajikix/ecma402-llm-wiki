## Adopting Unicode BCP47 Locale Identifiers

- proposal: [ecma402#289](https://github.com/tc39/ecma402/pull/289) (with [proposal-intl-locale#66](https://github.com/tc39/proposal-intl-locale/pull/66))

The question was whether the `Intl.Locale` constructor should enforce sorting of Unicode extension subtags. ICU has generally treated canonicalization as a separate step (for performance, passing `char*` strings from other APIs, and not mutating the input), but MWS and [SRL](../../people/SRL.md) said the ICU behaviour need not be carried forward, and since the constructor already mutates the input, sorting should be considered too. [DE](../../people/DE.md) asked whether that amounted to consensus and whether anyone had concerns about BCP 47 locale identifiers. On `zh-min` and other grandfathered tags, MWS noted it becomes `und-x-zh-min`, and [DE](../../people/DE.md) said the five grandfathered cases need a special check. [FYT](../../people/FYT.md) pointed out that the current canonicalized language tag section mentions both RFC 5646 and 6067 but says only "may"; [FYT](../../people/FYT.md) thought it should be "must", while [DE](../../people/DE.md) wanted to point to UTS 35 as well and thought many "may"s in the spec should change, which [FYT](../../people/FYT.md) preferred to decide case by case. [FYT](../../people/FYT.md) and [DE](../../people/DE.md) will continue in a subgroup; [FYT](../../people/FYT.md)'s two open items are canonicalization of grandfathered tags and the order of subtags. The agenda's question of shared work in ICU has no recorded discussion.

## Permit tailorings for case mapping

- proposal: [ecma402#291](https://github.com/tc39/ecma402/pull/291)

[DE](../../people/DE.md) reported that Andrej found the current wording ("use only the locale-insensitive parts of case mapping") is too restrictive: implementations pass the locale to case mapping (Turkish, Lithuanian and Greek differ), and the spec only allowed tailorings available in CLDR. [SRL](../../people/SRL.md) argued that CLDR should be an example source rather than a limit, as with the Unicode conformance clauses, and MWS added that ICU does not follow CLDR exactly (Greek uppercasing is hard to express in ICU transliterator rules). [DE](../../people/DE.md) recalled that people have previously asked the spec to be more specific rather than open. **Conclusion: be more general, allowing "CLDR or other tailorings", and look at putting this in the front matter as the Unicode standard does.** [SRL](../../people/SRL.md) filed [ecma402#299](https://github.com/tc39/ecma402/issues/299) to track it.

## BiDi note

- proposal: [ecma402#290](https://github.com/tc39/ecma402/pull/290)

[DE](../../people/DE.md) reported on a TPAC review by the W3C Internationalization WG, which raised concern that low-level APIs (such as `RelativeTimeFormat` without MessageFormat) can be used incorrectly, since formatters may need bidi marks or markup; [DE](../../people/DE.md) suggested Zibi's Project Fluent might become "MessageFormat version 2". [ZB](../../people/ZB.md) said that after over two years of using formatters in Firefox, no marks were needed as long as the message and the interpolated value use the same locale, and that handling belongs in the message localization system. [FYT](../../people/FYT.md) raised `ListFormat` for Urdu (the `unit` type uses a logical order), which [ZB](../../people/ZB.md) said could be handled with bidi marks in the pattern. [FYT](../../people/FYT.md), [FBN](../../people/FBN.md) and [ZB](../../people/ZB.md) preferred a high-level note rather than a warning on every call. **Conclusion: add a general note to the Intl module (with the W3C inline bidi markup article as reference); [DE](../../people/DE.md) will follow up with a patch.** [ZB](../../people/ZB.md) asked for the Urdu example to be posted in the issue.

## Intl.ListFormat

- proposal: [proposal-intl-list-format](https://github.com/tc39/proposal-intl-list-format)

**Locales without "or" data** ([issue #34](https://github.com/tc39/proposal-intl-list-format/issues/34)): some locales have no "or" data in CLDR and fall back to root. [FYT](../../people/FYT.md) called it an implementation detail and a chicken-and-egg problem (no one uses "or" data, so no one provides it), and noted that Ecma 402 does not define a minimum set of locales. [ZB](../../people/ZB.md) suggested two actions: require coverage for an implementation to claim a locale in `ListFormat`, and ask Unicode whether data providers could always provide "and" and "or" together. [SRL](../../people/SRL.md) said "or" is in CLDR "moderate" coverage and "and" in "modern", and that interested parties should sign up and provide data. [FYT](../../people/FYT.md) asked that the CLDR committee at least be signalled that Ecma 402 would like it, and [SFC](../../people/SFC.md), [FBN](../../people/FBN.md) and [DE](../../people/DE.md) agreed. [DE](../../people/DE.md) found [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md)'s points convincing and said the spec is already clear about the coverage point.

**Oxford comma** ([issue #31](https://github.com/tc39/proposal-intl-list-format/issues/31)): [MB](../../people/MB.md) expected the same problem in other locales. [SRL](../../people/SRL.md) said this should be a CLDR request and asked for a ticket on cldr.org; [SFC](../../people/SFC.md) asked how it would then reach Ecma 402, and [ZB](../../people/ZB.md) said that would be looked at later (perhaps a locale tag).

## Intl.Segmenter

- proposal: [proposal-intl-segmenter](https://github.com/tc39/proposal-intl-segmenter)

**`{granularity: "line"}` promotes reimplementing paragraph layout in script** ([issue #49](https://github.com/tc39/proposal-intl-segmenter/issues/49)): [MCM](../../people/MCM.md) wanted to discourage reimplementing CSS layout in JS and argued browsers should not have to carry the feature, with a library being the right home. [FYT](../../people/FYT.md), [SRL](../../people/SRL.md) and [DE](../../people/DE.md) gave use cases (WebGL text, email wrapping, plain-text editors, dot-matrix rendering, non-browser hosts), and [DE](../../people/DE.md) said the feature motivated by existing V8 usage should not be dropped and that segmentation data is too large to ship to the client. [MCM](../../people/MCM.md) agreed the only concern is misuse, but said "misuse" needs a shared understanding. **Conclusion (per [DE](../../people/DE.md)): follow up offline with more documentation and use-case investigation, and bring in the CSS Houdini people.**

**Do iteration results describe segments or breaks/boundaries?** ([issue #59](https://github.com/tc39/proposal-intl-segmenter/issues/59); related [issue #44](https://github.com/tc39/proposal-intl-segmenter/issues/44) on renaming `breakType` to `segmentType`): [SRL](../../people/SRL.md) said "segment" is the section of text and "break" the boundary; [RGN](../../people/RGN.md) noted Unicode defines both terms. [DE](../../people/DE.md)'s feeling was that iteration is over boundaries, and [MCM](../../people/MCM.md) noted that iterating over boundaries would need both start and end of the segment returned. [RGN](../../people/RGN.md): "rough consensus over making this an iterator over the boundaries", and [RGN](../../people/RGN.md) will follow up with a PR. [FYT](../../people/FYT.md) floated `boundaryType` as the name. [RGN](../../people/RGN.md) observed that line break is the only kind that associates properties with boundaries, and [SRL](../../people/SRL.md) found a word versus non-word distinction useful (for example, word counts).

[Remove state-exposing fields from %SegmentIteratorPrototype%](https://github.com/tc39/proposal-intl-segmenter/pull/57) and [Should segmentIterator.following(n) match a break position at n?](https://github.com/tc39/proposal-intl-segmenter/issues/52) were deferred to a future meeting.

## Intl.NumberFormat Unified Feature Proposal

- proposal: [proposal-unified-intl-numberformat](https://github.com/sffc/proposal-unified-intl-numberformat)

The agenda marks this "For Stage 3 in November!". A new CLDR spec for "core unit identifiers" removes the type prefix from unit identifiers and enables custom compound units.

**Fallback behavior for measure units** ([issue #11](https://github.com/tc39-transfer/proposal-unified-intl-numberformat/issues/11)): [SFC](../../people/SFC.md) asked whether, with no type prefix, the unit string can be echoed verbatim like currency codes. [FBN](../../people/FBN.md) and [DE](../../people/DE.md) thought the string is not good enough and that internals should not be exposed, and [SRL](../../people/SRL.md) said an unknown unit differs from the "or" pattern case, where the pattern is known but coverage is incomplete. [SRL](../../people/SRL.md) added that silently falling back would require reporting it in `resolvedOptions`. **Conclusion (per [SFC](../../people/SFC.md)): consensus is to keep throwing an exception for unknown units.**

## Additional Locale features (overflow)

The overflow list was discussed. These items were covered:

- [Intl.getParentLocales](https://github.com/tc39/ecma402/issues/87): [ZB](../../people/ZB.md) said the original motivation was resolved because likely subtags (part of `Intl.Locale`) enabled Firefox's locale negotiation, and [FYT](../../people/FYT.md) saw no need to expose it to JavaScript. **Conclusion: deprioritise.**
- [Directionality of scripts](https://github.com/tc39/ecma402/issues/205): [DE](../../people/DE.md) asked whether CSS logical properties suffice; [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md) said script directionality data is needed (companies otherwise hard-code Arabic and Hebrew lists), and [FYT](../../people/FYT.md) said it is "definitely needed".
- [First day of the week](https://github.com/tc39/ecma402/issues/6): [ZB](../../people/ZB.md) said calendar widgets need it, along with when the weekend starts and ends.

## Casing in options

[SFC](../../people/SFC.md) asked whether option string values should be camelCase or kebab-case, citing `currencyDisplay: "narrowSymbol"` versus `"narrow-symbol"`. [DE](../../people/DE.md) and [MB](../../people/MB.md) said keys are camelCase and string values should be kebab-case, the general web convention. **Conclusion: [SFC](../../people/SFC.md) will make that change in the Unified `NumberFormat` spec proposal** ([issue #22](https://github.com/tc39-transfer/proposal-unified-intl-numberformat/issues/22)).
