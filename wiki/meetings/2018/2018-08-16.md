## Overview

The notes are a numbered outline and the attendee list is empty, so `attendees` is derived from who speaks. Abbreviations are normalised to delegates.txt: SC → [SFC](../../people/SFC.md), SL → [SRL](../../people/SRL.md), FB → [FBN](../../people/FBN.md), JW → [JSW](../../people/JSW.md), SG → SGN (Sathya Gunasekaran, inferred from the 2018-09-20 attendee list, where `SG` also speaks), and "Romulo" → [RCA](../../people/RCA.md). The meeting is an implementation and issue round for the Stage 3 APIs (`Intl.Locale`, `Intl.RelativeTimeFormat`, `Intl.ListFormat`), plus two Stage 2 proposals: Unified `Intl.NumberFormat` (two issues settled) and `formatRange` (kept as specified). Also covered: `Intl.DisplayNames` (deferred until the champion can attend), Temporal's Intl support, a MessageFormat update from [ZB](../../people/ZB.md), and how TG2 should communicate and liaise with Unicode. Items on the agenda with no recorded discussion (PRs against ECMA-402, `Intl.Segmenter`, the W3C i18n WG, the overflow list) are omitted.

## Intl.RelativeTimeFormat

- proposal: [proposal-intl-relative-time](https://github.com/tc39/proposal-intl-relative-time)

**Review handling of "narrow" style** ([issue #88](https://github.com/tc39/proposal-intl-relative-time/issues/88)): SGN thought the effective style should show up in `resolvedOptions`, while [ZB](../../people/ZB.md) noted it cannot be verified which format was taken. [SRL](../../people/SRL.md) said missing data is a CLDR error and that the CLDR root locale should alias `short` from `narrow`, which would make the problem disappear; [ZB](../../people/ZB.md) added that some locales have no distinct short form, so `narrow` equals `short` there. **Conclusion: file a bug in CLDR if needed, and close the issue as working as intended.**

Implementation status: the underlying ICU API (ICU-13256) is not yet available. [DE](../../people/DE.md) was unsure when to do it, [SRL](../../people/SRL.md) pointed out that with ICU's move to GitHub anyone can open a PR, and [FBN](../../people/FBN.md) said a colleague had implemented `RelativeTimeFormat` in V8 with a workaround (`ListFormat` needs the ICU change). SpiderMonkey was two test262 tests from done but has no `formatToParts`; V8 was complete except `formatToParts`, waiting on an ICU bug (ICU-12171) that [SRL](../../people/SRL.md) said still had open design questions from 2016. A test262 bug with Polish and a short/narrow test bug (test262#1681) both had fixes under review.

## Intl.ListFormat

- proposal: [proposal-intl-list-format](https://github.com/tc39/proposal-intl-list-format)

**Handling partial support of options in data files** ([issue #16](https://github.com/tc39/proposal-intl-list-format/issues/16)): [JSW](../../people/JSW.md) suggested starting with `RangeError` for the combinations that lack data and extending later. [DE](../../people/DE.md) spelled this out as throwing when `narrow` is used without `unit`, [SRL](../../people/SRL.md) agreed and wanted developers told to use `short` in that case (possibly in the `RangeError` message or a CLDR spec sentence). **Conclusion: throw a `RangeError` on `narrow` combined with `conjunction`/`disjunction`.**

V8 was done apart from ICU bugs (including the FieldPositionIterator work in ICU-13754); [SFC](../../people/SFC.md) noted ICU's move to GitHub lowers the bar for contributing patches. SpiderMonkey had a first-iteration patch.

## Intl.NumberFormat Unified Feature Proposal

- proposal: [proposal-unified-intl-numberformat](https://github.com/sffc/proposal-unified-intl-numberformat)

[SFC](../../people/SFC.md) brought two issues to the group. **Issue #11**: the spec holds a closed list of supported measure units, extended in sync with CLDR/ICU releases; unlisted units throw. [ZB](../../people/ZB.md) found this good. **Conclusion: go with that.** **Issue #9**: compact units get rounding behaviour that is not exposed in `resolvedOptions` and can be overridden with significant-digit or min/max fraction-digit options; only this case is special-cased, with no new API to set rounding on other types. **Conclusion: no concerns raised, go with that.**

[SFC](../../people/SFC.md) said these were the last changes needed; [DE](../../people/DE.md) suggested landing them for the next TC39 meeting and asking for Stage 3 reviewers, with a polyfill (as in Intl.js) as a useful but non-required step. The C API for NumberFormatter was a draft in ICU 62 and would be stable in ICU 64 (spring 2019). The notes open the Stage 2 section with "Congratulations on the results at TC39!" without naming the proposals or results.

## formatRange/formatRangeToParts

- proposal: [proposal-intl-DateTimeFormat-formatRange](https://github.com/fabalbon/proposal-intl-DateTimeFormat-formatRange)

**What happens when dates are the same? (#4)** The three options are listed in the issue rather than the notes; from the discussion, option 1 is the current spec and ICU behaviour and option 3 is an approximation pattern (a CLDR approximation symbol was planned for the fall release, at least for numbers). [ZB](../../people/ZB.md) first favoured option 2 (which cannot be built on top of option 1), and [DE](../../people/DE.md) wanted to stay minimal. The group was split, with [SFC](../../people/SFC.md) finding option 1 most intuitive; SGN proposed starting with option 1 and considering a flag for option 2 later, which persuaded [ZB](../../people/ZB.md). [FBN](../../people/FBN.md) noted ICU only does option 1 and any other behaviour needs an ICU change; [DE](../../people/DE.md) said TG2 does not follow ICU strictly. **Conclusion: keep the specification as is.**

Next steps: close the remaining issues, build a polyfill and head to Stage 3; SGN said the ICU API is needed before Stage 3 so the feature is implementable, so [FBN](../../people/FBN.md) would write an ICU proposal for date interval formatting. Asked by Romulo how a same-date, different-time range looks, [FBN](../../people/FBN.md) said what is shown is controlled by the options bag.

## Intl support for Temporal

- proposal: [ecma402#254](https://github.com/tc39/ecma402/issues/254)

The linked Temporal issue is that its date-time cycle is very specific (Gregorian, midnight, 24-hour). [SRL](../../people/SRL.md) suggested setting the fields from the Temporal object directly into an ICU calendar object instead of using a fractional-seconds value. [DE](../../people/DE.md) invited anyone interested to get in touch.

## MessageFormat (and Romulo's effort)

- wiki: [Intl.MessageFormat](../../proposals/intl-messageformat.md)

[ZB](../../people/ZB.md) gave an update: the only existing format TG2 would consider is ICU MessageFormat, but based on experience at Mozilla "we'd be reluctant to choose that". Mozilla has been developing Fluent (in Firefox since January for DOM and React UI, with a 1.0 to be presented at the Unicode conference the following month, syntax at 0.7), and Mark Davis reported interest in a "MessageFormat 2.0" at Unicode, to be discussed from September; [ZB](../../people/ZB.md) hoped that could ground ECMA-402 standardisation once it is standardised at Unicode. Romulo ([RCA](../../people/RCA.md)) had positive impressions of Fluent but wanted to try it. [ZB](../../people/ZB.md) also pointed to Facebook's FBT, expected to be open-sourced soon. No conclusion recorded.
