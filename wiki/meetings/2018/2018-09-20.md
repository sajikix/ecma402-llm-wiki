## Overview

The notes are a numbered outline and list five attendees ([DE](../../people/DE.md), SGN, [SFC](../../people/SFC.md), NC, [EAO](../../people/EAO.md)). [FBN](../../people/FBN.md), [JSW](../../people/JSW.md) and "Romulo" ([RCA](../../people/RCA.md)) also speak but are not in the attendee list, and `attendees` includes them. Abbreviations are normalised to delegates.txt: SC → [SFC](../../people/SFC.md), SG → SGN, FB → [FBN](../../people/FBN.md), JW → [JSW](../../people/JSW.md), "Eemeli" → [EAO](../../people/EAO.md), "Romulo" → [RCA](../../people/RCA.md). The meeting is an implementation round for the Stage 3 APIs (`Intl.Locale`, `Intl.RelativeTimeFormat`, `Intl.ListFormat`, `Intl.Segmenter`) plus the Stage 2 proposals. Outcomes: duplicate unicode extension keys will not throw; Unified `Intl.NumberFormat` keeps its `style`-driven options handling, and [SFC](../../people/SFC.md) plans to ask for Stage 3 at the November plenary; `formatRange` is now targeting Stage 3 in January. The meeting also covered `dateStyle`/`timeStyle`, `Intl.DisplayNames`, Intl support for [Temporal](../../proposals/temporal.md), a Globalize.js-based polyfill idea, and whether TG2 needs a chat channel.

## Duplicate tags?

- proposal: [ecma402#262](https://github.com/tc39/ecma402/issues/262)

Whether duplicate subtags in a language tag should throw. NC favoured throwing; [DE](../../people/DE.md) noted the specification allows it and the interpretation is unambiguous (the last one wins). SGN was fine either way, since the bigger problem is letting ICU do the parsing, and the related ICU issue (ICU-20140) has been fixed. **Conclusion: do not throw.**

## Intl.Locale

- proposal: [proposal-intl-locale](https://github.com/tc39/proposal-intl-locale)

A new ChakraCore implementation (ChakraCore#5675) was announced. SGN said the tests look good after bugs filed against the ChakraCore implementation were fixed. On ICU as a backing implementation: SGN said ICU cannot validate subtags (a problem V8 faces now; SpiderMonkey uses its own parser). NC and [SFC](../../people/SFC.md) noted that ICU's subtag length limit was removed in the latest ICU push, along with other new APIs, and that the V8 side is still fixing bugs in `Intl.Locale` as they are found.

## Intl.RelativeTimeFormat

- proposal: [proposal-intl-relative-time](https://github.com/tc39/proposal-intl-relative-time)

No PRs were out for review. V8 has a full workaround for the missing ICU API (ICU-13256); [FBN](../../people/FBN.md) said `ListFormat` is the higher priority for the V8 side, and [JSW](../../people/JSW.md) took a look at the workaround, noting that using the C++ API directly is something they try to avoid but can do temporarily, as elsewhere. SGN reported that V8 passes all the test262 tests and that shipping in Chrome 71 is the goal. [DE](../../people/DE.md) suggested this might allow Stage 4 in November. NC asked about usage counters for the new APIs in Chrome; SGN said that is planned.

## Intl.ListFormat

- proposal: [proposal-intl-list-format](https://github.com/tc39/proposal-intl-list-format)

**Handling partial support of options in data files** ([issue #16](https://github.com/tc39/proposal-intl-list-format/issues/16)): the notes record the answer "Yes, throw". On implementations, the ICU API for `formatToParts` (ICU-13754) was contributed by Frank Tang; NC said the ICU code is somewhat complex and Markus is working through it, and [SFC](../../people/SFC.md) said a dependency issue was fixed and the C++ API has landed (the C API was not confirmed). SGN expects V8 to be quick but, because ICU changes only arrive when V8 branches for 71, hopes to ship in 72 (mid-November). [JSW](../../people/JSW.md) described Andre's patches as a first draft that uses the C++ API manually; NC warned that depending on a draft ICU API is risky. SGN found the spec and tests fine.

## Intl.NumberFormat Unified Feature Proposal

- proposal: [proposal-unified-intl-numberformat](https://github.com/sffc/proposal-unified-intl-numberformat)

[SFC](../../people/SFC.md) plans to prioritise a V8 implementation in Q4, understanding that Stage 3 needs an implementation. [DE](../../people/DE.md) corrected that there is no implementation requirement, and a polyfill is nice but not required. Discussion on a polyfill: NC called a polyfill throwaway work compared to a C++ implementation; SGN and [EAO](../../people/EAO.md) argued it increases adoption ([EAO](../../people/EAO.md): even an English-only polyfill is better than none), and [DE](../../people/DE.md) thought a high-quality polyfill, possibly built on Globalize.js, would be worthwhile.

**Throw exceptions more eagerly?** ([issue #16](https://github.com/sffc/proposal-unified-intl-numberformat/issues/16)): NC said the exception matrix becomes complicated and combinations add bugs. [SFC](../../people/SFC.md) compared it to unrelated properties in an options bag being ignored, and recalled that the earlier decision to keep `style` (rather than formatting as currency whenever `currency` is provided) rested on backwards compatibility and on [EAO](../../people/EAO.md)'s point that a locale options bag may carry a `currency` without wanting currency formatting. **Conclusion: keep things as is.** [SFC](../../people/SFC.md) will propose Stage 3 at the November plenary ([SFC](../../people/SFC.md) does not plan to attend the plenary the following week). [DE](../../people/DE.md) will ask for Stage 3 reviewers at the next plenary; SGN agreed to start tests in a branch if the test262 maintainers are fine with it.

## formatRange/formatRangeToParts

- proposal: [proposal-intl-DateTimeFormat-formatRange](https://github.com/fabalbon/proposal-intl-DateTimeFormat-formatRange)

[FBN](../../people/FBN.md) is focused on proposing and implementing an ICU `FieldPositionIterator` API for `DateTimeFormat`, probably needed before Stage 3. NC did not expect Stage 3 readiness in November, and SGN saw no point in advancing before it is implementable with ICU; [DE](../../people/DE.md) did not see this as a strict requirement. SGN accepted Stage 3 once the ICU work lands in trunk (not necessarily a release), and [FBN](../../people/FBN.md) estimated that would not complete until January. [SFC](../../people/SFC.md) pointed to ICU-20138 for field positions and to the `NumberRangeFormatter` in ICU 63 as a model for range collapse, noting that collapsing may need to be locale-specific while a locale-independent heuristic is a fine start. **Conclusion: January is the plan for Stage 3**; tests wait until some spec questions are resolved.

## dateStyle/timeStyle (Stage 1)

- proposal: [proposal-ecma402-datetime-style](https://github.com/tc39/proposal-ecma402-datetime-style)

NC said the precanned sizes were discussed in the original `DateTimeFormat` design and would be easy to add; [DE](../../people/DE.md) cited Mozilla-internal use and Globalize.js as demand. Three spec issues were discussed:

- [Consider making BestFormatForStyle more specific](https://github.com/tc39/proposal-ecma402-datetime-style/issues/3) (#3): [DE](../../people/DE.md) asked whether to leave it undefined or bake in the CLDR-style schema; NC found CLDR fine and said the group will look into it.
- [Applying settings from the OS](https://github.com/tc39/proposal-ecma402-datetime-style/issues/4) (#4): NC said Chrome has no good way to read OS overrides, and the question applies to all Intl APIs. [SFC](../../people/SFC.md) related it to [ecma402#210](https://github.com/tc39/ecma402/issues/210) (pluggable data sources). [DE](../../people/DE.md) proposed leaving OS overrides as a follow-on and defining the styles as coming from CLDR for now; [SFC](../../people/SFC.md) said that layers well with a data-driven approach.
- [Consider error checking for using dateStyle/timeStyle together with other options](https://github.com/tc39/proposal-ecma402-datetime-style/issues/2) (#2): [DE](../../people/DE.md) did not want these to throw. [EAO](../../people/EAO.md) found the name `dateTimeStyle` (a connector) confusing, and [DE](../../people/DE.md) suggested following ICU by not exposing a direct way to set it. [SFC](../../people/SFC.md) advised studying real usage rather than assuming ICU is perfect, and NC said naming deserves a close look.

NC said there is implementation interest, and there were no concerns about bringing it to the November plenary. Related: `navigator.locale` ([whatwg/html#3046](https://github.com/whatwg/html/pull/3046)), which [DE](../../people/DE.md) saw as a possible way to pass around locale overrides.

[SFC](../../people/SFC.md) asked whether it is more useful as an `Intl` wrapper around Globalize or a Globalize wrapper around `Intl`; [EAO](../../people/EAO.md) argued the group's long-term preference is `Intl`, so polyfilling `Intl` lets the polyfill shrink over time, and [SFC](../../people/SFC.md) agreed.
