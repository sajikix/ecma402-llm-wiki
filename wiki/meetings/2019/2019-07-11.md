## Overview

Moderated by [SFC](../../people/SFC.md). TG2 reached consensus on the `fractionalSecondDigits` normative PR (#347), while the `quarter` PR (#345) was pushed back towards Stage 1-like status pending CLDR work. The proposal status round set targets of September for `Intl.RelativeTimeFormat` Stage 4 and discussed the data-size cost of volume and consumption units in the unified `Intl.NumberFormat` (PR #48). A long thread on string-enum casing ended in a recommendation of camelCase for `Intl.DisplayNames` and other active proposals. Further consensus items: `Intl.Locale` boolean keywords return `true` rather than an empty string (#65), and the date/time glue pattern follows ICU defaults (#338). Abbreviations are normalised to delegates.txt: SC → [SFC](../../people/SFC.md), CC → [CCN](../../people/CCN.md), FB → [FBN](../../people/FBN.md), FT → [FYT](../../people/FYT.md), JV → JVA, JW → [JSW](../../people/JSW.md), LB → [LEO](../../people/LEO.md), LH → LHO, RG → [RGN](../../people/RGN.md), RC → [RCA](../../people/RCA.md), `MM` → [MCM](../../people/MCM.md), VY → VYG, YM → [YMD](../../people/YMD.md). ## Casing

- proposal: [proposal-intl-displaynames#32](https://github.com/tc39/proposal-intl-displaynames/issues/32)

[SFC](../../people/SFC.md) laid out three options: kebab-case strings (W3C design principles, inconsistent when used as a key), camelCase everywhere, or supporting both. [FYT](../../people/FYT.md)'s key point was that the output of one API may be the input of another and that casing is beyond DisplayNames. [LEO](../../people/LEO.md) stated a strong preference for W3C but conceded that consistency wins, recommending camelCase without aliases; [FYT](../../people/FYT.md) agreed about avoiding aliases, [RGN](../../people/RGN.md) found the camelCase argument (output of one API usable as input to another) the most compelling although "really weak", and [JSW](../../people/JSW.md) wanted camelCase because most of JS uses it. [SFC](../../people/SFC.md) observed existing inconsistency (`formatToParts`, locale strings, "2-digit"), [CCN](../../people/CCN.md) argued casing should be consistent within a class, and the CSS-versus-`element.style` analogy (kebab in CSS, camelCase in JS) was raised. [LEO](../../people/LEO.md) posed two questions to the room: whether to recommend camelCase for DisplayNames, and whether that recommendation affects other active proposals such as NumberFormat (not changing shipped APIs). No objection was voiced to the first; for the second, [SFC](../../people/SFC.md) preferred camelCase for `sign: "exceptZero"` and noted unit identifiers such as `meter-per-second` stay kebab-case because they come from UTS 35; [RGN](../../people/RGN.md) agreed, and [LEO](../../people/LEO.md) took silence as assent. **Conclusion (silence taken as assent): recommend camelCase for `Intl.DisplayNames` and for other active proposals; unit identifiers remain kebab-case.**

## How to select the glue pattern?

- proposal: [ecma402#338](https://github.com/tc39/ecma402/issues/338)

With `dateStyle: long` and `timeStyle: short`, how date and time are joined needs a default; [SFC](../../people/SFC.md) asked whether exposing a key would be a useful feature. [FBN](../../people/FBN.md) suggested adopting ICU's behaviour for simplicity and [RGN](../../people/RGN.md) saw no compelling case to deviate from the default. **Conclusion: update the spec to adopt ICU's default behaviour, with no plans for an API right now.**
