## Overview

Moderated by [SFC](../../people/SFC.md). The status round prepared the December plenary: `Intl.RelativeTimeFormat` and the unified `Intl.NumberFormat` looked ready for a Stage 4 request ([CLA](../../people/CLA.md) to present), `Intl.Segmenter` was aiming for Stage 3, while `Intl.ListFormat` was held back by [SFC](../../people/SFC.md)'s objection to Stage 4 until the Spanish `disjunction` problem is fixed, and `Intl.Locale` and `dateStyle`/`timeStyle` were not December Stage 4 candidates. SRL's Unicode properties proposal drew sustained skepticism from [MCM](../../people/MCM.md) and others, [SFC](../../people/SFC.md) pitched `Intl.DurationFormat` at Stage 0 with [FYT](../../people/FYT.md) volunteering as champion, and the new MessageFormat Working Group was announced. Abbreviations are normalised to delegates.txt: USH → [USA](../../people/USA.md) (the attendee list itself writes USH). FBN speaks but is not in the attendee list; "FBR" in the Unicode properties discussion is kept as written (probably a typo, not mapped).

## MessageFormat Working Group

[RCA](../../people/RCA.md) (MessageFormat Working Group liaison) had sent an invite for the first meeting on 25 November, planning to share what had been collected from stakeholders so the group can define a roadmap and next steps.

## Intl.ListFormat (Stage 3)

- proposal: [proposal-intl-list-format](https://github.com/zbraniecki/proposal-intl-list-format)
- proposal: [proposal-intl-list-format#45](https://github.com/tc39/proposal-intl-list-format/issues/45)

The main blocker is the Spanish `type: 'disjunction'` bug. [SFC](../../people/SFC.md) reported [JSW](../../people/JSW.md)'s ICU patch (unicode-org/icu#894) was approved by ICU-TC and awaited another review from [FYT](../../people/FYT.md), and that data from Google's LPM was still pending; SRL had a short list of locales needing the fix from George Rhoten (Apple) and said Korean and Maltese also need exceptions ([YMD](../../people/YMD.md) doubted Maltese). [SFC](../../people/SFC.md) refused to go to Stage 4 with this problem ("embarrassing"); SRL objected that it has been in production for some time, [DE](../../people/DE.md) asked whether any browser would ship without it ([JSW](../../people/JSW.md) preferred waiting) and noted that Stage 4 requires multiple implementations, and [ZB](../../people/ZB.md) proposed exposing `MozListFormat` internally to gather feedback from translators in every locale. SRL and [DE](../../people/DE.md) pointed out the spec's data model does not allow the intended output change, so the spec also needs to change; [FYT](../../people/FYT.md) floated shipping what CLDR gives; [SFC](../../people/SFC.md) asked who the spec champion is, since the spec could be changed to allow the fix. **Conclusion: [SFC](../../people/SFC.md) objected to moving forward without a solution; the group will eventually come back to this issue.**

## Intl.Locale (Stage 3)

- proposal: [proposal-intl-locale](https://github.com/zbraniecki/proposal-intl-locale)

`Intl.Locale` had landed in SpiderMonkey behind a preference. [DE](../../people/DE.md) was confused about [JSW](../../people/JSW.md)'s concern that SpiderMonkey's behaviour differed from a canonicalization implementation (anba usually being right), and clarified that this was no longer a December 2019 Stage 4 candidate. Later in the session [JSW](../../people/JSW.md) found the concern invalid: TR35 version 34 required a canonical attribute/keyword order that version 36 removed. [CLA](../../people/CLA.md) wanted to see the spec text; [ZB](../../people/ZB.md) offered to present in December, and [JSW](../../people/JSW.md) would file a bug to get it fully landed in Firefox.

## Intl.NumberFormat Unified API Proposal (Stage 3)

- proposal: [proposal-unified-intl-numberformat](https://github.com/sffc/proposal-unified-intl-numberformat)

[SFC](../../people/SFC.md) had a PR fixing several open issues: mostly editorial, plus one minor behaviour issue for later; SpiderMonkey was shipping behind a flag (enabled in Firefox 70 but needing a flag). The one ICU issue was how to show the sign for values that round to zero for display, fixed in ICU but only available from ICU 67 in February 2020; V8 did not cherry-pick the 500-600 line change. [DE](../../people/DE.md) argued the proposal still gives users value without the fix and [JSW](../../people/JSW.md) agreed; [DE](../../people/DE.md) said it was good enough, being on a path to stable, to move to Stage 4. [CLA](../../people/CLA.md) would present the deck ([SFC](../../people/SFC.md) to follow up with [CLA](../../people/CLA.md) offline). No formal conclusion line was recorded; the discussion pointed to a Stage 4 request at the December plenary without waiting for the round-to-zero fix.

## Intl.DateFormat.prototype.formatRange (Stage 3)

- proposal: [proposal-intl-DateTimeFormat-formatRange](https://github.com/fabalbon/proposal-intl-DateTimeFormat-formatRange)

FBN is leading it. A few ICU issues remain ([FYT](../../people/FYT.md) took some; one is bigger): ICU not respecting interval formats, no proper `dateStyle`/`timeStyle` support (only via an ugly workaround), and a C-binding gap, giving an inconsistency between interval and regular date format output. [DE](../../people/DE.md) judged these blocking for Stage 4; [FYT](../../people/FYT.md) asked whether the engine could work around the issue internally instead of waiting for ICU, and [SFC](../../people/SFC.md) said a separate constructor-intent issue could be a behaviour change.

## Intl.DisplayNames (Stage 3)

- proposal: [proposal-intl-displaynames](https://github.com/tc39-transfer/proposal-intl-displaynames)

The notes record that it advanced to Stage 3 at the October TC39 meeting and that it now takes a `calendar` option to name "month", "weekday", "quarter" and "dayPeriod". [LEO](../../people/LEO.md) was finishing tests (missing mainly `supportedLocalesOf` and `of`). [FYT](../../people/FYT.md) was implementing it in V8 and asked how to handle 13-month years, since the Chinese leap month is not always the same numeric month; [SFC](../../people/SFC.md) asked for a recommendation at the next meeting. [LEO](../../people/LEO.md) hoped for shipping around February 2020, but [FYT](../../people/FYT.md) did not think Stage 4 by February was feasible; [JSW](../../people/JSW.md) noted unresolved bugs.

## Unicode Properties

- proposal: [ecma402#90](https://github.com/tc39/ecma402/issues/90) ([es-unicode-properties](https://github.com/srl295/es-unicode-properties))

SRL argued the proposal addresses use cases (text analysis, extracting a property rather than testing it, polyfilling) that regexes do not cover, and that these are fundamental properties. [MCM](../../people/MCM.md) countered that segmentation covers many such cases, that higher-level APIs should be implemented directly, and suggested number parsing; [SFC](../../people/SFC.md) said re-litigating parsing in ECMA-402 was out of scope. [FYT](../../people/FYT.md) and [LEO](../../people/LEO.md) held that it belongs in ECMA-262 (regex lives there), [LEO](../../people/LEO.md) having heard TC53 interest. [SFC](../../people/SFC.md) suggested Stage 1 would raise awareness and gather use cases, while [DE](../../people/DE.md) preferred to just gather use cases since Stage 0 versus 1 adds little; [MCM](../../people/MCM.md) objected that a web standard needs use cases. No conclusion; the discussion went offline.
