## Overview

Moderated by [SFC](../../people/SFC.md). The group closed two `formatRange` data-loading and `dateStyle`/`timeStyle` questions (no spec change for data loading; no exception for `dateStyle`/`timeStyle` with `formatRange`), gave consensus to an off-by-one fix in `PartitionPattern` (#392), split the calendar-dependent `Intl.DisplayNames` types into a v2, and walked through the Stage 3 status list ahead of a possible Stage 4 request in February for `Intl.Locale` and the unified `Intl.NumberFormat`. [SFC](../../people/SFC.md) also reported that `Intl.RelativeTimeFormat` had been approved for Stage 4 at TC39, and reported progress on first-class calendar support in [Temporal](../../proposals/temporal.md), then opened the default calendar question (proposal-[temporal](../../proposals/temporal.md)#292). [LHO](../../people/LHO.md) speaks but is not in the attendee list. Abbreviations in the notes already match delegates.txt.

## Potential problem with data loading #17

- proposal: [proposal-intl-DateTimeFormat-formatRange#17](https://github.com/tc39/proposal-intl-DateTimeFormat-formatRange/issues/17)

[SFC](../../people/SFC.md) reported estimates showing the extra data and code for `formatRange` is small (about 48 KiB of ICU code; skeleton resolution means the full data need not be loaded), leaving memory consumption as a possible Stage 3 concern. [FBN](../../people/FBN.md) favoured keeping the spec as is and loading data in the constructor; [JSW](../../people/JSW.md) said the size increase looked fine and engines already initialise lazily. [SFC](../../people/SFC.md) argued that optimization concerns should not drive spec changes before implementations exist. **Conclusion: close the issue.**

## About interop with dateStyle/timeStyle #19

- proposal: [proposal-intl-DateTimeFormat-formatRange#19](https://github.com/tc39/proposal-intl-DateTimeFormat-formatRange/issues/19)

`dateStyle`/`timeStyle` are patterns for a single date, so there is no CLDR data for ranges. [SFC](../../people/SFC.md) proposed forbidding them with `formatRange` (CLDR/ICU engineers prefer skeletons), while [FBN](../../people/FBN.md), [ZB](../../people/ZB.md) and [FYT](../../people/FYT.md) stressed that styles should display the same way in all cases and that ranges should eventually be supported ([ZB](../../people/ZB.md) later said it is not a blocker and throwing errors is acceptable). V8 already ships a workaround that derives a range from a skeleton, and [SFC](../../people/SFC.md) suggested SpiderMonkey do the same or throw. The workaround means `format(d)` and `formatRange(d, d)` can differ, which [SFC](../../people/SFC.md) flagged as a round-trip problem; [FYT](../../people/FYT.md) objected that a `TypeError` at format time is not where the problem actually is. **Conclusion: do not throw an exception. [FBN](../../people/FBN.md) to work with [FYT](../../people/FYT.md) to decide whether to relax the spec requirement that `format` and `formatRange` outputs are equal, or leave it as a known compliance issue until ICU/CLDR are fixed.**

## Default Calendar

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal-temporal#292](https://github.com/tc39/proposal-temporal/issues/292)

[SFC](../../people/SFC.md): "We want people to do Intl correctly by default." The default calendar had been ISO; [SFC](../../people/SFC.md) laid out the issue's four options and asked for the committee's view. [CLA](../../people/CLA.md) and [RCA](../../people/RCA.md) found option 4 problematic (browser-side errors; [RCA](../../people/RCA.md) called it "essentially no-go") and liked 2 and 3; [SFC](../../people/SFC.md) liked 2 and 3 best; [LHO](../../people/LHO.md) called 2 best, since in headless environments like Node each request has different Intl preferences. [SFC](../../people/SFC.md) added that [PDL](../../people/PDL.md) prefers option 1 or 4 and would not consider 2 or 3 "unless there is overwhelming sentiment from the i18n side". No conclusion was recorded.
