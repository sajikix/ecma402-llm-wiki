## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). The file is named 2024-03-28, but its own title reads "2023-03-28 ECMA-402 Meeting" (a typo; the filename date is used here). [HJS](../../people/HJS.md) attended only the later part. The dominant topic was TG2's position on dropping string source (syntax) support from the Intl MessageFormat proposal, which ended with [EAO](../../people/EAO.md) stepping back as champion. [LAF](../../people/LAF.md) presented an `eraDisplay` idea, and [EAO](../../people/EAO.md) floated wrapper types such as `UnitNumber`. TG2 also agreed on the direction for range validation order (#691) and acknowledged a `resolvedOptions` year bug (#703).

## Drop string source support #47

- wiki: [Intl.MessageFormat](../../proposals/intl-messageformat.md)
- proposal: [proposal-intl-messageformat#47](https://github.com/tc39/proposal-intl-messageformat/pull/47)

[EAO](../../people/EAO.md) reported that colleagues at Mozilla believed leaving out the DSL would not further fracture an already fractured ecosystem, since the MessageFormat 2 data model makes migration between representations easier. [SFC](../../people/SFC.md) gave the Google i18n position in five points: the WG's primary deliverable is the syntax, not the data model; `Intl.MessageFormat` is only useful with a serialized form, otherwise users invent competing ones; a JSON-only form is verbose to author; processing a data model into a string is too easy to meet the ECMA-402 bar; and the data model is still expected to change after tech preview feedback. [FYT](../../people/FYT.md) added concerns about load when messages reach billions of users. [USA](../../people/USA.md) argued the status quo is a compromise, that parsing can be done in userland, and offered to co-champion a separate parser proposal; [EAO](../../people/EAO.md) planned a third proposal for the parser, similar to the message resource proposal. [SFC](../../people/SFC.md) said the parser removal turns it into "a JSON-based string formatting proposal" and Google could not support advancing to Stage 2 without addressing the concerns, though [SFC](../../people/SFC.md) remains excited about MessageFormat and suggested pausing the proposal. [EAO](../../people/EAO.md) said no resolution of the syntax-versus-data-model disagreement seemed possible through this discussion and stepped back from championing these proposals (this would go through TG1; [DLM](../../people/DLM.md) was named as the other, inactive, champion of `Intl.MessageFormat`). [SFC](../../people/SFC.md) suggested [EAO](../../people/EAO.md) record that Stage 1 was reached and leave the proposal for another champion. No formal conclusion is recorded.

## Displaying era for a date: how CLDR may help

- slide: [link](https://docs.google.com/presentation/d/11wsfwbJZzTFEWrD0ZCJPD3uPhSACbGr6O37asZnzvZk/edit#slide=id.p)

[LAF](../../people/LAF.md) argued that an era is always the basis for a year but is conventionally implied, and proposed CLDR attributes giving the year ranges in which eras are needed, plus an `eraDisplay` option with four values: `"auto"` (follow CLDR), `"always"`, `"never"` and `"hide"` (mark the era as implied). [SFC](../../people/SFC.md) welcomed locale-dependent behaviour, asked how `"auto"` and `"hide"` differ (`"hide"` means the document is understood to use that calendar and the era shows only if it could be a different epoch), and questioned the added concept of a reckoning system separate from calendar and era. [SFC](../../people/SFC.md) suggested a Julian-to-Gregorian transition calendar (e.g. `juli-greg`), and thought this could land in CLDR 46 before the ECMAScript proposal moves; [SFC](../../people/SFC.md) offered to invite [LAF](../../people/LAF.md) to a CLDR meeting.

## Introducing wrapper units like CurrencyNumber and UnitNumber to keep the options together for formatting and other operations.

[EAO](../../people/EAO.md), inspired by [SFC](../../people/SFC.md)'s concerns in the MessageFormat 2 function registry discussions, observed that `unit`, `currency` and `timeZone` are part of the value being formatted rather than formatting options, and asked whether a proposal for a wrapper holding a value with its unit or currency would be supported (not championed by [EAO](../../people/EAO.md)). [SFC](../../people/SFC.md) said Temporal solves this for time zones and the Decimal proposal for precision; for units, the smart-unit proposals on the backburner make a "unit with quantity" type interesting; there would be no currency conversion in the standard; and the motivation is weaker for currency. [SFC](../../people/SFC.md) supported the direction if someone pursues it.

## Intl.NumberFormat compact notation leaves out comma #751

- proposal: [ecma402#751](https://github.com/tc39/ecma402/issues/751)

[SFC](../../people/SFC.md) first saw an engine bug needing test coverage, but [RGN](../../people/RGN.md) found both outputs valid and locale-dependent and was uncomfortable asserting guarantees in tests. [YSZ](../../people/YSZ.md) reported that V8, SpiderMonkey and JSC all agree now (comma in both cases). [SFC](../../people/SFC.md) closed the issue.

## Clarification on PartitionDateTimePattern: Constructing NumberFormat instances

- proposal: [ecma402#563](https://github.com/tc39/ecma402/issues/563)

[RGN](../../people/RGN.md) preferred moving the construction of `NumberFormat` instances (steps 4-9 of FormatDateTimePattern) out of the long algorithm and onto the `DateTimeFormat` object, a purely editorial change. [SFC](../../people/SFC.md) related it to wanting minimum integer digits to be a format-time concern (it is a data-model matter: "year 2" versus "year 02"), possibly via a private abstract operation. [RGN](../../people/RGN.md) replied that 402 consistently puts all options in the constructor and any change to that pattern should be done holistically.

## Numeric range validation is inconsistent #691

- proposal: [ecma402#691](https://github.com/tc39/ecma402/issues/691)

[RGN](../../people/RGN.md): options such as `minimumIntegerDigits` are range-checked before truncation, unlike Temporal's "range validation follows truncation" and ECMA-262's `toFixed`; fixing it is a normative change unlikely to affect real code. [SFC](../../people/SFC.md) proposed a 402 PR plus a 30 minute TG1 agenda item to adopt a common style. No objections; [BAN](../../people/BAN.md) and [FYT](../../people/FYT.md) supported. **Conclusion: someone creates an ECMA-402 PR and puts it on the TG1 agenda to establish a standard style to follow in these cases now and in the future.**

## How to show different language time formats in different countries #703

- proposal: [ecma402#703](https://github.com/tc39/ecma402/issues/703)

The discussion focused on `resolvedOptions` not round-tripping for formatting behaviour (e.g. Chinese calendar output contains `relatedYear` and `yearName` while `resolvedOptions` lacks a year). [SFC](../../people/SFC.md) suggested following Anba's suggestion and adding test262 coverage that a year in the input options yields a year in the output; the slots are set from the best-format pattern in CreateDateTimeFormat step 45, which [SFC](../../people/SFC.md) regarded as a spec bug. [RGN](../../people/RGN.md) doubted a spec change was required and questioned what value a derived year field would take. **Conclusion: the observed behaviour is a bug (the output contains a year, so `resolvedOptions` should too); unclear whether it is a spec or an implementation bug; further investigation warranted.**
