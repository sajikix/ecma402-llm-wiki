## Overview

Co-moderated by [SFC](../../people/SFC.md) and [USA](../../people/USA.md). [EAO](../../people/EAO.md) brought `Intl.MessageFormat` for a Stage 2 discussion, but after pushback from some TG1 members against adding a new DSL, TG2 advised turning the TG1 slot into a stage update rather than a Stage 2 request. TG2 approved normative PR #846, agreed not to change default time zone canonicalization before [Temporal](../../proposals/temporal.md) lands, and asked for test262 coverage and docs (not new API) for currency rounding behaviour. [JGT](../../people/JGT.md) spoke but is not in the attendee list. In the notes, `YSK` (JSC implementer update) is a typo for [YSZ](../../people/YSZ.md).

[USA](../../people/USA.md) mentioned Anba's editorial PR removing the `dataLocale` alias; [BAN](../../people/BAN.md) made table-iteration wording consistent with ECMA-262 (changes in `DateTimeFormat`). ## Intl.MessageFormat for Stage 2?

- wiki: [Intl.MessageFormat](../../proposals/intl-messageformat.md)
- proposal: [proposal-intl-messageformat](https://github.com/tc39/proposal-intl-messageformat)
- slide: [link](https://docs.google.com/presentation/d/1ejR7UZXOxywDxC-rHh4uJftvKpbdSirpmD5mHwCKlCA/edit)

[EAO](../../people/EAO.md) presented the proposal: [Intl.MessageFormat](../../proposals/intl-messageformat.md) was accepted for Stage 1 about two years earlier (with [MessageResource](../../proposals/intl-messageresource.md) split off), the formal spec language is largely complete, and the syntax and data model come from MF2 in Unicode. The constructor takes `source, locales, options` ([SFC](../../people/SFC.md) and others suggested `locales, source, options`), and `format()` takes the values plus an `onError` parameter whose default is to warn rather than throw, because messages come from translators and mismatches are hard for developers to test for. Because some TG1 members said they are "not necessarily comfortable with us bringing in any more DSL to JavaScript until it is very very stable", [EAO](../../people/EAO.md) floated leaving out the syntax and accepting only a pre-parsed MessageData structure. [SFC](../../people/SFC.md) said the proposal would be less motivated without the syntax and listed the Stage 2 tests: is it hard to do in userland, would it have wide impact, is there prior art. [SFC](../../people/SFC.md) said an API that "takes an AST and interpolates stuff into a string" might be seen as a userland library, and that Stage 2 should be gated on the Unicode MF2 spec reaching Stage 3 or the equivalent. [EAO](../../people/EAO.md) noted the data model is JSON-serializable (parse on a server, ship JSON) and could unify a fractured ecosystem; [DLM](../../people/DLM.md) said the parser is a core part of the proposal and would rather wait for it than drop it; [USA](../../people/USA.md) argued that the DSL need not be stable for Stage 2 (citing [Temporal](../../proposals/temporal.md)'s serialization format) and that context should be explained to TG1; [SFC](../../people/SFC.md) held that the question of syntax stability belongs to TG1 as the decision-maker, and that TG2 time is better spent on API shape and error handlers. The group favoured a TG1 stage update (about half progress and half history and stability) as a temperature check; [EAO](../../people/EAO.md) agreed to change the TG1 agenda item to an update, to ask what the minimum bar for accepting a DSL is, and welcomed help with the presentation, which [USA](../../people/USA.md) offered. The notes record no formal `Conclusion` heading, and no decision on the constructor argument order.

## Draft plan to align canonical time zone IDs across implementations #806

- proposal: [ecma402#806](https://github.com/tc39/ecma402/issues/806)

[SFC](../../people/SFC.md) asked whether the three engines could be made consistent about the _default_ time zone returned by `resolvedOptions().timeZone`: Firefox returns modern ids (for example `Asia/Ho_Chi_Minh`) while Chrome returns `Asia/Saigon`. [JGT](../../people/JGT.md) recalled that the [Temporal](../../proposals/temporal.md) canonical-time-zone changes approved by plenary stop canonicalizing explicitly supplied ids, and [HJS](../../people/HJS.md) argued that default and explicit canonicalization should stay consistent. [SFC](../../people/SFC.md) summarised the interim options for the three cases (default, `Asia/Saigon`, `Asia/Ho_Chi_Minh`). [FYT](../../people/FYT.md) and [JGT](../../people/JGT.md) argued against changing behaviour twice: a change now has a risk and cost, and the end state arrives with [Temporal](../../proposals/temporal.md) (which will provide `timeZone.equals`-style comparison); [EAO](../../people/EAO.md) argued there is a moral case for honouring renamed cities and suggested a standalone time zone proposal, which [JGT](../../people/JGT.md) did not support. [SFC](../../people/SFC.md) noted that standards bodies should be the last to adopt a change and that 2024 has more headroom for [Temporal](../../proposals/temporal.md). **Conclusion: do not make any changes right now; wait for [Temporal](../../proposals/temporal.md) and make the change then. If [Temporal](../../proposals/temporal.md)'s timeline changes, potentially revisit.**

## Support cash rounding #835

- proposal: [ecma402#835](https://github.com/tc39/ecma402/issues/835)

[BAN](../../people/BAN.md) noted CLDR has digit counts and cash-rounding increments but that cash rounding is not appropriate in many cases (some jurisdictions require rounding to the penny online), and that making CLDR use required was softened to recommended. [EAO](../../people/EAO.md) observed that CLDR seems to lack data for online transactions, [HJS](../../people/HJS.md) that attaching rounding to currencies rather than regions is the wrong domain model, and [SFC](../../people/SFC.md) that Intl should not be a data source for law and is uneasy about rounding monetary values at all (see ecma402#134). [SFC](../../people/SFC.md) proposed focusing on the original problem (a better source for currency digits), keeping financial rounding as the behaviour of 402, and documenting it; [BAN](../../people/BAN.md) agreed, and [HJS](../../people/HJS.md) agreed with keeping more digits. [EAO](../../people/EAO.md) asked for an API that returns the resolved value; [SFC](../../people/SFC.md) suggested it fit with the Decimal proposal and that this need not be decided for San Diego. **Conclusion: add Test262 and docs for the current spec behaviour. LGTM: [SFC](../../people/SFC.md), [BAN](../../people/BAN.md), [FYT](../../people/FYT.md).**
